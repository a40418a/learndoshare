왜 알아야 하나

밀버스는 사람이 읽는 문서만으로 끝나지 않는다. 새 프로젝트를 시작하는 사람은 Claude Code에게 "이 브랜드로 바꿔 줘"라고 말할 것이고, 그때 Claude가 우리 규칙대로 움직여야 한다. 규칙을 모르면 Claude는 lightning-button 내부 스타일을 덮어쓰거나 컴포넌트에 hex 색을 박아 넣을 수 있다.

② 브랜드 요청Storybook 브랜드 명세 페이지나 채팅으로 입력

이 네 단계를 Claude가 순서대로, 금지 사항을 지키며 수행하게 만드는 문서 묶음을 이 문서에서는 런북이라고 부른다. 위 흐름은 패키지·CLI 설계의 흐름이다(설계 0장). 2026-10-12 갱신: ①의 init과 ③의 check, .claude 묶음의 permissions와 hook은 구현됐다(Task 11·12. 이 문서의 "Task 번호"는 패키지 구현 계획의 작업 번호다. 계획서는 공개 저장소에 없어 근거는 설계 문서 장 번호로 적는다). 2026-10-13 갱신: ②의 브랜드 명세 페이지(Task 19)와 ③의 milvus-brand skill·milvus-design.md 내용(Task 20)도 구현됐다. 2026-10-14 갱신: ④ deploy도 구현했고(Task 22), tgz로 설치한 프로젝트로 ①~④를 한 번 이어서 해 본 리허설에서 배포 두 단계가 모두 성공했다(Task 23). ②에서 ④까지는 브랜드 요청 → 반영 흐름에 자세히 적었다.

plugin과 marketplace

plugin은 skill, agent, hook, MCP 서버를 한 단위로 설치하는 디렉터리다. marketplace는 plugin 목록과 받을 위치를 적은 .claude-plugin/marketplace.json이 있는 저장소(또는 디렉터리)다. 호스팅되는 스토어가 아니라 카탈로그 파일이다.

my-plugin/
├── .claude-plugin/
│   └── plugin.json        ← 매니페스트. 선택이지만 쓰면 name만 필수
├── skills/
│   └── review/SKILL.md    ← /my-plugin:review
├── agents/
├── hooks/hooks.json
└── .mcp.json
{
  "name": "my-marketplace",
  "owner": { "name": "Your Name" },
  "plugins": [
    { "name": "my-first-plugin", "source": "./plugins/my-first-plugin", "description": "..." }
  ]
}
  • marketplace.json에는 name, owner, plugins가 필요하다. 각 plugin 항목에는 설치할 때 쓰는 name과 받을 위치 source를 적는다
  • 상대 경로 source는 .claude-plugin/이 든 marketplace 루트 기준이다. ..은 쓸 수 없다
  • 항목의 name과 plugin의 plugin.json name을 같게 둔다. 다르면 설치가 실패하기 쉽다
  • 셸에서 claude plugin validate ./my-marketplace로 검증한다

설치 명령 (세션 안)

/plugin marketplace add owner/repo           # GitHub 저장소. #v1.2.0 처럼 ref 고정 가능
/plugin install plugin-name@marketplace-name # 상세 패널이 열리고 설치 범위를 고른다
/plugin                                      # Discover / Installed / Marketplaces 탭
/plugin uninstall                            # 패널에서 제거
/plugin marketplace remove <name>            # marketplace와 거기서 설치한 plugin 제거
설치 범위기록되는 곳의미
user~/.claude/settings.json이 컴퓨터의 내 모든 프로젝트
project.claude/settings.json (커밋)저장소 협업자 모두에게 켜짐. 단, 각자 한 번 설치는 해야 한다
local.claude/settings.local.json나만, 이 저장소에서만

데스크톱 앱 Code 탭에서는 입력창 옆 + → Plugins → Add plugin으로 같은 일을 한다. 클라우드 세션(claude.ai/code)은 로컬에 설치한 plugin을 읽지 않는다.

hook과 permissions: 반드시 막아야 할 때

hook은 Claude Code가 특정 시점(도구 실행 전후, 세션 시작 등)에 실행하는 셸 명령이다. LLM이 "지키기로 선택"하는 것이 아니라 항상 실행된다. PreToolUse hook 스크립트가 exit code 2로 끝나면 그 도구 호출이 막히고, stderr 메시지가 Claude에게 피드백으로 간다.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

PROTECTED_PATTERNS=(".sfdx/" ".env" "pnpm-lock.yaml")   # 예시 목록
for pattern in "${PROTECTED_PATTERNS[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH 는 밀버스 런북에서 수정 금지" >&2
    exit 2
  fi
done
exit 0

스크립트는 실행 권한(chmod +x)이 있어야 하고 jq가 필요하다. 세션에서 /hooks로 등록된 hook을 확인한다.

PostToolUse: 도구가 실행된 뒤에 알리기 (2026-10-12 추가)

PostToolUse hook은 도구가 이미 실행된 뒤에 돈다. 그래서 막을 수는 없고, Claude에게 알려서 고치게 한다. 무엇이 Claude에게 가는지는 종료 코드에 따라 다르다.

hook 결과Claude가 보는 것
종료 코드 2stderr. 도구는 이미 실행된 상태로 남는다
종료 코드 0, stderr에만 쓴 경우아무것도 보지 못한다. 공식 문서는 0으로 끝난 hook의 stderr를 Claude가 보지 못하고 디버그 로그로만 확인할 수 있다고 적는다. 이 이벤트의 stdout도 디버그 로그로만 간다
종료 코드 0, stdout에 JSON hookSpecificOutput.additionalContext그 문자열. Claude Code가 system reminder로 감싸 도구 결과 옆에 넣고, Claude는 다음 요청에서 읽는다. 채팅 화면에 메시지로 보이지는 않는다
{
  "hookSpecificOutput": {
    "hookEventName": "PostToolUse",
    "additionalContext": "Claude에게 전할 문장"
  }
}

hook 입력 JSON에는 작업 디렉터리 cwd가 들어 있고, command hook은 세션을 시작한 프로젝트 루트를 환경 변수 CLAUDE_PROJECT_DIR로 받는다. 밀버스 hook은 이 둘로 패키지를 찾는다(아래).

permissions: 스크립트 없이 막거나 묻기

settings의 permissions에 규칙을 적으면 스크립트 없이 도구 호출을 막거나(deny) 실행 전에 묻게(ask) 할 수 있다.

  • 규칙은 deny → ask → allow 순서로 보고, 처음 맞는 것이 결과를 정한다. 넓은 deny는 좁은 allow로 뚫리지 않는다
  • Edit(...) 규칙은 파일을 고치는 모든 내장 도구에 적용된다
  • 경로가 / 하나로 시작하면 설정 파일 기준이다. 프로젝트 설정에서는 프로젝트(주 작업 디렉터리) 기준이다. 파일 시스템 절대 경로는 //로 쓴다
  • Bash(pnpm milvus deploy *)처럼 끝의 * 앞에 공백이 있으면 인자 없는 pnpm milvus deploy에도 맞는다
  • Bash의 ask 규칙은 auto 모드에서도 묻는다
  • PreToolUse hook이 허용을 돌려줘도 deny·ask 규칙은 그대로 적용된다. 반대로 exit 2로 막는 hook은 allow 규칙보다 먼저 막는다

init의 사전 점검

pnpm milvus init --target-org <별칭> (--brand <이름> | --from-org) [--no-vf]는 아래를 차례로 확인한다. 하나라도 실패하면 프로젝트에 아무것도 쓰지 않고 한국어 오류와 종료 코드 1로 끝난다.

  1. 옵션: --target-org가 있고, --brand와 --from-org 중 정확히 하나만 있다. 브랜드 이름은 영문자로 시작하고 영문자·숫자·_만 쓴다(__ 금지, _로 끝나지 않음, 한글 불가)
  2. Node 22.18 이상(23.x는 23.6 이상). .ts를 그대로 실행하는 버전이고 패키지 engines와 같다
  3. 위로 올라가며 sfdx-project.json을 찾고, 기본 패키지 폴더가 force-app인지 본다
  4. .claude/settings.json이 있으면 올바른 JSON 객체인지 본다. 몇 초 걸리는 sf 조회보다 먼저 한다
  5. 이미 milvus.config.json이 있고 그 버전이 설치된 패키지 버전과 다르면 멈추고 pnpm milvus update를 쓰라고 안내한다. 같은 버전이면 다시 실행해도 된다
  6. sf가 설치되어 있고 <별칭> org에 로그인되어 있는지 본다(읽기만 하는 조회). sf는 프로젝트 밖 임시 폴더에서 실행한다
  7. --from-org면 org의 활성 테마 이름을 먼저 읽고, 그 테마·BrandingSet·로고만 임시 폴더로 받아 검증한다. 활성 테마가 SLDS 2(SLDS_v2)가 아니면 "밀버스는 SLDS 2 테마를 기준으로 합니다"로 멈춘다(#22). 로고 자산 이름과 BRAND_IMAGE는 org 값 그대로 쓴다. 배포할 때 org에 같은 로고가 하나 더 생기지 않게 하려는 것이다

init이 쓰는 방식

  • 이미 있는 파일은 덮어쓰지 않는다. 건너뛴 파일은 목록으로 알려 준다. 예외로 다음은 기존 내용에 더한다: .claude/settings.json(병합), CLAUDE.md(@milvus-design.md 한 줄), .gitignore(.milvus/), .forceignore(**/__tests__/**), .npmrc(범위 레지스트리와 토큰 환경 변수 두 줄, 07 pnpm), package.json(scripts.storybook이 없을 때만)
  • JSON 파일을 고칠 때는 기존 들여쓰기(공백 수 또는 탭)를 지킨다. 새로 만드는 파일은 2칸이다
  • sfdx-project.json은 읽기만 한다. 밀버스 LWC는 JavaScript라서 defaultLwcLanguage를 바꾸지 않는다(10/9 결정 D1, 02 LWC)
  • --no-vf: VF용 파일(milvusHead 컴포넌트, milvusVf 정적 리소스)을 만들지 않고 milvus.config.json의 vf를 false로 둔다. 기본은 포함이다
  • 모든 결과를 먼저 만든 뒤에 쓰므로, 병합할 JSON이 깨져 있으면 아무것도 쓰지 않는다. 두 번 실행해도 결과가 같다(tests/init.test.ts)

  // pnpm을 거치지 않는다(기동 약 0.3초, Windows의 pnpm.cmd에 셸이 필요한 문제). 프로젝트의 node_modules에서 패키지를 찾아 node로 직접 실행한다
  const start = process.env.CLAUDE_PROJECT_DIR || input.cwd;
  let cli;
  try {
    cli = join(dirname(createRequire(join(start, "package.json")).resolve(`${PKG}/package.json`)), "dist/cli/index.js");
    if (!existsSync(cli)) throw new Error(cli);
  } catch {
    process.stderr.write(`milvus-check hook: ${start}에서 ${PKG}을 찾지 못했습니다. pnpm install을 실행하세요\n`);
    process.exit(1);
  }
  // 고친 파일의 폴더에서 실행한다. check가 위로 올라가며 sfdx-project.json을 찾는다(worktree에서도 그 파일의 프로젝트를 본다)

  if (r.status === 0) {

  • pnpm을 거치지 않는다: pnpm milvus check --style 대신, 프로젝트의 node_modules에서 @a40418a/milvus-design-system/package.json을 찾아 그 패키지의 dist/cli/index.js를 지금 실행 중인 node(process.execPath)로 직접 실행한다. pnpm 기동 시간(약 0.3초)과 Windows에서 pnpm.cmd를 실행하려면 셸이 필요한 문제를 없앤다. 인자는 배열로 넘기고 셸을 쓰지 않는다. 찾는 시작 위치는 CLAUDE_PROJECT_DIR, 없으면 hook 입력의 cwd다. 패키지를 찾지 못하면 한국어 오류로 1이다
  • check --style이 보는 것: util.css 규칙과 피드백 색 대비(설계 5.2·5.3), milvusOverride.css의 경고 규칙(5.1), milvus.config.json 브랜드의 LEXTHEMING<브랜드> BrandingSet의 BRAND_COLOR 형식(#RRGGBB). 다른 BrandingSet(Experience Cloud 사이트 등)은 보지 않는다. 정규식 수준이라 200ms 안에 끝난다(tests/check.test.ts)
  • 결과 전달: 위 PostToolUse 표대로 나눈다. 고칠 것이 있으면 check가 2로 끝나고, hook은 stderr(고칠 값)를 그대로 넘기며 2로 끝난다. Claude가 그 값을 보고 고친다. milvusOverride.css 경고만 있으면 check는 0으로 끝나는데, 0이면 stderr가 Claude에게 가지 않는다. 그래서 hook이 경고 문장("공식 권고 밖" 포함)을 additionalContext로 stdout에 쓴다. 경고도 없으면 아무것도 쓰지 않는다
  • 커밋된 설정의 hook은 팀원에게도 별도 동의 없이 실행되므로 hook은 하나만 둔다(설계 7.2). 공식 문서에 따르면 대화형 세션은 폴더 신뢰 대화상자를 받아들이기 전까지 settings 파일의 hook을 실행하지 않는다. 받아들인 뒤에 hook마다 따로 묻는다는 설명은 문서에 없다. claude -p·SDK 세션은 대화상자 없이 신뢰한 것으로 보고 커밋된 hook을 실행한다. command hook은 사용자의 전체 권한으로 셸 명령을 실행한다. 이 안내는 milvus-design.md 4절(파일 지도) 끝에 한 줄로 적었다(2026-10-13, tests/templates.test.ts가 확인)

개념

  • 파일로 넘긴다: 명세 페이지(브라우저)와 Claude Code(터미널)는 서로를 직접 부르지 않는다. 프로젝트 루트의 Markdown 파일 하나를 사이에 둔다. 사람이 편집기로 열어 고칠 수도 있고 git으로 남길 수도 있다
  • skill: SKILL.md에 적은 절차다. 평소에는 description만 컨텍스트에 있고, Claude가 description을 보고 지금 요청과 관련 있다고 판단하거나 사용자가 /skill-name으로 부르면 본문 전체가 들어온다. 프로젝트 skill은 .claude/skills/<이름>/SKILL.md에 둔다(skill 자세히)
  • 지시와 강제: skill과 milvus-design.md는 Claude가 따르는 지시다. 반드시 지켜야 하는 것은 hook과 permissions가 맡는다. PostToolUse hook이 2로 끝나면 stderr가 Claude에게 가고(도구는 이미 실행됨), 0으로 끝난 hook의 stderr는 Claude가 보지 못한다. permissions 규칙은 deny → ask → allow 순서로 보고, Bash의 ask 규칙은 auto 모드에서도 묻는다
  • permissions 규칙의 한계: Bash 규칙은 Claude가 쓴 명령 문자열에 맞춘다. 공식 문서는 같은 프로그램을 다른 형태로 부르면 규칙에 맞지 않으므로, deny·ask 규칙이 그 프로그램을 둘러싼 보안 경계는 아니라고 적는다. 그래서 밀버스는 milvus deploy의 실행 형태 4가지를 모두 ask에 넣고, 채팅 승인도 skill 절차로 따로 요구한다

Q6. README 11장의 H7(관리 파일 수정 차단 hook)과 H2(sf 명령 차단 hook, 3층)는 패키지 설계에서 무엇으로 바뀌었나?

H7은 permissions.deny의 Edit(...) 규칙으로 바뀌었다. H2는 세 층이 따로 갔다. 1층(되돌릴 수 없는 sf 명령, sf data create 포함)은 permissions.ask, 3층 중 토큰을 출력하는 sf org display와 sf org open --url-only는 permissions.deny다. 2층(개인정보 필드·FIELDS(ALL))은 명령 패턴으로 막을 수 없어 milvus-design.md의 규칙 문장으로 둔다(강제력 없음). Edit 규칙은 파일을 고치는 모든 내장 도구에 적용되고, Bash의 ask 규칙은 auto 모드에서도 묻는다. H8(세션 시작 안내)은 두지 않는다. (2026-10-09 갱신)

Q7. PostToolUse hook이 경고를 stderr에 쓰고 0으로 끝나면 Claude는 그 경고를 보나? 밀버스 hook은 milvusOverride.css 경고를 어떻게 전하나?

보지 못한다. 공식 문서에 따르면 0으로 끝난 hook의 stderr는 Claude가 보지 못하고 디버그 로그로만 확인할 수 있다. PostToolUse에서 Claude에게 stderr를 보여 주는 것은 종료 코드 2다. 그러나 override 경고는 막을 일이 아니라 0으로 끝내야 한다. 그래서 밀버스 hook은 경고가 있으면 stdout에 {"hookSpecificOutput":{"hookEventName":"PostToolUse","additionalContext":"…"}}를 쓴다(설계 7.2). Claude Code가 이 문자열을 system reminder로 도구 결과 옆에 넣는다. 고칠 값이 있을 때는 2로 끝나고 stderr를 넘긴다 (2026-10-12 추가).

Q8. pnpm milvus init이 아무 파일도 쓰지 않고 1로 끝났다. 무엇을 먼저 보나?

오류 문장을 읽고 사전 점검 순서대로 본다. 옵션(--target-org, --brand와 --from-org 중 하나, 브랜드 이름 규칙), Node 버전(22.18 이상, 23.x는 23.6 이상), sfdx-project.json과 기본 패키지 폴더 force-app, .claude/settings.json의 JSON 문법, milvus.config.json 버전과 설치된 패키지 버전(다르면 update), sf 설치와 org 로그인, --from-org라면 활성 테마가 SLDS 2 커스텀 테마인지. 점검이 하나라도 실패하면 아무것도 쓰지 않으므로 고친 뒤 다시 실행하면 된다 (2026-10-12 추가).

Q9. 명세 페이지에 "버튼을 각지게"라고 저장하고 Claude에게 "브랜드 요청 반영해줘"라고 했다. Claude가 곧바로 milvusBrand.css를 고치지 않고 표만 보여 준다. 잘못된 동작인가? (2026-10-13 추가)

아니다. milvus-brand skill은 파일을 고치기 전에 브랜드 명세 표(적용 값, 쓰는 곳, 출처, 확정/추정, 못 하는 요구와 대안)를 내고 승인을 받으라고 지시한다. "각지게"는 global hook --slds-g-radius-border-*로 풀리는 요구라 2번 수단을 쓴다. 승인하면 Claude가 파일을 쓰고, hook이 check --style로 검사하고, 끝에 요청 파일에 반영: 줄을 적는다.

Q10. "반영한 거 바로 org에 올려 줘"라고 했다. 몇 번 확인을 거치나? (2026-10-13 추가)

두 번이다. Claude가 먼저 --yes 없는 pnpm milvus deploy로 계획(대상 org, 활성 테마 변화, 배포 목록, org 전체에 적용된다는 경고)을 보여 주고 채팅 승인을 받는다. 그다음 pnpm milvus deploy --yes를 실행할 때 permissions.ask가 한 번 더 묻는다. 배포 자체도 두 단계라서, 메타데이터 배포가 실패하면 활성 테마를 바꾸지 않는다.

Q11. 요청 파일 맨 위의 반영: 2026-10-14 줄이 사라졌다. 누가 지웠고 무슨 뜻인가? (2026-10-13 추가)
