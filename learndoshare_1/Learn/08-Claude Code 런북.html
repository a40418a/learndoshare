Claude Code 런북

밀버스 디자인 시스템을 각 프로젝트의 Claude Code가 "런북"처럼 따라 쓰게 만드는 방법을 정리한다. CLAUDE.md, skill, plugin, hook, permissions의 차이와 과잉 구현을 줄이는 Ponytail 플러그인을 함께 다룬다.

예상 1시간선행: 03 Storybook · 05 테마 동기화 · 07 pnpm2026-10-09 code.claude.com 공식 문서로 다시 확인

왜 알아야 하나

밀버스는 사람이 읽는 문서만으로 끝나지 않는다. 새 프로젝트를 시작하는 사람은 Claude Code에게 "이 브랜드로 바꿔 줘"라고 말할 것이고, 그때 Claude가 우리 규칙대로 움직여야 한다. 규칙을 모르면 Claude는 lightning-button 내부 스타일을 덮어쓰거나 컴포넌트에 hex 색을 박아 넣을 수 있다.

① pnpm milvus init밀버스 파일과 .claude 묶음을 프로젝트에 설치
→
② 브랜드 요청Storybook 브랜드 명세 페이지나 채팅으로 입력
→
③ 반영Claude가 milvus-brand skill로 명세 표 제안 → 승인 → 파일 작성 → check
→
④ pnpm milvus deploy배포 계획 확인 → 채팅 승인 → org에 적용

이 네 단계를 Claude가 순서대로, 금지 사항을 지키며 수행하게 만드는 문서 묶음을 이 문서에서는 런북이라고 부른다. 위 흐름은 패키지·CLI 설계의 계획이고 아직 구현 전이다(설계 0장).

기본 우선 (2026-10-09 갱신)기본 상태는 Salesforce 기본 모양에 브랜드 색·로고만 바꾼 것이다. 색·로고는 공식 기능인 BrandingSet 메타데이터로 배포한다. init 직후 util.css(milvusBrand.css)는 비어 있고, 브랜드 요청이 있을 때만 모양을 바꾼다(설계 1장, 10/9 결정). 이전의 4단계 흐름은 런북 설계의 "이전 설계"에 있다.

읽히는 규칙

  • 작업 디렉터리와 그 위의 모든 디렉터리의 CLAUDE.md, CLAUDE.local.md를 시작할 때 읽는다. 서로 덮어쓰지 않고 이어 붙인다 (위에서 아래 순서)
  • 작업 디렉터리 아래 하위 폴더의 CLAUDE.md는 시작할 때 읽지 않고, Claude가 그 폴더의 파일을 읽거나 고칠 때 포함된다
  • 파일당 200줄 이하를 목표로 한다. 길수록 컨텍스트를 먹고 잘 안 지켜진다
  • 로드됐는지는 세션에서 /context의 Memory files 목록으로 확인한다. /init은 코드베이스를 분석해 초안을 만들어 준다

@path import

브랜드 작업 규칙은 @docs/brand-rules.md 를 따른다.
명령 목록: @package.json
  • 상대 경로는 import하는 파일 기준으로 해석한다 (작업 디렉터리 기준이 아니다). 절대 경로도 된다
  • import한 파일이 다시 import할 수 있고, 최대 4단계까지다
  • 백틱(`@README`)이나 코드 블록 안의 @는 import하지 않는다
  • 작업 디렉터리 밖을 가리키는 import는 처음 한 번 승인 대화상자가 뜬다. 거절하면 계속 비활성화된다
  • import한 파일도 시작할 때 전부 컨텍스트에 들어간다. 나눠 두는 건 정리용이지 절약용이 아니다

plugin과 marketplace

plugin은 skill, agent, hook, MCP 서버를 한 단위로 설치하는 디렉터리다. marketplace는 plugin 목록과 받을 위치를 적은 .claude-plugin/marketplace.json이 있는 저장소(또는 디렉터리)다. 호스팅되는 스토어가 아니라 카탈로그 파일이다.

my-plugin/
├── .claude-plugin/
│   └── plugin.json        ← 매니페스트. 선택이지만 쓰면 name만 필수
├── skills/
│   └── review/SKILL.md    ← /my-plugin:review
├── agents/
├── hooks/hooks.json
└── .mcp.json
{
  "name": "my-marketplace",
  "owner": { "name": "Your Name" },
  "plugins": [
    { "name": "my-first-plugin", "source": "./plugins/my-first-plugin", "description": "..." }
  ]
}
  • marketplace.json에는 name, owner, plugins가 필요하다. 각 plugin 항목에는 설치할 때 쓰는 name과 받을 위치 source를 적는다
  • 상대 경로 source는 .claude-plugin/이 든 marketplace 루트 기준이다. ..은 쓸 수 없다
  • 항목의 name과 plugin의 plugin.json name을 같게 둔다. 다르면 설치가 실패하기 쉽다
  • 셸에서 claude plugin validate ./my-marketplace로 검증한다

설치 명령 (세션 안)

/plugin marketplace add owner/repo           # GitHub 저장소. #v1.2.0 처럼 ref 고정 가능
/plugin install plugin-name@marketplace-name # 상세 패널이 열리고 설치 범위를 고른다
/plugin                                      # Discover / Installed / Marketplaces 탭
/plugin uninstall                            # 패널에서 제거
/plugin marketplace remove <name>            # marketplace와 거기서 설치한 plugin 제거
설치 범위기록되는 곳의미
user~/.claude/settings.json이 컴퓨터의 내 모든 프로젝트
project.claude/settings.json (커밋)저장소 협업자 모두에게 켜짐. 단, 각자 한 번 설치는 해야 한다
local.claude/settings.local.json나만, 이 저장소에서만

데스크톱 앱 Code 탭에서는 입력창 옆 + → Plugins → Add plugin으로 같은 일을 한다. 클라우드 세션(claude.ai/code)은 로컬에 설치한 plugin을 읽지 않는다.

plugin은 내 권한으로 코드를 실행한다hook과 MCP 서버는 설치한 사람의 권한으로 돈다. 출처가 공식 marketplace가 아니면 설치 전에 상세 패널의 Will install 목록과 저장소를 확인한다.

hook과 permissions: 반드시 막아야 할 때

hook은 Claude Code가 특정 시점(도구 실행 전후, 세션 시작 등)에 실행하는 셸 명령이다. LLM이 "지키기로 선택"하는 것이 아니라 항상 실행된다. PreToolUse hook 스크립트가 exit code 2로 끝나면 그 도구 호출이 막히고, stderr 메시지가 Claude에게 피드백으로 간다.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

PROTECTED_PATTERNS=(".sfdx/" ".env" "pnpm-lock.yaml")   # 예시 목록
for pattern in "${PROTECTED_PATTERNS[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH 는 밀버스 런북에서 수정 금지" >&2
    exit 2
  fi
done
exit 0

스크립트는 실행 권한(chmod +x)이 있어야 하고 jq가 필요하다. 세션에서 /hooks로 등록된 hook을 확인한다.

permissions: 스크립트 없이 막거나 묻기

settings의 permissions에 규칙을 적으면 스크립트 없이 도구 호출을 막거나(deny) 실행 전에 묻게(ask) 할 수 있다.

  • 규칙은 deny → ask → allow 순서로 보고, 처음 맞는 것이 결과를 정한다. 넓은 deny는 좁은 allow로 뚫리지 않는다
  • Edit(...) 규칙은 파일을 고치는 모든 내장 도구에 적용된다
  • 경로가 / 하나로 시작하면 설정 파일 기준이다. 프로젝트 설정에서는 프로젝트(주 작업 디렉터리) 기준이다. 파일 시스템 절대 경로는 //로 쓴다
  • Bash(pnpm milvus deploy *)처럼 끝의 * 앞에 공백이 있으면 인자 없는 pnpm milvus deploy에도 맞는다
  • Bash의 ask 규칙은 auto 모드에서도 묻는다
  • PreToolUse hook이 허용을 돌려줘도 deny·ask 규칙은 그대로 적용된다. 반대로 exit 2로 막는 hook은 allow 규칙보다 먼저 막는다

밀버스 런북 설계 계획

2026-10-09 갱신. 아래 파일은 아직 없다. pnpm milvus init이 프로젝트에 만들 계획이다(설계 3장·7장). 이 절은 Claude Code와 관련된 파일만 다룬다.

파일구분내용
milvus-design.md관리세팅 안내서이자 Claude 규칙. 200줄 이하. 준비물, 세팅 순서, 파일 지도, 디자인 규칙, 배포 안전장치
CLAUDE.md소유@milvus-design.md 한 줄을 더한다. 파일이 없으면 이 한 줄로 만든다
.claude/skills/milvus-brand/SKILL.md관리브랜드 요청 → 브랜드 명세 표 제안 → 승인 → BrandingSet·milvusBrand.css 작성 → pnpm milvus check
.claude/hooks/milvus-check.mjs관리util.css나 브랜드 메타데이터를 고친 뒤 pnpm milvus check --style
.claude/settings.json소유아래 permissions와 hook을 기존 설정에 병합

관리 파일은 밀버스가 관리한다. 프로젝트에서 직접 고치지 않고 pnpm milvus update가 갱신한다. 소유 파일은 프로젝트가 고친다.

milvus-design.md는 프로젝트 루트에 있으므로 Claude Code를 프로젝트 루트에서 실행하면 작업 디렉터리 밖 import 승인 대화상자가 뜨지 않는다.

settings.json에 병합할 내용 요약

{
  "permissions": {
    "ask": ["Bash(pnpm milvus deploy *)", "Bash(sf project deploy *)", "Bash(sf data delete *)", "Bash(sf apex run *)"],
    "deny": ["Edit(/force-app/main/default/lwc/milvus*/**)", "Edit(/milvus-design.md)", "Edit(/.claude/skills/milvus-brand/**)"]
  },
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write", "hooks": [{ "type": "command", "command": "node \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/milvus-check.mjs" }] }
    ]
  }
}

실제 목록은 더 길다. 전체는 설계 7.2에 있다.

바뀐 hook 계획 (2026-10-09 갱신)

패키지 설계는 README 11장의 hook 계획 일부를 permissions로 바꾸었다(설계 문서 맨 앞 "이 문서가 대체하는 것" 표, 7.2). 이 hook들은 아직 구현되지 않았다. 저장소에 .claude/ 설정이 없고, README 4장 Phase 1의 hook 항목도 끝나지 않았다. 구현 첫 PR에서 CLAUDE.md 2장과 README 11장을 이 표에 맞게 고친다.

막으려던 것 (이전 hook)패키지 설계

Ponytail

DietrichGebert/ponytail은 AI 에이전트에게 "게으른 시니어 개발자" 규칙을 넣어 과잉 구현을 줄이는 플러그인이다. MIT 라이선스다. 2026-10-08에 v5.0.0이 나오면서 규칙, review, audit가 새로 쓰였고, 같은 날 v5.1.0에서 지름길 주석 표시가 바뀌었다(아래 /ponytail-debt). 아래 내용은 2026-10-09의 README와 INSTALL.md 기준이다(2026-10-09 갱신). 설치한 버전은 셸에서 claude plugin list로 확인한다.

코드를 쓰기 전의 사다리

처음으로 "예"가 나오는 칸에서 멈춘다.

3표준 라이브러리가 하나?그걸 쓴다

  • 사다리는 문제를 이해한 뒤에 적용한다. 바뀔 코드를 먼저 읽고 실제 흐름을 따라간다. 해법에 게으르되 읽기에는 게으르지 않다
  • 신뢰 경계의 검증, 데이터 손실 처리, 보안, 접근성은 절대 줄이지 않는다

설치 (Claude Code)

README는 두 명령을 각각 별도의 프롬프트로 보내라고 안내한다.

/plugin marketplace add DietrichGebert/ponytail

  • 데스크톱 앱 Code 탭에서는 같은 명령을 입력하거나 + → Plugins → Add plugin

제거

INSTALL.md는 /plugin remove ponytail을 안내하고, Claude Code 공식 문서의 제거 명령은 /plugin uninstall(또는 /plugin → Installed 탭 → Uninstall)이다. INSTALL.md에 따르면 plugin 폴더 밖에 남는 상태(모드 플래그, 설정 파일, statusLine 항목)는 plugin을 지우기 전에 node scripts/uninstall.js로 정리한다.

스스로 점검

Q1. "밀버스 디자인 규칙"과 "브랜드 요청 반영 절차"는 각각 CLAUDE.md와 skill 중 어디에 두나?

규칙은 항상 지켜야 하므로 CLAUDE.md 쪽이다. 밀버스는 CLAUDE.md에 @milvus-design.md 한 줄을 넣어 불러온다. 절차는 해당 작업 때만 필요하므로 skill(milvus-brand)이다. CLAUDE.md와 import한 파일은 매 세션 컨텍스트를 차지하므로 짧게 유지한다.

Q2. CLAUDE.md에 "이 파일은 고치지 마라"라고 썼는데도 확실히 막고 싶다. 어떻게 하나?

CLAUDE.md는 컨텍스트일 뿐 강제력이 없다. permissions.deny에 Edit(...) 규칙을 넣거나, PreToolUse hook 스크립트가 해당 경로면 exit code 2로 끝나게 해서 도구 호출을 막는다.

Q3. learndoshare/(git 루트)에서 Claude Code를 켰더니 밀버스 규칙을 모르는 것 같다. 왜?

learndoshare_1/CLAUDE.md는 작업 디렉터리 아래 하위 폴더라 시작할 때 읽히지 않고, 그 폴더의 파일을 다룰 때에야 포함된다. learndoshare_1/에서 실행한다.

Q4. Ponytail 설치 명령 두 줄을 한 프롬프트에 붙여 넣으면?

README는 두 명령을 별도의 프롬프트로 보내라고 안내한다. /plugin marketplace add DietrichGebert/ponytail을 먼저 보내고, 다음 프롬프트로 /plugin install ponytail@ponytail을 보낸다.

Q5. 사용자가 "다중 선택 컴포넌트 만들어 줘"라고 했다. Ponytail 사다리와 밀버스 원칙으로 첫 행동은?

새로 만들기 전에 4번 칸(플랫폼 기본 기능)을 확인한다. lightning-dual-listbox나 lightning-select의 multiple로 되는지 보고, 안 될 때만 milvusMultiSelect를 만든다. 만들더라도 접근성과 입력 검증은 줄이지 않는다.

Q6. README 11장의 H7(관리 파일 수정 차단 hook)과 H2(sf 명령 차단 hook, 3층)는 패키지 설계에서 무엇으로 바뀌었나?

H7은 permissions.deny의 Edit(...) 규칙으로 바뀌었다. H2는 세 층이 따로 갔다. 1층(되돌릴 수 없는 sf 명령, sf data create 포함)은 permissions.ask, 3층 중 토큰을 출력하는 sf org display와 sf org open --url-only는 permissions.deny다. 2층(개인정보 필드·FIELDS(ALL))은 명령 패턴으로 막을 수 없어 milvus-design.md의 규칙 문장으로 둔다(강제력 없음). Edit 규칙은 파일을 고치는 모든 내장 도구에 적용되고, Bash의 ask 규칙은 auto 모드에서도 묻는다. H8(세션 시작 안내)은 두지 않는다. (2026-10-09 갱신)
