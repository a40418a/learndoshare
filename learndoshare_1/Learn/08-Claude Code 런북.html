Claude Code 런북

밀버스 디자인 시스템을 각 프로젝트의 Claude Code가 "런북"처럼 따라 쓰게 만드는 방법을 정리한다. CLAUDE.md, skill, plugin의 차이와 과잉 구현을 줄이는 Ponytail 플러그인을 함께 다룬다.

예상 1시간선행: 03 Storybook · 05 테마 동기화 · 07 pnpm2026-09-26 code.claude.com 공식 문서로 확인

왜 알아야 하나

밀버스는 사람이 읽는 문서만으로 끝나지 않는다. 새 프로젝트를 시작하는 사람은 Claude Code에게 "우리 브랜드로 Storybook 만들어 줘"라고 말할 것이고, 그때 Claude가 우리 규칙대로 움직여야 한다. 규칙을 모르는 Claude는 lightning-button 내부 스타일을 덮어쓰거나 컴포넌트에 hex 색을 박아 넣는다.

① org 테마관리자가 Setup에서 설정
→
② pnpm sync:theme색 + 로고를 brands/<브랜드>/로
→
③ 브랜드 요청Claude가 root.css의 허용 변수만 수정
→
④ 컴포넌트 선택create-project.mjs로 프로젝트 Storybook 생성

이 네 단계를 Claude가 순서대로, 금지 사항을 지키며 수행하게 만드는 문서 묶음을 이 문서에서는 런북이라고 부른다.

CLAUDE.md · skill · plugin

CLAUDE.mdskillplugin
한 줄 요약항상 읽는 프로젝트 지침필요할 때 불러오는 절차서skill · hook · agent · MCP 서버를 묶어 배포하는 단위
위치./CLAUDE.md 또는 ./.claude/CLAUDE.md.claude/skills/<이름>/SKILL.md플러그인 디렉터리 (.claude-plugin/plugin.json + skills/, hooks/ …)
언제 컨텍스트에 들어가나세션 시작 시 매번평소엔 이름과 description만. 호출될 때 본문 전체설치·활성화한 뒤 구성 요소별 규칙대로
호출자동Claude가 description을 보고 자동으로, 또는 사용자가 /이름플러그인 skill은 /플러그인:skill
강제력없음 (컨텍스트일 뿐)없음안에 든 hook은 강제 가능
밀버스에서원칙과 금지 목록4단계 워크플로 절차여러 프로젝트에 한 번에 배포 (로드맵)
"지시"와 "강제"는 다르다공식 문서는 CLAUDE.md를 "강제되는 설정이 아니라 컨텍스트"로 설명하고, Claude의 판단과 무관하게 동작을 막으려면 PreToolUse hook을 쓰라고 안내한다. 금지 목록 중 정말 치명적인 것(예: .sfdx 커밋)은 hook으로 한 번 더 막는다.

예전의 커스텀 slash command(.claude/commands/deploy.md)는 skill에 통합됐다. .claude/commands/deploy.md와 .claude/skills/deploy/SKILL.md는 둘 다 /deploy를 만들고 똑같이 동작한다. 기존 command 파일은 계속 동작하지만 새로 만들 때는 skill을 쓴다.

CLAUDE.md 자세히

종류위치공유 범위
프로젝트./CLAUDE.md 또는 ./.claude/CLAUDE.md저장소에 커밋해 팀과 공유
개인(프로젝트별)./CLAUDE.local.md나만. .gitignore에 추가
사용자~/.claude/CLAUDE.md나의 모든 프로젝트

읽히는 규칙

  • 작업 디렉터리와 그 위의 모든 디렉터리의 CLAUDE.md, CLAUDE.local.md를 시작할 때 읽는다. 서로 덮어쓰지 않고 이어 붙인다 (위에서 아래 순서)
  • 작업 디렉터리 아래 하위 폴더의 CLAUDE.md는 시작할 때 읽지 않고, Claude가 그 폴더의 파일을 읽을 때 포함된다
  • 파일당 200줄 이하를 목표로 한다. 길수록 컨텍스트를 먹고 잘 안 지켜진다
  • 로드됐는지는 세션에서 /context의 Memory files 목록으로 확인한다. /init은 코드베이스를 분석해 초안을 만들어 준다

@path import

브랜드 작업 규칙은 @docs/brand-rules.md 를 따른다.
명령 목록: @package.json
  • 상대 경로는 import하는 파일 기준으로 해석한다 (작업 디렉터리 기준이 아니다). 절대 경로도 된다
  • import한 파일이 다시 import할 수 있고, 최대 4단계까지다
  • 백틱(`@README`)이나 코드 블록 안의 @는 import하지 않는다
  • 작업 디렉터리 밖을 가리키는 import는 처음 한 번 승인 대화상자가 뜬다. 거절하면 계속 비활성화된다
  • import한 파일도 시작할 때 전부 컨텍스트에 들어간다. 나눠 두는 건 정리용이지 절약용이 아니다
우리 저장소 구조에서 주의git 루트는 learndoshare/이고 밀버스 프로젝트는 learndoshare_1/이다. Claude Code를 learndoshare/에서 실행하면 learndoshare_1/CLAUDE.md는 하위 폴더라서 시작할 때 읽히지 않는다. 런북 작업은 learndoshare_1/에서 실행한다.

skill 자세히

범위경로쓰이는 곳
개인~/.claude/skills/<이름>/SKILL.md내 모든 프로젝트
프로젝트.claude/skills/<이름>/SKILL.md이 저장소의 세션
하위 폴더<subdir>/.claude/skills/<이름>/SKILL.md<subdir> 안이나 그 아래에서 시작한 세션
플러그인<plugin>/skills/<이름>/SKILL.md플러그인이 켜진 곳. /플러그인:이름

SKILL.md 구조

---
name: example                      # / 메뉴에 보이는 이름. 생략하면 폴더 이름
description: 무엇을 하는지와 언제 쓰는지   # Claude가 자동 호출을 판단하는 근거
---

여기부터 Claude가 따를 절차를 Markdown으로 쓴다.
frontmatter의미
name, description이름과 설명. description이 자동 호출의 기준이라 가장 중요하다
disable-model-invocation: trueClaude가 스스로 부르지 못하게 함. 사용자가 /이름으로만 실행
user-invocable: false반대로 사용자 메뉴에서 숨기고 Claude만 사용
allowed-toolsskill 실행 중 권한 확인 없이 쓸 도구를 미리 허용
paths특정 파일 패턴을 다룰 때만 자동 로드
  • 호출된 skill 본문은 메시지 하나로 들어가 이후 턴에도 남는다. 파일을 매 턴 다시 읽지는 않는다
  • SKILL.md는 500줄 이하로 두고 긴 자료는 같은 폴더의 별도 파일로 뺀다
  • 본문에서 $ARGUMENTS로 인자를, ${CLAUDE_SKILL_DIR}로 skill 폴더 경로를 쓸 수 있다

plugin과 marketplace

plugin은 skill, agent, hook, MCP 서버를 한 단위로 설치하는 디렉터리다. marketplace는 plugin 목록과 받을 위치를 적은 .claude-plugin/marketplace.json이 있는 저장소(또는 디렉터리)다. 호스팅되는 스토어가 아니라 카탈로그 파일이다.

my-plugin/
├── .claude-plugin/
│   └── plugin.json        ← 매니페스트. 선택이지만 쓰면 name만 필수
├── skills/
│   └── review/SKILL.md    ← /my-plugin:review
├── agents/
├── hooks/hooks.json
└── .mcp.json
{
  "name": "my-marketplace",
  "owner": { "name": "Your Name" },
  "plugins": [
    { "name": "my-first-plugin", "source": "./plugins/my-first-plugin", "description": "..." }
  ]
}
  • marketplace.json에는 name, owner, plugins가 필요하고, 각 plugin 항목에는 name과 source가 필요하다
  • 상대 경로 source는 .claude-plugin/이 든 marketplace 루트 기준이다. ..은 쓸 수 없다
  • 항목의 name과 plugin의 plugin.json name을 같게 둔다. 다르면 설치 오류가 난다
  • 셸에서 claude plugin validate ./my-marketplace로 검증한다

설치 명령 (세션 안)

/plugin marketplace add owner/repo           # GitHub 저장소. #v1.2.0 처럼 ref 고정 가능
/plugin install plugin-name@marketplace-name # 상세 패널이 열리고 설치 범위를 고른다
/plugin                                      # Discover / Installed / Marketplaces 탭
/plugin uninstall                            # 패널에서 제거
/plugin marketplace remove <name>            # marketplace와 거기서 설치한 plugin 제거
설치 범위기록되는 곳의미
user~/.claude/settings.json이 컴퓨터의 내 모든 프로젝트
project.claude/settings.json (커밋)저장소 협업자 모두에게 켜짐. 단, 각자 한 번 설치는 해야 한다
local.claude/settings.local.json나만, 이 저장소에서만

데스크톱 앱 Code 탭에서는 입력창 옆 + → Plugins → Add plugin으로 같은 일을 한다. 클라우드 세션(claude.ai/code)은 로컬에 설치한 plugin을 읽지 않는다.

plugin은 내 권한으로 코드를 실행한다hook과 MCP 서버는 설치한 사람의 권한으로 돈다. 출처가 공식 marketplace가 아니면 설치 전에 상세 패널의 Will install 목록과 저장소를 확인한다.

hook: 반드시 막아야 할 때

hook은 Claude Code가 특정 시점(도구 실행 전후, 세션 시작 등)에 실행하는 셸 명령이다. LLM이 "지키기로 선택"하는 것이 아니라 항상 실행된다. PreToolUse hook 스크립트가 exit code 2로 끝나면 그 도구 호출이 막히고, stderr 메시지가 Claude에게 피드백으로 간다.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
#!/bin/bash
INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')

PROTECTED_PATTERNS=(".sfdx/" ".env" "pnpm-lock.yaml")   # 예시 목록
for pattern in "${PROTECTED_PATTERNS[@]}"; do
  if [[ "$FILE_PATH" == *"$pattern"* ]]; then
    echo "Blocked: $FILE_PATH 는 밀버스 런북에서 수정 금지" >&2
    exit 2
  fi
done
exit 0

스크립트는 실행 권한(chmod +x)이 있어야 하고 jq가 필요하다. 세션에서 /hooks로 등록된 hook을 확인한다.

밀버스 런북 설계 계획

현재 저장소에는 아래 파일이 아직 없다. 이 절은 무엇을 어디에 둘지에 대한 설계안이다.

파일내용
learndoshare_1/CLAUDE.md원칙과 금지 목록 (짧게, 200줄 이하)
learndoshare_1/.claude/skills/milvus-init/SKILL.md새 프로젝트 4단계 절차와 정확한 명령
learndoshare_1/.claude/settings.json + .claude/hooks/치명적 금지 사항만 hook으로 강제

CLAUDE.md 예시

# 밀버스 디자인 시스템

## 원칙
- 색은 org에서 온다. 브랜드 색은 Setup의 Themes and Branding → `pnpm sync:theme`으로만 들어온다
- SLDS와 lightning-* 기본 컴포넌트를 먼저 쓴다. 없을 때만 milvus 컴포넌트를 만든다
- 패키지 매니저는 pnpm만. npm / npx / yarn 금지 (npx 예제는 pnpm exec / pnpm dlx로 바꾼다)

## 금지
- `--slds-g-*` 재정의 금지 (읽기만)
- `--slds-c-*` (컴포넌트 styling hook) 사용 금지
- 컴포넌트 CSS/JS에 hex 색 직접 쓰기 금지. 변수만 쓴다
- `.sfdx/` 커밋 금지
- `sf` 배포 명령은 실행 전에 반드시 사용자에게 묻는다
- 이 저장소는 공개 저장소다. org ID, 사용자명, 토큰을 파일에 쓰지 않는다

## 절차
새 프로젝트/브랜드 작업은 milvus-init skill을 따른다.

SKILL.md 예시

---
name: milvus-init
description: 밀버스 디자인 시스템으로 새 프로젝트를 시작하거나 브랜드 스타일을 바꿀 때 사용한다. org 테마 동기화, brands/<브랜드>/root.css 수정, 프로젝트별 Storybook 생성 절차.
---

# 밀버스 새 프로젝트 절차

## 1. org 테마 확인
사용자에게 Setup > Themes and Branding에서 테마를 설정했는지 묻는다.
org 설정은 Claude가 바꾸지 않는다.

## 2. 색과 로고 가져오기
    pnpm sync:theme
결과: brands/<브랜드>/theme.json (L1), brands/<브랜드>/logo.png (L2).
이 두 파일은 손으로 고치지 않는다. 다시 가져오려면 명령을 다시 실행한다.

## 3. 브랜드 요청 반영 (L3)
- 수정 가능한 파일은 brands/<브랜드>/root.css 하나뿐이다
- 허용 목록에 있는 --milvus-* 변수만 선언/수정한다 (허용 목록: brands/ALLOWLIST.md)
- --slds-g-* 는 값으로 참조만 한다: --milvus-x: var(--slds-g-...);
- --slds-c-* 는 쓰지 않는다
- 허용 목록에 없는 요청은 수정하지 말고 이유를 설명한다
- 수정 후 Storybook 툴바에서 해당 브랜드로 확인하라고 안내한다

## 4. 프로젝트 Storybook 생성
사용자에게 필요한 컴포넌트를 묻고 실행한다:
    node scripts/create-project.mjs --brand <브랜드> --components badge,button --out <경로>

## 거절하고 대안을 제시할 요청
- "lightning-button을 둥글게" → 먼저 org 테마나 lightning-button의 기존 옵션으로 되는지 확인하고,
  그래도 필요하면 milvusButton(--milvus-button-*)을 제안한다.
  사용자가 lightning-button 자체를 원하면 opt-in override.css의 위험
  (SLDS 공식 권고 밖, Salesforce 릴리스마다 재확인)을 설명하고 확인을 받은 뒤에만 켠다.
  override.css에서도 색(accent 계열)은 재정의하지 않는다
- 컴포넌트에 색을 hex로 넣어 달라는 요청 → root.css의 변수로 안내한다
- sf 배포 → 실행 전에 대상 org와 명령을 보여 주고 승인을 받는다
  • brands/ALLOWLIST.md, 허용 변수 목록, create-project.mjs의 인자 이름은 모두 예시다. 스크립트를 만들 때 확정한다
  • package.json에 "create:project": "node scripts/create-project.mjs"를 등록하면 pnpm create:project --brand X --components badge,button --out <경로>로도 실행할 수 있다 (스크립트 이름 뒤 인자는 스크립트로 전달된다)
  • description에 "언제 쓰는지"를 구체적으로 적어야 Claude가 자동으로 불러온다. 자동 호출이 불안하면 사용자가 /milvus-init으로 직접 실행하게 안내한다

Ponytail

DietrichGebert/ponytail은 AI 에이전트에게 "게으른 시니어 개발자" 규칙을 넣어 과잉 구현을 줄이는 플러그인이다. MIT 라이선스, 2026-09-14 v4.10.0 릴리스, GitHub 별 14만 개 이상으로 널리 쓰인다. 아래 내용은 저장소 README 기준이다.

코드를 쓰기 전의 사다리

처음으로 "예"가 나오는 칸에서 멈춘다.

#질문예라면
1이게 꼭 있어야 하나?만들지 않는다 (YAGNI)
2이 코드베이스에 이미 있나?재사용한다
3표준 라이브러리가 하나?그걸 쓴다
4플랫폼 기본 기능이 있나?그걸 쓴다
5이미 설치된 의존성이 하나?그걸 쓴다
6한 줄로 되나?한 줄로
7그제서야동작하는 최소한
  • 사다리는 문제를 이해한 뒤에 적용한다. 바뀔 코드를 먼저 읽고 실제 흐름을 따라간다. 해법에 게으르되 읽기에는 게으르지 않다
  • 신뢰 경계의 검증, 데이터 손실 처리, 보안, 접근성은 절대 줄이지 않는다

설치 (Claude Code)

두 명령을 각각 별도의 프롬프트로 보내야 한다.

/plugin marketplace add DietrichGebert/ponytail
/plugin install ponytail@ponytail
  • 데스크톱 앱 Code 탭에서는 같은 명령을 입력하거나 + → Plugins → Add plugin
  • lifecycle hook 두 개가 Node.js로 돌기 때문에 node가 PATH에 있어야 한다 (nvm 사용자는 비대화형 셸의 PATH 기준)
  • 세션 안의 /plugin install은 바로 설치하지 않고 상세 패널을 연다. 여기서 범위(user / project / local)를 고른다. 개인이 먼저 써 보는 단계면 user 범위가 무난하다

모드와 명령

명령하는 일
/ponytail lite|full|ultra|off강도 변경. 인자 없으면 현재 단계 표시. 기본 full
/ponytail-review현재 diff의 과잉 구현을 검토해 삭제 목록을 준다
/ponytail-auditdiff가 아니라 저장소 전체를 검사
/ponytail-debt미뤄 둔 ponytail: 주석을 목록으로 모은다
/ponytail-gain벤치마크 기반 효과 표시
/ponytail-help명령 요약
  • 기본 단계는 환경 변수 PONYTAIL_DEFAULT_MODE 또는 ~/.config/ponytail/config.json의 defaultMode로 바꾼다
  • 켜져 있으면 Agent 도구로 띄운 subagent에도 규칙이 들어간다. PONYTAIL_SUBAGENT_MATCHER(정규식)로 대상 agent 유형을 좁힌다
  • 공식 문서상 plugin skill은 /<plugin>:<skill> 형태이고, 다른 명령과 겹치지 않으면 skill 이름만으로도 호출된다. 미확인 Claude Code에서 실제로 /ponytail:ponytail-review처럼 보이는지는 설치해서 확인한다

제거

README는 /plugin remove ponytail을 안내하고, Claude Code 공식 문서의 제거 명령은 /plugin uninstall(또는 /plugin → Installed 탭 → Uninstall)이다. README에 따르면 plugin 폴더 밖에 남는 상태(모드 플래그, 설정 파일, statusLine 항목)는 plugin을 지우기 전에 저장소의 node scripts/uninstall.js로 정리한다.

숫자는 어떻게 읽나

제작자 자체 측정이다README의 agentic 벤치마크(Haiku 4.5, 과제 12개, n=4)는 기준 대비 코드 약 54% 감소, 비용 약 20% 감소, 시간 약 27% 감소를 보고한다. 예전의 80~94% 수치는 단발 생성에서 과제별 최대치였지 평균이 아니다. 모델과 과제에 따라 결과가 다르고, 생각 토큰을 많이 쓰는 추론 모델에서는 비용이 오히려 늘 수 있다고 README 스스로 적고 있다.

밀버스 원칙과 겹치는 지점

사다리 4번 "플랫폼 기본 기능"이 밀버스의 "SLDS와 lightning-* 먼저" 원칙과 같다.

요청먼저 확인할 것 (4번 칸)그다음
다중 선택이 필요하다lightning-dual-listbox, lightning-select의 multiple그래도 안 되면 milvusMultiSelect
버튼 모양을 바꾸고 싶다org 테마, lightning-button의 기존 옵션그래도 안 되면 milvusButton
브랜드 색을 바꾸고 싶다org Setup → pnpm sync:theme컴포넌트 코드는 건드리지 않는다
"코드가 적다"가 목표가 아니다Ponytail이 줄인 코드는 테스트(sfdx-lwc-jest, Storybook 인터랙션 테스트, a11y 검사)로 확인한다. 입력 검증, 오류 처리, 접근성 속성이 빠졌다면 되돌린다. PR 전에 /ponytail-review로 과잉 구현을, 사람 리뷰로 빠진 것을 확인한다.

우리 프로젝트 적용

10/23 데모까지 할 일
  1. learndoshare_1/CLAUDE.md에 원칙과 금지 목록을 200줄 이하로 쓴다 (공개 저장소이므로 org 정보 제외)
  2. .claude/skills/milvus-init/SKILL.md에 4단계 절차와 정확한 명령(pnpm sync:theme, root.css 규칙, node scripts/create-project.mjs ...)을 쓴다
  3. --milvus-* 허용 목록 파일을 만들고 skill에서 참조한다
  4. .sfdx/ 같은 치명적 금지만 PreToolUse hook으로 막는다
  5. create-project.mjs가 생성 프로젝트에 CLAUDE.md와 skill을 복사하게 한다 (배포 형태 (b))
  6. Claude Code는 learndoshare_1/에서 실행해 CLAUDE.md와 skill이 로드되는지 /context로 확인한다
  7. Ponytail은 개인 user 범위로 먼저 써 보고, 팀 적용(project 범위)은 데모 후 결정한다

plugin 배포 (a)는 데모 이후 로드맵이다. 그때 skill 이름이 /milvus:milvus-init으로 바뀐다는 점을 문서에 반영한다.

스스로 점검

Q1. "색상 원칙"과 "새 프로젝트 4단계 절차"는 각각 CLAUDE.md와 skill 중 어디에 두나?

원칙은 항상 지켜야 하므로 CLAUDE.md, 절차는 해당 작업 때만 필요하므로 skill(milvus-init). CLAUDE.md는 매 세션 컨텍스트를 차지하므로 짧게 유지한다.

Q2. CLAUDE.md에 ".sfdx는 커밋 금지"라고 썼는데도 확실히 막고 싶다. 어떻게 하나?

CLAUDE.md는 컨텍스트일 뿐 강제력이 없다. PreToolUse hook 스크립트가 해당 경로면 exit code 2로 끝나게 해서 도구 호출을 막는다.

Q3. learndoshare/(git 루트)에서 Claude Code를 켰더니 밀버스 규칙을 모르는 것 같다. 왜?

learndoshare_1/CLAUDE.md는 작업 디렉터리 아래 하위 폴더라 시작할 때 읽히지 않고, 그 폴더의 파일을 읽을 때에야 포함된다. learndoshare_1/에서 실행한다.

Q4. Ponytail 설치 명령 두 줄을 한 프롬프트에 붙여 넣으면?

README는 두 명령을 별도의 프롬프트로 보내야 설치가 된다고 안내한다. /plugin marketplace add DietrichGebert/ponytail을 먼저 보내고, 다음 프롬프트로 /plugin install ponytail@ponytail을 보낸다.

Q5. 사용자가 "다중 선택 컴포넌트 만들어 줘"라고 했다. Ponytail 사다리와 밀버스 원칙으로 첫 행동은?

새로 만들기 전에 4번 칸(플랫폼 기본 기능)을 확인한다. lightning-dual-listbox나 lightning-select의 multiple로 되는지 보고, 안 될 때만 milvusMultiSelect를 만든다. 만들더라도 접근성과 입력 검증은 줄이지 않는다.
