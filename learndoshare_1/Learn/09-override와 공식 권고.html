LEARN 09 · override

override와 공식 권고

기존 컴포넌트의 모양을 바꿀 때 새 컴포넌트를 만들지, 기존 컴포넌트의 CSS를 덮어쓸지 정리한다. Salesforce가 덮어쓰기를 권하지 않는 이유를 공식 자료로 확인하고, 세 가지 실험으로 직접 비교한다. 발표에서 "두 방식을 다 해 봤고, 이래서 공식적으로는 권하지 않는다"를 설명하는 것이 목표다.

예상 1시간선행: 00 개념 · 01 SLDS2026-10-09 공식 문서 · 설치된 패키지 · 실측 기록으로 확인
표시 규칙미확인은 공식 문서나 실측으로 확인하지 못한 것이다. 추정은 공식 문서가 밝히지 않아 우리가 해석한 것이다. 계획은 설계만 있고 아직 구현하지 않은 것이다. 이 문서의 공식 자료 조사는 2026-10-09 조사 기록에 원문 위치와 함께 있다.

1. 질문: 새로 만들까, 덮어쓸까

개념

기존 컴포넌트의 모양을 바꾸는 길은 둘이다. 하나는 같은 기능의 컴포넌트를 새로 만들어 원하는 모양으로 그리는 것이다. 다른 하나는 기존 컴포넌트를 그대로 쓰고, 그 컴포넌트에 걸린 CSS를 바깥에서 덮어쓰는 것(override)이다. 둘 다 디자인 시스템이 정한 모양에서 벗어나는 일이라, 드는 비용과 깨질 위험을 비교해서 고른다.

Salesforce에서는

  • 권장 순서: base 컴포넌트(lightning-*)의 속성 → 맞는 base 컴포넌트가 없을 때 블루프린트 → hook을 읽는 커스텀 컴포넌트. SLDS 2 사이트는 블루프린트를 "가능하면 피한다"고 표시하고, base 컴포넌트의 커스터마이즈는 제한적이라고 적는다
  • 덮어쓰기: LWC 개발자 가이드는 base 컴포넌트의 스타일 override를 문서화된 styling hook을 쓸 때만 지원한다고 적는다. SLDS 클래스를 덮어쓰거나 렌더된 내부 마크업을 겨냥한 스타일은 지원하지 않는다. 가이드의 안티패턴 예시가 바로 .slds-button { padding: 16px; } 같은 규칙이다
  • 새로 만들기: 블루프린트는 모양만 있는 HTML·CSS 틀이라 동작과 로직이 없고, 플랫폼의 최신 개선과 보호를 받지 못한다. 그래서 base 컴포넌트가 해 주던 동작과 접근성을 직접 맞춰야 한다

2. SLDS 1과 SLDS 2의 커스터마이즈 범위

개념

커스터마이즈 범위는 "누가, 어디서, 무엇을 바꿀 수 있는가"다. 같은 CSS라도 공식 지원(업그레이드 뒤에도 Salesforce가 동작을 책임진다)과 실제로 동작함(지금 화면에서 바뀐다)은 다르다. 이 둘을 섞으면 "공식 문서는 안 된다는데 우리 org에서는 된다"는 혼란이 생긴다.

Salesforce에서는

항목SLDS 1SLDS 2 (2026-10-09)변화

디자인 토큰 --lwc-*동작설정을 지원하지 않고, 다시 할당한 값은 무시된다줄어듦
.slds-* 클래스 덮어쓰기지원하지 않음(실제로는 동작)지원하지 않음. 실제로 닿는지는 shadow 모드가 정한다(5절)지원 범위는 같다. 깨질 위험이 커졌다

관리자 테마 새 기능—브랜드 색에서 WCAG 대비를 맞춘 accent 자동 생성, advanced accent(재정의는 강하게 비권장), 다크 모드(Winter '27 GA, 2026-09부터), 다크 모드용 로고늘어남
hook 값의 성격고정값 중심hook마다 라이트·다크 값이 있고, 밀도에 따라 바뀌는 간격 hook이 있다. 릴리스에서 이름이 폐기되기도 한다(Winter '26: --slds-g-font-family → --slds-g-font-family-base 등)값이 동적이 됨

정리하면 컴포넌트 하나를 CSS로 고치던 자유는 줄었고, 테마로 시스템 전체를 바꾸는 자유는 늘었다. 공식 자료는 "줄였다"고 쓰지 않는다. Winter '26 GA 릴리스 노트는 SLDS 2가 구조와 시각 스타일을 분리해 더 깊은 커스터마이즈와 테마를 준다고 쓴다.

"SLDS 2에서는 무시된다"는 무엇을 말하나 (2026-10-09 원문 확인)
  • 공식 문장: SLDS 1 Best Practices의 "Update Styling Hooks" 절, --slds-* 소절 "Replace a Styling Hook as a Value for a Selector that You Don't Own"은 세 문장이다. 컴포넌트에 대한 직접 CSS 커스터마이즈는 SLDS 2에서 지원하지 않는다. CSS를 지워 문제가 생기면 아직 바꾸지 말라. 다시 할당한 값은 SLDS 1에서는 계속 동작하지만 "will be ignored in SLDS 2"다
  • 우리 실측: 2026-10-08 org 프로브에서 loadStyle로 넣은 :root의 hook 두 개(--slds-g-radius-border-pill, --slds-s-input-radius-border)는 프로브 컴포넌트, 표준 헤더 버튼, LightningAlert 모달까지 닿았다
  • 차이의 이유: ① 그 문장의 주어는 남의 선택자에 다시 할당한 hook 값이다. 같은 페이지의 --lwc-* 소절도 같은 꼴이다. 클래스 규칙의 속성 값을 말하는 문장이 아니다. ② 이 --slds-* 소절의 "무시된다"가 어떤 값을 가리키는지는 공식 설명이 없다 미확인. 설치된 SLDS 2 CSS(2.264.2)는 --lwc-*를 3곳(브랜드 이미지)에서만 읽으므로, "SLDS 2가 더는 읽지 않는 옛 이름에 넣은 값을 말한다"고 읽을 수는 있다 추정. 반대 사실도 있다. 같은 CSS는 --slds-c-* 이름 199개를 지금도 읽는다. 그러니 --slds-* 값이 모두 무시된다고 일반화할 수 없고, 위 추정도 이 소절을 다 설명하지 못한다. 우리가 넣은 두 이름은 SLDS 2 CSS가 지금 읽는 이름이라 닿았다. ③ "지원하지 않는다"는 정책이다. 동작을 보장하지 않는다는 뜻이지, 플랫폼이 그 CSS를 걸러 낸다는 뜻이 아니다 추정. 공식 문장이 아니라 우리 해석이다. 걸러 내는지를 밝힌 공식 문장은 찾지 못했다
  • 남은 빈칸: 클래스 규칙은 그 프로브에 들어 있지 않았다. "지금 org에서는 클래스 규칙도 닿는다"는 2026-10-07 synthetic 실측과, LWC 개발자 가이드의 설명(synthetic에서는 문서 맨 위의 공유 스타일시트가 페이지의 모든 컴포넌트를 꾸밀 수 있다)에서 나온 결론이다. org에서 클래스 규칙을 직접 잰 기록은 없다 미확인. 10/12 org 프로브에서 측정 예정이다(설계 14장): 프로브 milvusOverride에 .slds-button { border-radius: 0 } 한 줄을 넣고, 같은 화면의 lightning-button 내부 버튼과 표준 헤더 버튼의 모서리를 잰다 계획

밀버스에서는

  • 우리 org는 SLDS 2 테마를 쓰고, 밀버스는 SLDS 2 org를 기준으로 한다(설계 1장 #22). 그래서 SLDS 1의 공식 수단(c hook GA)은 쓸 수 없다
  • "기본 우선"은 늘어난 쪽(관리자 테마)을 먼저 쓰는 결정이다. 줄어든 쪽을 메우는 util.css·브리지·override는 모두 공식 권고 밖이다

3. Salesforce가 권하지 않는 이유

개념

규칙을 설명할 때는 공식 자료가 직접 밝힌 이유와, 밝히지 않아 우리가 짐작한 이유를 나눠 말해야 한다. 짐작을 공식 이유처럼 말하면 발표에서 반박당한다.

Salesforce에서는: 공식 자료가 밝힌 것

  1. hook 값의 주인은 SLDS다. global hook 값은 SLDS가 정하고, Salesforce가 언제든 바꾸고 릴리스 노트로 알린다. 값 할당은 테마 도구의 몫이고, 고객 커스터마이즈에서 재정의하는 것은 지원하지 않는다(Global Styling Hooks, Develop, Styling Hook Index)
  2. 테마는 hook 값을 바꾸는 방식으로 동작한다. 활성 테마에 따라 global hook 값이 바뀌고, Themes and Branding도 특정 hook 값을 덮어써서 브랜드를 입힌다(Styling API)
  3. 내부는 언제든 다시 설계된다. Salesforce는 성능, 기능, 접근성을 위해 컴포넌트 내부를 다시 설계할 자유가 필요하다고 적는다. HTML, CSS, DOM의 하위 호환을 보장한 적이 없고, 내부 변경은 대개 문서화하지 않는다. 지원되지 않는 커스터마이즈는 시각 회귀나 테스트 실패를 낼 수 있고, Salesforce UI 개선을 받아들이기 어렵게 만든다(Anti-Patterns, KB 001395244, Summer '24 릴리스 노트)
  4. native shadow로 옮겨 가는 중이다. 성능과 Web Components 표준을 위해 base 컴포넌트를 native shadow에 맞게 바꾸고 있고, 그 과정에서 내부 DOM 구조가 바뀐다. Spring '23부터 90개가 넘는 base 컴포넌트가 바뀌었다(Summer '25 릴리스 노트)
  5. 하드코딩과 재할당은 테마·다크 모드·접근성 개선을 따라가지 못한다. global hook 재할당은 SLDS 2에서 레이아웃을 깨뜨릴 수 있다(Transition to SLDS 2)
  6. 관리자 테마 옵션 일부는 접근성 때문에 뺐다. 배경색, 배경 이미지, 글로벌 헤더 색은 SLDS 2 테마에서 쓸 수 없고, accent 재정의는 강하게 권하지 않는다(Considerations for Themes and Branding, Manage Custom Configurations)

Salesforce에서는: 공식 자료가 밝히지 않은 것

질문공식 자료에 있는 것우리 해석
컴포넌트 hook을 SLDS 2 출시 때 왜 뺐나Spring '25 릴리스 노트는 "아직 지원하지 않음", LWC 가이드는 "작업 중"이라고만 쓴다. Winter '27에 범주와 modifier 패턴을 갖춘 Styling API로 다시 나왔다추정 SLDS 2 테마(g hook 참조) 위에서 이름 체계를 다시 설계하는 동안 비워 두었다
--slds-s-*를 왜 private로 두었나린터는 "내부용"이라는 분류만 적는다. Winter '27에 --slds-s-table-color 매핑을 접근성 이유로 바꿨다추정 컴포넌트 사이 내부 배선 값이라 릴리스마다 매핑을 바꿀 수 있게 공개 계약에서 뺐다
global hook 재정의를 막는 설계 의도 전체소유권("테마 도구 몫")과 결과(테스트 실패, 레이아웃 깨짐)까지만 밝힌다. hook마다 라이트·다크 값이 다르다추정 고객이 :root에 값을 고정하면 모드·밀도 전환과 접근성 조정이 그 hook에서 멈춘다
native 전환과 컴포넌트 hook 축소의 관계둘을 직접 잇는 문장은 없다. "native에서는 클래스 대신 hook"(Salesforce 공식 블로그, 2024-01), "컴포넌트 hook은 shadow 경계를 넘어 상속된다"(Winter '27 릴리스 노트)만 있다추정 native 전환이 클래스 override를 막는 방향을 굳혔고, hook을 유일한 공식 통로로 만들었다
"커스터마이즈가 줄었다"는 인식에 대한 답찾지 못했다. 공식 메시지는 일관되게 "더 깊은 커스터마이즈와 테마"다—

밀버스에서는

  • 발표에서는 1~6만 "Salesforce가 밝힌 이유"로 말하고, 표의 해석은 "추정"이라고 밝힌다
  • "기본 우선"은 1·2번과 맞는다. 브랜드는 org 테마로 입히고 hook은 읽기만 한다. override는 3·4번 위험을 알고 쓰는 예외다

4. 실험 A: 같은 요구를 세 방식으로

개념

같은 요구를 여러 방식으로 풀어 보면 방식마다 무엇을 대가로 내는지 보인다. 요구는 "버튼을 각지게, 글자를 굵게"다.

Salesforce에서는: 버튼 CSS가 읽는 것

/* @layer component 안의 :where(html) — SLDS 2가 c hook으로 버튼 굵기를 600으로 둔다 */
--slds-c-button-font-weight: var(--slds-g-font-weight-6);

.slds-button {
  border-radius: var(--slds-c-button-radius-border,
    var(--slds-s-button-radius-border, var(--slds-g-radius-border-2)));
  font-weight: var(--slds-c-button-font-weight, var(--slds-g-font-weight-4));
}
/* 버튼 그룹의 위치별 모서리는 더 구체적인 선택자가 s hook을 직접 읽는다 */
.slds-button-group .slds-button:first-child {
  border-start-start-radius: var(--slds-s-button-radius-border);
  border-end-start-radius: var(--slds-s-button-radius-border);
}
  • 모서리: --slds-s-button-radius-border를 읽는 줄이 30개다. Cosmos 테마에서 이 값은 --slds-g-radius-border-pill(15rem)이다
  • 굵기: 버튼만 가리키는 이름은 c hook --slds-c-button-font-weight뿐이다. 그 기본값 --slds-g-font-weight-6은 전역 hook이라 18줄이 읽는다

밀버스에서는: 세 방식

:root {
  --slds-s-button-radius-border: 0;   /* 각지게: 버튼과 버튼 그룹 30줄이 함께 바뀐다 */
  /* 굵게: 버튼만 바꾸는 허용 hook이 없다.
     --slds-c-button-font-weight는 c hook(Developer Preview, util.css 금지)
     --slds-g-font-weight-6을 바꾸면 600을 쓰는 모든 글자가 굵어진다 */
}
.slds-button { border-radius: 0; font-weight: 700; }
/* 단독 버튼은 바뀐다. 버튼 그룹의 첫째·끝 버튼 바깥 모서리는
   더 구체적인 SLDS 선택자(명시도 0,3,0)에 져서 둥근 채로 남는다 */
:root {
  --milvus-button-custom: on;                          /* 블루프린트로 그린다 */
  --milvus-button-radius: 0;
  --milvus-button-font-weight: var(--slds-g-font-weight-7);
}
<c-milvus-button label="저장" variant="brand"></c-milvus-button>   <!-- lightning-button 대신 -->
① util.css hook② override 클래스 규칙③ 밀버스 컴포넌트
각지게됨 단독·그룹 모두 0px (로컬 실측)일부 단독만 0px. 그룹 첫째·끝 바깥 모서리는 240px로 남음 (로컬 실측). 맞추려면 SLDS 선택자를 따라 써야 한다됨
굵게버튼만은 안 됨 c hook은 금지, g hook은 전역됨 700 (로컬 실측)됨
닿는 범위같은 페이지의 모든 버튼. org에서 g hook(--slds-g-radius-border-pill)이 표준 헤더 버튼과 모달까지 닿았다 (2026-10-08 실측)synthetic에서는 페이지의 모든 .slds-button org 미측정 (10/12 org 프로브에서 측정 예정, 설계 14장). native 컴포넌트 안에는 닿지 않는다<c-milvus-button>으로 바꾼 곳만. 표준 UI 버튼은 그대로라 한 화면에서 모양이 섞인다
native 전환 뒤custom property는 상속된다. 기본 컴포넌트의 native CSS(button.slds.css)도 --slds-s-button-radius-border를 읽으므로 닿을 가능성이 높다 추정기본 컴포넌트 안에는 닿지 않는다 (5절)우리 컴포넌트는 shadow 모드를 스스로 정한다. 그 안의 블루프린트 클래스는 SLDS 변경을 그대로 받는다
유지 비용낮다. 이름 폐기·매핑 변경은 릴리스 노트로 알린다릴리스마다 클래스·선택자를 다시 확인한다접근성, 아이콘, 비활성, variant를 직접 맞추고 사용처를 모두 바꾼다
공식 지위권고 밖. s hook은 private, g 재정의는 미지원지원하지 않음. 가이드의 안티패턴 예시와 같은 꼴hook 읽기는 공식. 블루프린트는 가능하면 피함
무엇을 배웠나hook은 Salesforce가 정한 읽기 지점이 있는 곳까지만 바꾸지만, 그 범위 안에서는 숨은 선택자까지 한 번에 바뀐다. 클래스 규칙은 어디든 바꿀 수 있지만 Salesforce의 선택자를 하나씩 따라가야 한다. 새 컴포넌트는 가장 확실하지만 가장 비싸고, 표준 UI와 모양이 갈라진다.

5. 실험 B: synthetic과 native를 나란히

개념

shadow DOM은 컴포넌트 내부를 감싸 페이지의 CSS 규칙이 들어가지 못하게 한다. 그러나 상속은 경계를 넘는다. shadow 트리의 맨 위 요소는 호스트에서 상속받고, --로 만든 사용자 정의 속성은 기본적으로 상속된다. 그래서 클래스 규칙은 막히고 hook 변수는 들어간다. 단, 안쪽 CSS가 그 이름을 var()로 읽어야 효과가 있다.

Salesforce에서는

  • LEX는 synthetic shadow(폴리필)를 쓴다. LWC 개발자 가이드는 synthetic에서는 문서 맨 위의 공유 스타일시트가 페이지의 모든 컴포넌트를 꾸밀 수 있고, native에서는 컴포넌트 스타일을 번들에 넣어야 한다고 적는다
  • base 컴포넌트는 native shadow로 옮겨 가는 중이다(3절 4번)

직접 해 보기

두 칸에 같은 마크업(.slds-button 두 개)과 같은 "컴포넌트 CSS"를 둔다. (가)는 그림자 없는 일반 DOM이라 synthetic처럼 문서 CSS가 닿는다. (나)는 attachShadow로 만든 진짜 shadow root 안에 둔다. 아래 전역 CSS를 켜고 끄며 결과를 본다.

/* 클래스 규칙 1개 */
.slds-button { font-weight: 700; }
/* hook 변수 1개 */
:root { --slds-s-button-radius-border: 0; }
/* 첫 번째 버튼: hook을 읽는 규칙 */
.slds-button { border-radius: var(--slds-s-button-radius-border, 15rem); font-weight: 400; }
/* 두 번째 버튼: 값을 직접 쓰는 규칙 (hook을 읽지 않는다) */
.slds-button.demo-fixed { border-radius: 15rem; }
칸버튼모서리 (hook)굵기 (클래스)
스크립트가 실행되면 계산된 값이 여기에 나온다

예상 결과 (전역 CSS를 켰을 때)

칸버튼모서리굵기이유
(가)hook을 읽는 규칙0px, 각짐700문서 CSS가 그대로 닿는다
(가)값을 직접 쓰는 규칙240px, 둥긂700클래스 규칙은 닿지만, 모서리는 hook을 읽지 않는다
(나)hook을 읽는 규칙0px, 각짐400변수는 상속으로 들어가고, 클래스 규칙은 경계에서 막힌다
(나)값을 직접 쓰는 규칙240px, 둥긂400변수는 들어갔지만 읽는 곳이 없다

끄면 네 버튼 모두 240px(15rem)과 400으로 돌아간다. 2026-10-09에 내장 브라우저(Chromium)에서 이 페이지를 열어 위 표와 같은 값이 나오는 것을 확인했다.

밀버스에서는

  • 전제 수정(전 컴포넌트 분석 0장 5번): "native에서는 --slds-s-*가 닿지 않는다"는 지나친 서술이다. custom property는 g·s 구분 없이 상속된다. native에서는 SLDS 전역 CSS 안의 읽기 지점이 사라지고, 기본 컴포넌트의 native CSS가 읽는 이름에만 닿는다. 두 번째 버튼이 그 경우다 추정, org 실측 필요
  • 그래서 native 전환 뒤에는 클래스 규칙(milvusBridge.css, milvusOverride.css)은 기본 컴포넌트 안에서 효과를 잃고, util.css의 hook도 읽는 이름이 바뀐 곳에서는 효과를 잃는다(설계 9.1의 "native" 열)

직접 확인하기

  • DevTools Elements에서 (나) 칸을 펼치면 #shadow-root (open) 아래에 <style>과 버튼이 있다. (가) 칸에는 없다
  • (나)의 첫 버튼을 선택하고 Computed 탭에서 --slds-s-button-radius-border가 상속된 값으로 보이는지 본다

6. 실험 C: 업데이트 위험

개념

override는 "지금 이 버전의 마크업과 선택자"에 기댄다. 그래서 버전이 바뀔 때 무엇이 바뀌었는지 실제 패키지에서 찾아 보면 위험의 크기를 잴 수 있다.

Salesforce에서는: 패키지와 릴리스 노트에서 찾은 사례

사례무엇이 다른가override(클래스 규칙)에 미치는 영향hook에 미치는 영향
1. 버튼 반경의 원본SLDS 1: 공개 c hook --slds-c-button-radius-border, 기본 0.25rem. SLDS 2 Cosmos: --slds-s-button-radius-border → --slds-g-radius-border-pill(15rem). 같은 2.264.2의 Lightning Blue 테마: → --slds-g-radius-border-2(0.25rem)값을 박으면 테마·버전과 상관없이 그 값이 된다. 관리자가 테마를 바꿔도 따라가지 않는다테마가 바꾼 값을 따라간다. 다만 읽는 이름이 버전마다 다르다(SLDS 1은 c, SLDS 2는 s)
2. 같은 모양, 여러 선택자SLDS 2 CSS는 버튼 그룹의 위치별 모서리를 더 구체적인 선택자로 따로 정한다.slds-button 한 줄로는 그룹 첫째·끝의 바깥 모서리가 안 바뀐다(실험 A). 선택자가 늘거나 바뀌면 다시 따라가야 한다그 선택자들도 같은 s hook을 읽어 함께 바뀐다
3. native 전환lightning-base-components 1.28.19-alpha는 package.json의 lwc.nativeShadowEnabledComponents에 156개를 지정했다. lightning-button, -badge, -input, -card가 들어 있다. native일 때 lightning-button은 호스트에 data-render-mode="shadow"를 붙이고, 안쪽 버튼을 [part~='button'] 선택자로 꾸민다문서의 .slds-button 규칙은 shadow 안에 닿지 않는다(실험 B)상속으로 들어간다. 단 읽는 이름이 다르다. 예: 버튼 굵기는 synthetic에서 c hook → g hook, native에서 --slds-s-button-font-weight
4. 릴리스마다 이름·매핑·클래스 동작Winter '26: --slds-g-font-family → -base, --slds-g-font-lineheight-* → --slds-g-font-line-height-* 등 폐기. Winter '27: --slds-s-table-color가 neutral-base-0(검정)으로 바뀌고, slds-nubbin_left·_right가 물리 방향으로 고정되며 논리 방향 slds-nubbin_start·_end가 생겼다클래스의 동작이 바뀌면 그 클래스에 기댄 규칙이 RTL 등에서 의도와 다르게 보인다위 예시 이름(--slds-g-font-family, --slds-g-font-lineheight-*)은 2.264.2에 새 이름을 가리키는 별칭으로 남아 있다. 같은 폐기 목록이라도 모두 별칭은 아니다(예: --slds-g-color-accent-dark-1은 고정값 #002775). 릴리스 노트가 대체 이름을 알려 준다
:host([data-render-mode="shadow"]) [part~='button'] {
  font-weight: var(--sds-c-button-font-weight, var(--slds-s-button-font-weight));
  border-width: var(--sds-c-button-sizing-border, var(--slds-s-button-sizing-border, 1px));
}

밀버스에서는

  • org는 아직 기본 컴포넌트를 synthetic으로 그린다(2026-10-07 실측). 156개 목록은 npm 패키지의 지정이고, org에 언제 적용될지는 미확인이다
  • 위 사례 1·4는 테마 전환이나 정기 릴리스만으로도 생긴다. native 전환을 기다리지 않아도 override는 깨질 수 있다

7. 밀버스의 선택

개념

공식 경로로 안 되는 요구를 들어줄 때는 "쓰지 않는다"와 "아무렇게나 쓴다" 사이에 규칙을 둔다. 마지막 수단으로만 쓰고, 깨지면 먼저 알아채는 장치를 함께 둔다.

Salesforce에서는

공식 경로는 org 테마(색·로고)와 hook 읽기다(2·3절). 그 밖의 방법은 모두 지원 범위 밖이고, 내부 변경은 대개 문서화되지 않는다. 그래서 깨짐을 알아채는 일은 쓰는 쪽의 몫이다.

밀버스에서는

  • 기본 우선: 기본은 Salesforce 모양 + 브랜드 색·로고다. 2~5는 브랜드 요청이 있을 때만 쓴다
  • override는 opt-in이다: milvusOverride.css는 프로젝트 소유이고 처음엔 비어 있다. LEX에서는 loadBrand가 milvusBridge → milvusBrand → milvusOverride 순서로 실어 override가 마지막에 이긴다. VF에서는 milvusHead가 같은 순서로 싣는다 계획
  • override 규칙: check --style은 막지 않고 경고한다. hex 색, !important, .slds-*가 아닌 선택자, 브랜드 색(accent) hook 재정의가 경고 대상이다. @font-face·@import는 실패다(글꼴은 바꾸지 않는다) 계획
  • 알린다: override를 쓸 때는 그 규칙이 native 전환과 Salesforce 업데이트에 약하다는 것을 사용자에게 말한다
  • 밀버스 컴포넌트는 기능이 없을 때만: 모양만 바꾸려고 만들지 않는다. milvusButton은 실험 A의 비교 예시로 남는다

8. 발표용 요약 3줄

  1. SLDS 2는 커스터마이즈의 자리를 옮겼다. 컴포넌트별 CSS 대신 테마와 hook이다. 공식 경로는 org 테마(색·로고)와 hook 읽기뿐이고, hook 재정의와 클래스 덮어쓰기는 지원하지 않는다.
  2. 지금 org는 synthetic이라 덮어쓰기가 닿을 것으로 보지만, 언제든 깨질 수 있다. org에서 잰 것은 hook이 닿는다는 것까지이고, 클래스 규칙은 아직 org에서 재지 않았다 미확인(10/12 org 프로브에서 측정 예정). native shadow에서는 클래스 규칙이 막히고, 컴포넌트가 읽는 hook만 들어간다(실험 B). 선택자와 이름은 테마·릴리스마다 바뀐다(실험 A·C).
  3. 그래서 밀버스는 기본 우선이다. 요청이 있을 때만 hook → 브리지 → opt-in override 순으로 쓰고, 새 컴포넌트는 기능이 없을 때만 만든다. 깨짐은 감지 장치로 먼저 알아챈다.

9. 스스로 점검

Q1. 고객사가 "버튼만 각지게"를 원한다. 밀버스는 어떤 순서로 제안하나?

먼저 정말 모양이 달라야 하는지 묻는다(기본 우선). 필요하면 util.css의 --slds-s-button-radius-border: 0을 제안한다. 버튼 그룹까지 함께 바뀌고 표준 UI 버튼에도 닿는다. 공식 권고 밖이고 s hook은 private로 분류된다는 것을 알린다. hook으로 안 되는 모양일 때만 milvusOverride.css로 내려간다. 새 버튼 컴포넌트는 만들지 않는다.

Q2. SLDS 1 Best Practices에 "will be ignored in SLDS 2"가 있는데, 우리 org에서는 util.css가 닿았다. 모순인가?

정책과 실제 도달로 나눠 보면 모순은 아니다. 그 문장은 남의 선택자에 다시 할당한 hook 값을 말하고, "지원하지 않는다"는 정책이지 차단이 아니다 추정(공식 문장이 아니라 우리 해석). 우리가 넣은 hook은 SLDS 2 CSS가 읽는 이름이었고, org가 synthetic이라 닿았다. 다만 이 --slds-* 소절의 "무시된다"가 어떤 값을 가리키는지는 공식 설명이 없다 미확인. "SLDS 2가 더는 읽지 않는 옛 이름(--lwc-* 등)을 말한다"는 우리 추정이다 추정. 설치된 SLDS 2 CSS는 --lwc-*를 3곳에서만 읽어 이 추정과 맞지만, --slds-c-*는 199개를 지금도 읽어 맞지 않는다. 발표에서는 이유를 단정하지 않는다. 클래스 규칙은 아직 org에서 직접 재지 않았다. 10/12 org 프로브에서 측정 예정이다(설계 14장).

Q3. 실험 B에서 전역 CSS를 켰을 때 (나)의 첫 버튼은 각지는데 굵어지지 않는다. 왜?

hook 변수(--slds-s-button-radius-border)는 custom property라서 상속으로 shadow 안에 들어가고, 안쪽 CSS가 그 이름을 읽는다. 클래스 규칙(.slds-button { font-weight: 700 })은 문서의 규칙이라 shadow 경계에서 막힌다.

Q4. (나)의 두 번째 버튼은 hook 변수가 들어갔는데도 둥글다. 무엇을 뜻하나?

안쪽 CSS가 그 이름을 읽지 않고 값을 직접 쓰기 때문이다. native에서 hook이 "닿는다"와 "효과가 있다"는 다르다. 기본 컴포넌트의 native CSS가 읽는 이름에만 효과가 있다(전 컴포넌트 분석의 전제 수정).

Q5. .slds-button { border-radius: 0 }을 넣었더니 버튼 그룹의 양 끝이 둥근 채다. 왜이고, 어떻게 고치나?

SLDS 2 CSS가 그룹의 위치별 모서리를 .slds-button-group .slds-button:first-child 같은 더 구체적인 선택자로 따로 정하기 때문이다. 그 선택자들이 --slds-s-button-radius-border를 직접 읽으므로, 그 hook을 0으로 두면 한 번에 바뀐다. 클래스 규칙으로 고치려면 SLDS 선택자를 하나씩 따라 써야 한다.

Q6. "버튼만 굵게"는 util.css hook으로 왜 안 되나?

SLDS 2 CSS의 버튼 굵기는 c hook --slds-c-button-font-weight를 읽고, 그 기본값이 전역 hook --slds-g-font-weight-6이다. c hook은 SLDS 2에서 Developer Preview라 util.css가 막고, g hook을 바꾸면 600을 쓰는 다른 글자도 모두 굵어진다. --slds-s-button-font-weight는 설치된 SLDS 2 CSS(2.264.2)가 읽지 않는다(org에서 잰 것은 아니다).

Q7. Salesforce는 왜 SLDS 2에서 컴포넌트 hook을 뺐나?

공식 문서에는 이유가 없다. "아직 지원하지 않음", "작업 중"이라고만 썼고, Winter '27에 Developer Preview로 다시 나왔다. 이름 체계를 다시 설계하는 동안 비웠다는 것은 우리의 추정이다. 발표에서는 추정이라고 밝힌다.
