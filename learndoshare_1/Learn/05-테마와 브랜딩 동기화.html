테마와 브랜딩 동기화

org의 Themes and Branding 설정이 어디에 어떻게 저장되는지 이해하고, 그것을 Storybook 브랜드로 가져오는 방법과 메타데이터로 배포하는 방법을 정리한다.

예상 1시간선행: 00 개념, 01 SLDS2026-09-26 org 조회 · 2026-10-08 org 프로브 · 2026-10-09 갱신

왜 알아야 하나

밀버스의 색상 원칙은 "색은 org 테마에서 온다"이다. 브랜드 색과 로고는 Salesforce 공식 기능인 Themes and Branding이 정한다. 브랜드 색을 넣으면 Salesforce가 어울리는 팔레트를 자동으로 만들고, 그 팔레트가 org 화면 전체에 쓰인다.

그런데 Storybook은 로컬에서 돌아가므로 org가 없다. org의 색을 Storybook에서 보려면 테마 정보를 org 밖으로 가져와야 한다. 이 문서는 그 재료다.

2026-10-09 갱신: 테마를 메타데이터로 관리한다처음에는 관리자가 Setup에서 색을 정하고 스크립트가 읽어 오기만 하는 흐름이었다. 2026-10-08 설계에서는 테마를 메타데이터 파일(BrandingSet, LightningExperienceTheme)로 프로젝트에 두고, 배포로 org에 만들고 활성화한다. 2026-10-08 org 프로브에서 테마 생성, 활성화, 복구가 모두 배포로 되는 것을 확인했다. 이 흐름을 맡을 패키지 명령(pnpm milvus init, pnpm milvus deploy)은 아직 구현 전이다.
프로젝트 (원본)BrandingSet 파일의 BRAND_COLOR, 로고
→
Storybook (미리 보기)같은 색으로 팔레트를 계산해 그린다
→
org (적용)테마를 배포하고 activeThemeName으로 활성화

org에 이미 쓰는 테마가 있으면 반대로 org에서 받아 온다. 디자인 시스템 저장소의 데모 브랜드(brands/)는 지금 pnpm sync:theme으로 org를 조회해 만든다. 패키지에서는 init --from-org가 이 역할을 맡을 계획이다.

시뮬레이션이라는 점을 잊지 말 것Storybook에서 브랜드를 바꿔도 org는 바뀌지 않는다. org에 적용하려면 테마를 배포해 활성화하거나, 관리자가 Setup에서 테마를 활성화한다. 활성 테마는 org 하나에 하나뿐이고 org 전체에 적용된다.

Themes and Branding이 다루는 것

간격, 반경아니오기본은 SLDS 기본값이다. 브랜드 요청이 있을 때만 util.css(milvusBrand.css)로 바꾼다 (2026-10-09 밀버스 결정)

org에는 커스텀 테마를 300개까지 만들 수 있지만, 활성 테마는 하나이고 org 전체에 적용된다. Lightning Blue, Salesforce Cosmos 같은 내장 테마는 고치거나 복제할 수 없다. 메타데이터 LightningExperienceTheme은 커스텀 테마를 나타내고, 설정의 activeThemeName이 비어 있으면 org는 내장 테마를 쓴다. 2026-09-26 조회에서도 내장 테마는 레코드로 나오지 않고 직접 만든 커스텀 테마만 나왔다.

미확인 항목"한 org에 테마를 여러 개 두고 pnpm sync:theme이 전부 읽으면 Storybook에 브랜드 여러 개가 뜬다"는 아직 확인하지 못했다. 2026-10-08 프로브에서 두 번째 테마를 잠시 배포했지만, 그때 스크립트를 실행한 기록은 없다.

데이터 구조

처음에는 테마 레코드에 색상 필드가 있을 것이라고 생각했지만 그렇지 않다. 색은 테마가 가리키는 브랜딩 집합(BrandingSet)의 속성으로 저장된다.

Lightning Experience 테마의 속성 이름은 Metadata API의 BrandingSet 문서에 표로 있다. 이름은 대문자이고 대소문자를 구분한다. SLDS 2 테마에는 ACCENT_COLOR_1~3, CONTAINER_ACCENT_COLOR_1~3(API 64.0부터), ACCENT_CONTAINER_CONTENT_COLOR_1~3(API 65.0부터)도 있다. HEADER_BACKGROUND_COLOR, PAGE_BACKGROUND_COLOR, OVERRIDE_A11Y_COLOR, BANNER_IMAGE, LINK_AS_BACKGROUND는 SLDS 1 테마 전용이다.

우리 org 조회 결과

2026-09-26에 org learndoshare_1의 테마 Milvus_DesignSystem (SLDS_v2, 다크 모드 꺼짐)이 가리키는 BrandingSet LEXTHEMINGMilvus_DesignSystem의 속성을 조회한 결과다. 이 조회의 원본 기록은 docs/research/에 없다. 테마와 BrandingSet의 이름은 2026-10-08 프로브의 조회 파일로 다시 확인했다. README 3장에는 테마(SLDS_v2, 다크 모드 꺼짐), BRAND_COLOR, HEADER_BACKGROUND_COLOR, BRAND_IMAGE 경로와 "자동 생성 팔레트는 API로 읽을 수 없다"는 결과가 남아 있다. 아래 표의 OVERRIDE_LOADING_PAGE와 null 항목은 README에도 기록이 없는 2026-09-26 조회 결과다 (2026-10-09 갱신).

SLDS 2 전용 ACCENT_COLOR_*, CONTAINER_ACCENT_COLOR_* 속성은 저장되어 있지 않았다. Help 문서는 이 고급 accent 색이 브랜드 색에서 자동으로 만들어지고, 덮어쓰지 말 것을 강하게 권한다고 적는다.

가장 중요한 발견 (2026-10-09 갱신)읽히는 색은 사실상 BRAND_COLOR 하나다. Salesforce는 브랜드 색으로 접근성(WCAG)을 맞춘 팔레트를 자동으로 만들지만, 파생 색은 API로 읽히지 않았다. 그래서 Storybook은 원본 색 하나로 팔레트를 직접 계산한다(lib/palette.ts). 2026-10-08 프로브에서 브랜드 색 #2E7D32를 활성화했을 때 LEX의 accent 색은 #468244였고, 우리 계산의 50단계와 같았다. LEX 화면에서 직접 잰 단계는 이 50단계 하나다.

조회 방법

1. 필드 목록 확인 (describe)

sf sobject describe --sobject LightningExperienceTheme --use-tooling-api -o learndoshare_1 --json \
  | jq -r '.result.fields[] | "\(.name)\t\(.type)"'

2. 테마와 연결된 BrandingSet 찾기

sf data query --use-tooling-api -o learndoshare_1 \
  -q "SELECT Id, DeveloperName, MasterLabel, DefaultBrandingSetId FROM LightningExperienceTheme"

3. 모든 BrandingSet의 속성을 한 번에 조회

sf data query --use-tooling-api -o learndoshare_1 --json \
  -q "SELECT BrandingSetId, BrandingSet.DeveloperName, PropertyName, PropertyValue
      FROM BrandingSetProperty ORDER BY BrandingSetId, PropertyName"

관계 필드 BrandingSet.DeveloperName으로 부모 이름을 같이 가져올 수 있다. BrandingSetProperty는 일반 API(--use-tooling-api 없이)로도 조회됐다(2026-09-26).

Metadata 필드 조회 시 주의Tooling API 문서는 Metadata·FullName 필드를 결과가 한 건 이하일 때만 조회하라고 적는다(BrandingSet 페이지). LightningExperienceTheme의 Metadata도 같은 제한을 받았다(2026-09-26). 그래서 WHERE Id = '...'처럼 한 건으로 좁혀야 한다. 전체를 순회할 때는 Metadata 대신 일반 필드를 쓴다.

4. 메타데이터 파일로 받기 (2026-10-09 갱신)

sf project retrieve start -o learndoshare_1 \
  -m LightningExperienceTheme:Milvus_DesignSystem \
  -m BrandingSet:LEXTHEMINGMilvus_DesignSystem \
  -m Settings:LightningExperience

2026-10-08 프로브는 배포 전에 BrandingSet, LightningExperienceTheme, Settings:LightningExperience를 메타데이터로 받아 두었다. 그래서 "BrandingSet까지 함께 받아지는가"는 더 이상 미확인이 아니다. 설계에서는 받은 테마 파일(BrandingSet, LightningExperienceTheme)을 프로젝트 소유 파일로 둔다(설계 3장). 받은 파일을 공개 저장소에 올리기 전에는 org 주소나 사용자 이름이 섞이지 않았는지 본다.

sync 스크립트 (저장소 데모용)

2026-10-09 갱신이 설계는 scripts/sync-theme.mjs로 구현됐다. 2026-10-08 설계에서 프로젝트용 경로는 pnpm milvus init --from-org로 바뀌었다(구현 전). 이 명령은 activeThemeName으로 활성 테마를 먼저 찾고, 그 테마의 LightningExperienceTheme, BrandingSet, 로고만 받아 프로젝트에 복사할 계획이다. pnpm sync:theme은 디자인 시스템 저장소의 데모 브랜드(brands/)에만 쓴다.

요구사항

  • 명령 하나: pnpm sync:theme
  • 테마 레코드를 전부 순회한다. 테마를 하나 더 만들면 스크립트를 고치지 않아도 브랜드가 추가된다
  • 결과는 brands/<DeveloperName>/theme.json (브랜드 색과 팔레트 17단계). 로고는 같은 폴더의 logo.*
  • JSON에는 색과 이름만 담는다. org 인증 토큰은 절대 넣지 않는다

처리 흐름

1. 테마 조회DeveloperName, MasterLabel, DefaultBrandingSetId
→
2. 속성 조회BrandingSetProperty 전체
→
3. 묶기BrandingSetId로 테마와 연결
→
4. 팔레트BRAND_COLOR로 17단계 계산
→
5. 저장테마마다 JSON 1개

뼈대 코드

실제 파일에는 테마 이름 고르기, 로고 다운로드, 오류 처리가 더 있다.

import { execFileSync } from 'node:child_process';
import { mkdirSync, writeFileSync } from 'node:fs';
import { brandPalette } from '../lib/palette.ts';

const org = process.env.SF_ORG ?? 'learndoshare_1';

// sf CLI 실행 결과(JSON)에서 레코드만 꺼낸다
function query(soql) {
  const out = execFileSync('sf', ['data', 'query', '--use-tooling-api', '-o', org, '--json', '-q', soql], { encoding: 'utf8' });
  return JSON.parse(out).result.records;
}

const themes = query('SELECT DeveloperName, MasterLabel, DefaultBrandingSetId FROM LightningExperienceTheme');
const props = query('SELECT BrandingSetId, PropertyName, PropertyValue FROM BrandingSetProperty');

// BrandingSetId → { BRAND_COLOR: '#0176D3', ... }
const bySet = {};
for (const p of props) {
  (bySet[p.BrandingSetId] ??= {})[p.PropertyName] = p.PropertyValue;
}

for (const t of themes) {
  const dir = `brands/${t.DeveloperName}`;
  mkdirSync(dir, { recursive: true });
  const values = bySet[t.DefaultBrandingSetId] ?? {};
  const theme = {
    name: t.DeveloperName,
    label: t.MasterLabel,
    brandColor: values.BRAND_COLOR,
    palette: values.BRAND_COLOR ? brandPalette(values.BRAND_COLOR) : null, // org가 저장하지 않는 파생 색
  };
  writeFileSync(`${dir}/theme.json`, JSON.stringify(theme, null, 2));
}

execSync에 문자열을 이어 붙이는 대신 execFileSync로 인자를 배열로 넘겼다. 기본값으로는 셸을 거치지 않으므로 따옴표나 공백 때문에 깨지지 않고, 셸 메타 문자로 다른 명령이 실행될 위험도 없다.

스스로 점검

Q1. 브랜드 색은 어느 객체의 어느 필드에 들어 있나?

BrandingSetProperty의 PropertyName = 'BRAND_COLOR'인 행의 PropertyValue. 테마(LightningExperienceTheme)에는 색 필드가 없고 DefaultBrandingSetId로 연결된다. 메타데이터 파일에서는 BrandingSet의 brandingSetProperty 목록에 있다.

Q2. Setup에서 자동 생성된 팔레트를 API로 가져올 수 있나?

읽히지 않았다(2026-09-26 조회). 원본 색(BRAND_COLOR)만 저장된다. Storybook은 같은 규칙으로 팔레트를 계산하고, 50단계는 2026-10-08 org 실측과 같았다.

Q3. 테마를 하나 더 만들었을 때 스크립트를 고쳐야 하나?

고치지 않는다. 스크립트가 테마 레코드를 전부 순회하므로 pnpm sync:theme을 다시 실행하면 JSON이 하나 더 생긴다. 실제로 두 테마를 함께 읽어 본 기록은 아직 없다(미확인).

Q4. 왜 Metadata 필드로 전체 테마를 한 번에 읽지 않나?

Tooling API의 Metadata 필드는 결과가 한 건 이하일 때만 조회되기 때문이다. 게다가 색은 테마의 Metadata에도 없다 (defaultBrandingSet 이름만 있다).

Q5. "Storybook에서 브랜드를 바꾸면 org도 바뀌나요?"라는 질문에 어떻게 답하나?

"아니요. Storybook은 미리 보기입니다. org에 적용하려면 테마를 메타데이터로 배포하고 activeThemeName으로 활성화합니다(밀버스 설계의 pnpm milvus deploy, 구현 전). 관리자가 Setup의 Themes and Branding에서 활성화할 수도 있습니다."
