LEARN 05 · Phase 4 준비

테마와 브랜딩 동기화

org의 Themes and Branding 설정이 어디에 어떻게 저장되는지 이해하고, 그것을 Storybook 브랜드로 가져오는 스크립트를 설계한다.

예상 1시간선행: 01 SLDS2026-09-26 org 조회로 확인

왜 알아야 하나

밀버스의 색상 원칙은 "색은 org에서 온다"이다. 관리자가 Setup에서 브랜드 색을 바꾸면 커스텀 컴포넌트도 코드 배포 없이 따라가야 한다.

그런데 Storybook은 로컬에서 돌아가므로 org가 없다. org의 색을 Storybook에서 보려면 누군가 가져와야 한다. 이 문서는 그 "가져오기"의 재료다.

org (실제)관리자가 Setup에서 테마 색 지정
→
pnpm sync:themesf CLI로 테마 조회 후 JSON 생성
→
Storybook (시뮬레이션)툴바에서 브랜드를 골라 미리 보기
시뮬레이션이라는 점을 잊지 말 것Storybook에서 브랜드를 바꿔도 org는 바뀌지 않는다. Storybook은 미리 보는 곳이고, 실제 적용은 관리자가 Setup에서 한다.

Themes and Branding이 다루는 것

항목Setup에서 관리?밀버스에서 관리하는 곳
브랜드 색예Themes and Branding (관리자, 배포 불필요)
헤더 배경색예Themes and Branding
로고, 배너 이미지예Themes and Branding
폰트, 타이포 계층아니오사내 CSS 변수 파일 1개 (개발자, 배포 필요)
간격, 반경아니오SLDS 기본값 그대로 (건드리지 않음)

org에는 커스텀 테마를 여러 개 만들 수 있지만, 동시에 활성화되는 테마는 하나다. Lightning Blue 같은 내장 테마는 레코드로 조회되지 않고, 직접 만든 커스텀 테마만 조회된다.

미확인 항목"한 org에 테마 레코드를 여러 개 만들어 두고 스크립트가 전부 읽으면 Storybook에 브랜드 여러 개가 뜬다"는 아직 확인하지 못했다. Phase 4에서 두 번째 테마를 만들어 확인한다.

데이터 구조

처음에는 테마 레코드에 색상 필드가 있을 것이라고 생각했지만 그렇지 않다. 색은 테마가 가리키는 브랜딩 집합(BrandingSet)의 속성으로 저장된다.

LightningExperienceTheme테마 1개. 이름, SLDS 버전, 다크 모드 여부
→
BrandingSetDefaultBrandingSetId로 연결. 이름은 LEXTHEMING + 테마 이름
→
BrandingSetProperty여러 행. PropertyName / PropertyValue 쌍

LightningExperienceTheme 주요 필드 (Tooling API)

필드타입의미
DeveloperNamestringAPI 이름. 예: Milvus_DesignSystem
MasterLabelstring화면에 보이는 이름
DefaultBrandingSetIdreference색이 들어 있는 BrandingSet의 Id
DesignSystemVersionpicklistSLDS_v2 등
IsDarkModeEnabledboolean다크 모드 사용 여부
Metadatacomplexvalue메타데이터 전체 (JSON). 아래 주의 참고

색상 이름이 들어간 필드는 하나도 없다. 이것이 "필드명을 추측하지 말고 describe로 확인하라"는 규칙이 필요했던 이유다.

BrandingSetProperty 필드

필드타입의미

가장 중요한 발견읽히는 색은 두 개뿐이다. Setup 화면에서 브랜드 색 하나를 넣으면 Salesforce가 밝기가 다른 파생 색(팔레트)을 자동으로 만들지만, 파생 색은 API에 저장되지 않는다. Storybook에서는 원본 색 하나로 파생 색을 우리가 직접 계산해야 하고, 그래서 org와 미세하게 다를 수 있다.

조회 방법

1. 필드 목록 확인 (describe)

sf sobject describe --sobject LightningExperienceTheme --use-tooling-api -o learndoshare_1 --json \
  | jq -r '.result.fields[] | "\(.name)\t\(.type)"'

2. 테마와 연결된 BrandingSet 찾기

sf data query --use-tooling-api -o learndoshare_1 \
  -q "SELECT Id, DeveloperName, MasterLabel, DefaultBrandingSetId FROM LightningExperienceTheme"

3. 모든 BrandingSet의 속성을 한 번에 조회

sf data query --use-tooling-api -o learndoshare_1 --json \
  -q "SELECT BrandingSetId, BrandingSet.DeveloperName, PropertyName, PropertyValue
      FROM BrandingSetProperty ORDER BY BrandingSetId, PropertyName"

관계 필드 BrandingSet.DeveloperName으로 부모 이름을 같이 가져올 수 있다. BrandingSetProperty는 일반 API(--use-tooling-api 없이)로도 조회된다.

Metadata 필드 조회 시 주의Tooling API에서 Metadata(complexvalue) 필드는 결과가 한 건일 때만 조회된다. 그래서 WHERE Id = '...'처럼 한 건으로 좁혀야 한다. 전체를 순회할 때는 Metadata 대신 일반 필드를 쓴다.

참고: 메타데이터로 받아 보기

sf project retrieve start -m LightningExperienceTheme:Milvus_DesignSystem -o learndoshare_1

파일로 받으면 구조를 읽기 쉽다. 다만 받은 파일을 저장소에 커밋할지는 미정이다 (README "결정이 필요한 것"). 스크립트는 파일 없이 조회 결과만 쓰므로 retrieve가 필요 없다. 미확인 BrandingSet 메타데이터까지 함께 받아지는지는 아직 시험하지 않았다.

sync 스크립트 설계

요구사항

  • 명령 하나: pnpm sync:theme
  • 테마 레코드를 전부 순회한다. 테마를 하나 더 만들면 스크립트를 고치지 않아도 브랜드가 추가된다
  • 결과는 brands/<DeveloperName>/theme.json (로고는 같은 폴더의 logo.*)
  • JSON에는 색과 이름만 담는다. org 인증 토큰은 절대 넣지 않는다

처리 흐름

1. 테마 조회DeveloperName, MasterLabel, DefaultBrandingSetId
→
2. 속성 조회BrandingSetProperty 전체
→
3. 묶기BrandingSetId로 테마와 연결
→
4. 매핑BRAND_COLOR를 accent hook 계열로 변환
→
5. 저장테마마다 JSON 1개

뼈대 코드

import { execFileSync } from 'node:child_process';
import { mkdirSync, writeFileSync } from 'node:fs';

const org = process.env.SF_ORG ?? 'learndoshare_1';

// sf CLI 실행 결과(JSON)에서 레코드만 꺼낸다
function query(soql) {
  const out = execFileSync('sf', ['data', 'query', '--use-tooling-api', '-o', org, '--json', '-q', soql], { encoding: 'utf8' });
  return JSON.parse(out).result.records;
}

const themes = query('SELECT DeveloperName, MasterLabel, DefaultBrandingSetId FROM LightningExperienceTheme');
const props = query('SELECT BrandingSetId, PropertyName, PropertyValue FROM BrandingSetProperty');

// BrandingSetId → { BRAND_COLOR: '#0176D3', ... }
const bySet = {};
for (const p of props) {
  (bySet[p.BrandingSetId] ??= {})[p.PropertyName] = p.PropertyValue;
}

for (const t of themes) {
  const dir = `brands/${t.DeveloperName}`;
  mkdirSync(dir, { recursive: true });
  const values = bySet[t.DefaultBrandingSetId] ?? {};
  const theme = {
    name: t.DeveloperName,
    label: t.MasterLabel,
    brandColor: values.BRAND_COLOR,
    headerBackground: values.HEADER_BACKGROUND_COLOR,
    hooks: toAccentHooks(values.BRAND_COLOR), // 01 SLDS 문서의 accent hook 목록 참고
  };
  writeFileSync(`${dir}/theme.json`, JSON.stringify(theme, null, 2));
}

execSync에 문자열을 이어 붙이는 대신 execFileSync로 인자를 배열로 넘겼다. 셸을 거치지 않으므로 따옴표나 공백 때문에 깨지지 않는다.

산출물 예시

{
  "name": "Milvus_DesignSystem",
  "label": "Milvus_DesignSystem",
  "brandColor": "#0176D3",
  "headerBackground": "#FFFFFF",
  "hooks": {
    "--slds-g-color-accent-1": "#0176D3",
    "...": "파생 색 (직접 계산)"
  }
}

Storybook의 decorator가 이 폴더를 읽어 툴바 항목을 만들고, 선택된 테마의 hooks를 래퍼 요소의 CSS 변수로 주입한다. 자세한 방법은 03 스토리북 · decorator와 globals에 있다.

한계와 주의

한계영향대응
원본 색만 읽힌다파생 색이 org와 미세하게 다를 수 있다발표에서 시뮬레이션임을 밝힌다. 핵심 화면은 org 캡처와 비교한다
폰트는 동기화되지 않는다"전부 자동"이 아니다타이포는 CSS 변수 파일로 관리한다고 명확히 말한다
앱 단위 브랜딩(App Branding)은 다른 곳에 저장된다브랜드가 앱 단위라면 이 스크립트로 못 읽는다브랜드 단위(org / 앱)가 정해지면 확장한다 미정
sf 인증이 필요하다CI에서는 별도 인증이 필요하다로컬에서만 실행하고 결과 JSON을 커밋하는 방식으로 시작한다

스스로 점검

Q1. 브랜드 색은 어느 객체의 어느 필드에 들어 있나?

BrandingSetProperty의 PropertyName = 'BRAND_COLOR'인 행의 PropertyValue. 테마(LightningExperienceTheme)에는 색 필드가 없고 DefaultBrandingSetId로 연결된다.

Q2. Setup에서 자동 생성된 팔레트를 API로 가져올 수 있나?

없다. 원본 색(BRAND_COLOR)만 저장된다. 파생 색은 Storybook 쪽에서 계산하므로 org와 다를 수 있다.

Q3. 테마를 하나 더 만들었을 때 스크립트를 고쳐야 하나?

고치지 않는다. 스크립트가 테마 레코드를 전부 순회하므로 pnpm sync:theme을 다시 실행하면 JSON이 하나 더 생긴다.

Q4. 왜 Metadata 필드로 전체 테마를 한 번에 읽지 않나?

Tooling API의 complexvalue 필드(Metadata)는 결과가 한 건일 때만 조회되기 때문이다. 게다가 색은 Metadata에도 없다 (defaultBrandingSet 이름만 있다).

Q5. "Storybook에서 브랜드를 바꾸면 org도 바뀌나요?"라는 질문에 어떻게 답하나?

"아니요. Storybook은 org 설정을 가져와 미리 보는 시뮬레이션입니다. 실제 적용은 관리자가 Setup의 Themes and Branding에서 합니다."
