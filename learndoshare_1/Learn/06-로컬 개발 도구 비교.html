LEARN 06 · Phase 7 준비

로컬 개발 도구 비교

LWC를 배포하지 않고 확인하는 방법은 여러 가지다. 각 도구가 무엇을 잘하고 무엇을 못하는지 정리하고, 밀버스에서 어떤 도구를 어디에 쓸지 정한다.

예상 1시간선행: 03 Storybook, 04 통합2026-09-26 확인 · 2026-10-09 공식 문서로 다시 확인

왜 알아야 하나

밀버스의 주 경로는 Storybook이다 (04 통합). 그런데 발표나 리뷰에서 "Salesforce 공식 도구(Live Preview)가 있는데 왜 Storybook을 따로 쓰나?"라는 질문이 반드시 나온다.

답은 "둘 중 하나"가 아니라 "잘하는 일이 다르다"이다. 이 문서는 그 답의 근거를 모으고, Phase 7 보조 실습에서 직접 비교할 계획을 세운다.

이름부터 헷갈린다 (2026-10-09 갱신)"Local Dev"는 2026년 4월 13일 주부터 Live Preview로 이름이 바뀌었다(Summer '26 릴리스 노트). LWC 개발자 가이드는 Spring '26에 이름을 바꿨다고 적는다. CLI 명령(sf lightning dev …)은 그대로다. 또 이와 별개로, 예전 "Local Development Server"는 2025년 9월 5일에 은퇴했다. 블로그 글이 어느 쪽을 말하는지 먼저 확인한다.

Live Preview (구 Local Dev)

CLI 플러그인 @salesforce/plugin-lightning-dev(2026-10-09 기준 최신 6.2.19)로 동작한다. 공식 문서는 "Salesforce CLI가 Live Preview 플러그인을 자동으로 설치한다"고 적는다. 그래서 따로 설치할 필요가 없다(Summer '26 릴리스 노트). VS Code 확장(Live Preview VS Code Extension)도 있다. (2026-10-09 갱신: "CLI에 함께 들어 있는 플러그인"을 공식 표현으로 고쳤다)

명령보는 대상메모
sf lightning dev appLightning 앱데스크톱 또는 -t(--device-type)로 iOS 시뮬레이터·Android 에뮬레이터
sf lightning dev siteExperience Cloud LWR 사이트사이트를 먼저 게시해야 한다. --ssr는 Spring '26부터 지원 안 함
sf lightning dev component컴포넌트 하나를 단독으로-n 이름, -o 대상 org (Winter '26부터 필수). 이름 없이 실행하면 프로젝트의 컴포넌트 목록에서 고른다. -c(--client-select)는 컴포넌트를 고르지 않고 미리 보기를 연다 (2026-10-09 갱신)
# 컴포넌트 하나를 org에 연결해 미리 보기
sf lightning dev component -n milvusBadge -o learndoshare_1

# 이름 없이 실행하면 목록에서 골라 실행
sf lightning dev component -o learndoshare_1

준비 조건

  • 처음 실행하면 CLI가 org에서 기능을 켤지 묻는다. org 설정이 바뀐다(Metadata API의 enableLightningPreviewPref가 "Local Dev 사용 여부" 필드다)
  • 기능을 켜는 사람의 권한: View Setup, Customize Application
  • 프로젝트에 lwc 디렉터리가 있어야 한다
  • 운영 org에서도 쓸 수 있지만, 공식 문서는 sandbox와 scratch org에서만 쓰기를 권한다

되는 것과 안 되는 것

항목동작
HTML/CSS 수정, 공개 API를 바꾸지 않는 JS 수정, 새 컴포넌트 참조HMR 저장하면 바로 반영
새 @api, @wire 관련 변경, 새 @salesforce scoped import, .js-meta.xml 수정수동 단독 컴포넌트는 브라우저 새로 고침, 앱·사이트는 배포 후 Live Preview 서버 재시작
단독 컴포넌트에서 LDS wire adapter, @salesforce scoped 모듈, Apex 컨트롤러가능 Winter '26에 베타로 추가(Winter '26 릴리스 노트). Apex는 Salesforce 서버에서 실행되는 언어다(Apex 개발자 가이드). 로컬에서 고친 Apex가 미리 보기에 바로 반영되는지는 문서에 없다 미확인 (2026-10-09 갱신)
Aura 컴포넌트, Landing Page지원 안 함
베타 여부 (2026-10-09 갱신)이전에는 "베타일 수 있다"고 적었다. 공식 릴리스 노트로 다시 확인했다. Lightning 앱 미리 보기는 Spring '25에 GA가 됐다. 단일 컴포넌트 미리 보기(Single Component Live Preview)는 2026년 4월 13일 주부터 GA다. Experience 사이트 미리 보기는 Spring '25 기준 베타였고, 지금 상태는 찾지 못했다 미확인. VS Code 확장으로 React 컴포넌트를 미리 보는 것은 베타다.

은퇴한 Local Development Server

쓰지 않는다예전 도구 LWC Local Development Server(Salesforce CLI 플러그인 @salesforce/lwc-dev-server, 마지막 버전 2.11.0)는 2025년 9월 5일에 은퇴했다 (Summer '25 릴리스 노트). Salesforce GitHub 조직(forcedotcom)의 관련 저장소 lwc-dev-server는 2024년 2월 17일, lwc-dev-server-feedback은 2024년 8월 10일에 보관(archived) 처리됐다. VS Code 확장 65.18.0(2026-02-18)에서 관련 명령 4개가 제거됐다(salesforcedx-vscode CHANGELOG). 2026-10-09 갱신: 보관 연도를 2023년에서 2024년으로 고쳤다.

블로그에 "LWC Local Development Server"나 lwc-dev-server가 나오면 이 도구를 말하는 것이다. 따라 하지 않는다.

Storybook

밀버스 주 경로다. LWC를 Rollup으로 컴파일하고 Storybook(@storybook/web-components-vite)에서 렌더한다. 구성은 04 통합에 있다. (2026-10-09 갱신: 블로그 이름으로 부르던 "digitalflask 방식" 표현을 뺐다)

잘하는 것

org 없음, 컴포넌트 카탈로그, 한 화면에 여러 상태 나열, Controls로 props 조작, 브랜드 전환 툴바, 정적 빌드로 비개발자에게 공유, 접근성 검사(a11y 애드온, axe-core)

못하는 것

실제 데이터 없음(mock 필요), LWC를 바꾸면 pnpm build:lwc를 다시 실행해 다시 빌드한다. 컴포넌트 단위 HMR이 아니다. 2026-10-09 갱신: 감시 모드 스크립트 pnpm dev:lwc(rollup -w)는 빌드를 lib/lwc-build.ts(Rollup JavaScript API)로 옮기면서 지웠다

org 내 문서 앱

org 안에 Lightning App Builder로 앱 페이지를 만들어 컴포넌트를 나열하는 방법이다. 컴포넌트를 App Builder에 올리려면 .js-meta.xml에 대상(lightning__AppPage 등)을 정하고 org에 배포해야 한다.

  • 장점: 통합 위험이 0이다. 실제 환경 그대로 보인다
  • 단점: 확인할 때마다 배포해야 한다. props 조작, 코드 보기 같은 문서 기능을 직접 만들어야 한다

역할 분담 권장

한 줄 결론개발 중 데이터 붙은 확인은 Live Preview, 카탈로그·변형·브랜드·공유·프로젝트 시작은 Storybook. 조건: 표현/컨테이너 분리.
표현 컴포넌트props만 받아 그린다. 예: milvusBadge
→
Storybook모든 상태·브랜드를 나열하고 공유한다
→
컨테이너 컴포넌트@wire, Apex로 데이터를 받아 표현 컴포넌트에 넘긴다
→
Live Preview실제 데이터로 연결을 확인한다
분리가 왜 조건인가표현 컴포넌트 안에 @wire가 섞여 있으면 Storybook에서 그릴 때마다 mock이 필요해지고, 상태 나열이라는 Storybook의 강점이 사라진다. 반대로 분리돼 있으면 표현은 Storybook, 연결은 Live Preview로 깔끔하게 나뉜다. 이 분리는 밀버스의 결정이다(README 1.3 원칙, 확정. 2026-10-09 갱신).

스스로 점검

Q1. 블로그에 "LWC Local Development Server로 로컬에서 띄우라"고 나온다. 따라 해도 되나?

안 된다. Local Development Server(@salesforce/lwc-dev-server)는 2025년 9월 5일에 은퇴했다. 지금은 Live Preview(sf lightning dev)를 쓴다.

Q2. Live Preview에서 컴포넌트에 새 @api 속성을 추가했는데 반영되지 않는다. 왜인가?

공개 API가 바뀌는 수정은 자동 반영 대상이 아니다. 새 @api, @wire 관련 변경, 새 scoped import, .js-meta.xml 수정은 단독 컴포넌트라면 브라우저를 새로 고치고, 앱·사이트라면 배포한 뒤 Live Preview 서버를 다시 시작한다.

Q3. "공식 도구가 있는데 왜 Storybook을 쓰나?"에 어떻게 답하나?

"잘하는 일이 다릅니다. Live Preview는 org에 붙여 실제 데이터로 확인할 때, Storybook은 org 없이 모든 상태·브랜드를 나열하고 정적 빌드로 비개발자와 공유할 때 씁니다."

Q4. LWC Garden을 주 경로로 쓰지 않는 이유 두 가지는?

① 저장소와 README의 라이선스가 배포 조건이 까다로운 GPL-3.0이고, npm 패키지에는 라이선스 표시가 없어(none) 회사 사용 전 확인이 필요하다. README 배지도 GPL-3.0을 표시한다(MIT는 배지의 대체 텍스트에만 있다). ② 유지보수자가 한 명이고 커밋 간격이 길며 릴리스가 없다. 그 밖에 lightning-* 지원 여부도 확인되지 않았다. (2026-10-09 갱신)

Q5. 역할 분담이 성립하려면 컴포넌트를 어떻게 설계해야 하나?

표현 컴포넌트와 컨테이너 컴포넌트를 분리한다. 표현은 props만 받아 Storybook에서 나열하고, 데이터 조회(@wire, Apex)는 컨테이너가 맡아 Live Preview에서 확인한다.
