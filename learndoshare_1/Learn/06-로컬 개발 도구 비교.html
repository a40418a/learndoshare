LEARN 06 · Phase 7 준비

로컬 개발 도구 비교

LWC를 배포하지 않고 확인하는 방법은 여러 가지다. 각 도구가 무엇을 잘하고 무엇을 못하는지 정리하고, 밀버스에서 어떤 도구를 어디에 쓸지 정한다.

예상 1시간선행: 03 Storybook, 04 통합2026-09-26 공식 문서 · GitHub · npm으로 확인

왜 알아야 하나

밀버스의 주 경로는 Storybook이다 (04 통합). 그런데 발표나 리뷰에서 "Salesforce 공식 도구(Live Preview)가 있는데 왜 Storybook을 따로 쓰나?"라는 질문이 반드시 나온다.

답은 "둘 중 하나"가 아니라 "잘하는 일이 다르다"이다. 이 문서는 그 답의 근거를 모으고, Phase 7 보조 실습에서 직접 비교할 계획을 세운다.

이름부터 헷갈린다"Local Dev"는 Spring '26에 Live Preview로 이름이 바뀌었다. 또 이와 별개로, 예전 "LWC Local Development Server"는 이미 은퇴했다. 블로그 글이 어느 쪽을 말하는지 먼저 확인한다.

후보 네 가지

Live Preview

Salesforce 공식. org에 연결해 실제 데이터로 미리 본다. sf lightning dev

LWC Garden

개인이 만든 오픈소스. LWC용 Storybook 비슷한 도구

Storybook

밀버스 주 경로. org 없이 카탈로그·변형·브랜드를 보여 준다

org 내 문서 앱

org 안에 컴포넌트 문서 페이지를 직접 만든다

Live Preview (구 Local Dev)

Salesforce CLI에 기본 포함된 플러그인 @salesforce/plugin-lightning-dev(2026-09-26 기준 6.2.19)로 동작한다. VS Code 확장도 있다.

명령보는 대상메모
sf lightning dev appLightning 앱데스크톱 또는 -t로 iOS/Android 시뮬레이터
sf lightning dev siteExperience Cloud LWR 사이트사이트를 먼저 게시해야 한다. --ssr는 Spring '26부터 지원 안 함
sf lightning dev component컴포넌트 하나를 단독으로-n 이름, -c 목록에서 선택, -o 대상 org (Winter '26부터 필수)
# 컴포넌트 하나를 org에 연결해 미리 보기
sf lightning dev component -n milvusBadge -o learndoshare_1

# 목록에서 골라 실행
sf lightning dev component -c -o learndoshare_1

준비 조건

  • 처음 실행하면 CLI가 org에서 기능을 켤지 묻는다
  • 권한: View Setup, Customize Application
  • 프로젝트에 lwc 디렉터리가 있어야 한다

베타 여부는 불확실미확인 Summer '25 릴리스 노트와 Winter '26 개발자 블로그는 "Beta"라고 불렀지만, 현재 가이드 페이지에는 Beta 표시가 없다. GA가 됐다는 공식 발표는 찾지 못했으므로 "베타일 수 있다"고 말한다.

은퇴한 Local Development Server

쓰지 않는다예전 도구 @salesforce/lwc-dev-server(LWC Local Development Server)는 2025년 9월 5일에 은퇴했다 (Summer '25 릴리스 노트). 저장소는 2023년에 보관(archived) 처리됐고, VS Code 확장 65.18.0(2026년 2월)에서 관련 명령이 제거됐다.

블로그에 "LWC Local Development Server"나 lwc-dev-server가 나오면 이 도구를 말하는 것이다. 따라 하지 않는다.

LWC Garden

Luke Secomb이 만든 오픈소스 도구다. LWC 컴포넌트를 org 없이 모아 보는, Storybook과 비슷한 목적을 가진다.

Storybook

밀버스 주 경로다. digitalflask 방식으로 LWC를 Storybook에서 렌더한다. 구성은 04 통합에 있다.

잘하는 것

org 없음, 컴포넌트 카탈로그, 한 화면에 여러 상태 나열, 브랜드 전환 툴바, 정적 빌드로 비개발자에게 공유, 접근성 검사

못하는 것

실제 데이터 없음(mock 필요), 진짜 HMR 아님(rollup -w로 다시 빌드 후 새로 고침)

org 내 문서 앱

org 안에 Lightning 앱 페이지를 만들어 컴포넌트를 나열하는 방법이다.

  • 장점: 통합 위험이 0이다. 실제 환경 그대로 보인다
  • 단점: 확인할 때마다 배포해야 한다. props 조작, 코드 보기 같은 문서 기능을 직접 만들어야 한다

Storybook의 시각 회귀는 Storybook 생태계의 별도 도구(테스트 러너, 외부 서비스 등)를 붙여야 한다는 뜻이다. 어떤 도구를 쓸지는 정하지 않았다.

역할 분담 권장

한 줄 결론개발 중 데이터 붙은 확인은 Live Preview, 카탈로그·변형·브랜드·공유·프로젝트 시작은 Storybook. 조건: 표현/컨테이너 분리.
표현 컴포넌트props만 받아 그린다. 예: milvusBadge
→
Storybook모든 상태·브랜드를 나열하고 공유한다
→
컨테이너 컴포넌트@wire, Apex로 데이터를 받아 표현 컴포넌트에 넘긴다
→
Live Preview실제 데이터로 연결을 확인한다
분리가 왜 조건인가표현 컴포넌트 안에 @wire가 섞여 있으면 Storybook에서 그릴 때마다 mock이 필요해지고, 상태 나열이라는 Storybook의 강점이 사라진다. 반대로 분리돼 있으면 표현은 Storybook, 연결은 Live Preview로 깔끔하게 나뉜다.

스스로 점검

Q1. 블로그에 "LWC Local Development Server로 로컬에서 띄우라"고 나온다. 따라 해도 되나?

안 된다. @salesforce/lwc-dev-server는 2025년 9월 5일에 은퇴했다. 지금은 Live Preview(sf lightning dev)를 쓴다.

Q2. Live Preview에서 컴포넌트에 새 @api 속성을 추가했는데 반영되지 않는다. 왜인가?

공개 API가 바뀌는 수정은 HMR 대상이 아니다. 새 @api, @wire 변경, 새 scoped import, .js-meta.xml 수정은 수동 새로 고침이나 배포가 필요하다.

Q3. "공식 도구가 있는데 왜 Storybook을 쓰나?"에 어떻게 답하나?

"잘하는 일이 다릅니다. Live Preview는 org에 붙여 실제 데이터로 확인할 때, Storybook은 org 없이 모든 상태·브랜드를 나열하고 정적 빌드로 비개발자와 공유할 때 씁니다."

Q4. LWC Garden을 주 경로로 쓰지 않는 이유 두 가지는?

① 라이선스가 GPL-3.0이고 README 배지(MIT)와 달라 회사 사용 전 확인이 필요하다. ② 유지보수자가 한 명이고 커밋 간격이 길며 릴리스가 없다. 그 밖에 lightning-* 지원 여부도 확인되지 않았다.

Q5. 역할 분담이 성립하려면 컴포넌트를 어떻게 설계해야 하나?

표현 컴포넌트와 컨테이너 컴포넌트를 분리한다. 표현은 props만 받아 Storybook에서 나열하고, 데이터 조회(@wire, Apex)는 컨테이너가 맡아 Live Preview에서 확인한다.
