Figma to LWC

Figma 디자인을 LWC로 바꾸는 Salesforce 공식 경로(MCP 도구 → experience-lwc-design-generate 스킬)와, 그 안에서 SLDS 참고서 역할을 하는 design-systems-slds-apply 스킬을 공식 문서와 스킬 원문으로 정리한다. 2026-10-30 실습(figma_to_lwc)에서 확인한 것과 밀버스 디자인 시스템과의 관계를 끝에 적는다.

예상 1.5시간선행: 01 SLDS, 08 Claude Code, 09 override2026-10-30 확인 (공식 문서, sf-skills 저장소, Figma 도움말, 실습 기록)

왜 알아야 하나

밀버스 디자인 시스템은 디자이너가 만드는 Figma 구간을 범위 밖으로 두었다. org 테마와 SLDS 기본 컴포넌트 위에 브랜드 색을 입히는 일이 중심이라, Figma 파일을 받아 LWC를 만드는 입구가 없다. 고객이 Figma 디자인 시스템을 갖고 와서 "화면을 그대로 만들어 달라"고 하면 그 입구가 필요하다.

Salesforce는 이 입구를 두 가지 형태로 제공한다. 처음에는 DX MCP 서버의 도구(guide_figma_to_lwc_conversion)였고, 지금은 sf-skills 저장소의 스킬(experience-lwc-design-generate)이 그 자리를 이어받았다. 스킬은 혼자 일하지 않고 형제 스킬 여럿을 순서대로 부르는데, 그중 SLDS 규칙을 맡는 것이 design-systems-slds-apply다. 이 두 가지가 각각 무엇이고, 무엇을 하고 무엇을 하지 않는지 알아야 밀버스를 어디까지 넓힐지 정할 수 있다.

이 문서가 답하는 것

두 스킬의 정체와 범위, Figma를 읽는 두 서버(공식 Figma MCP, Framelink)의 차이와 요금제 한도, SLDS Linter가 잡는 것과 못 잡는 것, 실습 결과, 밀버스와 함께 쓰는 구조

이 문서가 다루지 않는 것

LWC 작성법 자체(02 LWC), hook·블루프린트의 세부(01 SLDS), 플러그인·스킬 구조(08 Claude Code)

Figma to LWC란

공식 문서의 정의는 이렇다. guide_figma_to_lwc_conversion 도구는 SLDS 가이드라인을 제공하고 Figma 디자인을 LWC 명세로 바꾸는 일을 돕는다. 문서는 같은 줄에서 이 MCP 도구가 experience-lwc-design-generate 스킬로 대체되었다(superseded)고 적는다. 즉 "Figma to LWC"라는 이름은 기능 하나가 아니라 MCP 도구 경로와 스킬 경로 두 가지를 가리키고, 지금 권장은 스킬 경로다. 이 문서에서 "MCP 도구"는 Salesforce DX MCP 서버(@salesforce/mcp)의 도구를, "스킬"은 sf-skills 저장소의 SKILL.md 묶음을 뜻한다.

변환 흐름 (MCP 도구 경로)

① 가이드 제공guide_figma_to_lwc_conversion이 SLDS 가이드를 대화에 올린다
→
② Figma 읽기Framelink MCP 서버가 디자인 데이터를 읽어 대화에 싣는다
→
③ 코드 생성create_lwc_component_from_prd가 데이터로 LWC를 만든다
→
④ 검토·테스트사람이 검토하고 sandbox·scratch org에서 확인한다

문서는 ②의 도구를 figma_data_tool이라고 부른다. 지금 npm에 있는 Framelink(figma-developer-mcp)가 실제로 내놓는 도구 이름은 get_figma_data와 download_figma_images다(2026-10-30, 이 저장소에 연결한 서버의 도구 목록으로 확인). 이름이 다르지만 역할은 같다. 프롬프트는 세 가지를 예로 든다. "Convert this Figma design to LWC", "Extract design tokens such as for spacing, color, radius, and typography from Figma and map them to SLDS variables", "Generate an LWC component breakdown and file scaffold plan from this Figma frame". 셋 다 Figma 파일 링크를 뒤에 붙인다.

experience-lwc-design-generate 스킬 자세히

sf-skills 저장소(Apache-2.0)의 스킬이다. 저장소는 같은 스킬을 두 곳에 둔다. skills/ 아래 단독 스킬과 plugins/builder/experience-lwc/skills/ 아래 플러그인 묶음이다. 실습에서 쓴 것은 플러그인 experience-lwc 0.3.0(2026-10-16)이고, 스킬 자체의 version은 1.0이다. 스킬 정의는 자신을 "top-level workflow skill"이라고 부른다. 각 단계를 맡는 형제 스킬을 순서대로 부르는 지휘자이지, 코드를 직접 쓰는 스킬이 아니다.

다섯 단계와 담당

단계스킬이 직접 하는 것넘기는 형제 스킬산출물

완료 기준 11항목 (Definition of Done)

스킬은 이 목록을 PR 설명에 그대로 복사하라고 한다. 실습 기록(slackMessageBox TEST-RECORD)도 이 11항목으로 채웠다.

  1. PRD 요구사항은 모두 구현되거나, 추적 항목이 연결된 TODO:로 남는다
  2. 운영 경로에 TODO·FIXME·console.log·alert()가 없다
  3. 주석 처리된 코드, 빈 함수, 자리표시 값, 더미 데이터, 안 쓰는 import가 없다
  4. lwc:dom="manual"이나 서드파티 우회는 이유 주석 없이는 없다
  5. .js-meta.xml의 AI 메타데이터(<ai><description>와 @api마다 aiDescription)가 감사를 통과한다
  6. SLDS 스타일이 design-systems-slds-apply 검증을 통과한다. 직접 hex·px 값이 없다
  7. 접근성: 소스 리뷰와 자동 Jest 둘 다 통과
  8. 보안(LWS)과 RTL 리뷰 통과
  9. 모든 wire·명령형 호출이 PRD 데이터 절에 적혀 있고 승인된 LDS 어댑터와 맞는다
  10. Jest가 프로젝트 커버리지 기준을 넘고, 모든 @api·이벤트·오류 경로를 덮는다
  11. 브라우저 수준 교차 컴포넌트 흐름이 있으면 UTAM 페이지 객체 (없으면 생략)
실측에서 찾은 정의 문서의 빈틈참고 파일 references/prd-analysis-template.md는 PRD 양식이 아니라 SARIF 검사 보고서 프롬프트다(실습 발견 1). PRD 구성은 figma-to-prd-blueprint.md로 대신했다. 또 5항의 <ai> 요소 스키마는 스킬 문서에서 찾지 못해 실습에서 넣지 못했다. 정의가 "하라"고 적은 것과 실제로 가능한 것 사이에 틈이 있으니, 완료 기준은 그대로 믿지 말고 항목마다 근거를 남긴다.

하지 않는 것

  • 기존 LWC 리팩터링(experience-lwc-generate), Aura 제자리 이관, SLDS 토큰만 다루는 일(design-systems-slds-apply), 데이터 계층만 다루는 일(experience-lds-*)에는 쓰지 말라고 정의에 적혀 있다
  • Figma를 직접 읽지 않는다. Phase 1.2의 입력은 "사용자가 주는" URL·스크린샷·메타데이터다. MCP 서버가 없으면 사람이 붙여 넣어야 한다
  • org 테마나 브랜드를 적용하지 않는다. 컴포넌트 하나가 단위다

design-systems-slds-apply 스킬 자세히

같은 sf-skills 저장소의 단독 스킬이다(version 1.1, SLDS 2 대상). experience-lwc 플러그인에는 들어 있지 않고 저장소 skills/ 아래에만 있다. 실습에서 "플러그인에 빠져 있어 따로 복사해 넣었다"고 기록한 이유가 이것이다. 공식 설치 경로는 npx skills add forcedotcom/sf-skills(단독 스킬 설치)이고, SLDS 2 AI Starter Kit에는 미리 들어 있다. 정체는 SLDS 참고서다. 스킬 정의의 첫 문장이 "SLDS는 수천 개의 산출물을 가진 CSS 프레임워크이고, 이 스킬은 에이전트가 그것을 찾아 올바르게 쓰는 법을 가르친다"이다.

결정 계층과 규칙

① Lightning 기본 컴포넌트LWC면 먼저 Component Library에서 찾는다
→
② SLDS 블루프린트정확한 SLDS 클래스로 마크업
→
③ hook으로 직접 CSSvar(--slds-g-*, fallback)
→
④ 커스텀 CSS마지막 수단. 값은 여전히 hook

하라

계층을 따른다. 테마에 걸리는 값은 모두 var(--slds-g-*, fallback). .slds-*를 덮지 말고 my-*·c-* 클래스를 만든다. hook·클래스·아이콘은 쓰기 전에 스크립트로 존재를 확인한다. surface 색과 on-surface 색을 짝지운다. lightning-icon마다 alternative-text

하지 마라

색·간격·글꼴 직접 값. .slds-* 재정의. --lwc-* 레거시 토큰을 주 값으로. --slds-s-*(공유 hook, 내부용). hook 값 재할당(읽기만). 색만으로 의미 전달. 다른 계열의 이름 패턴을 보고 hook 이름을 지어내기

이름 함정 세 가지

글꼴 크기는 번호가 없다(--slds-g-font-size-3 없음, --slds-g-font-scale-*). 색 hook은 반드시 번호가 붙는다(--slds-g-color-on-surface 없음, -2). 모든 값에 hook이 있지는 않다(min-width: 7rem 같은 것은 주석과 함께 직접 값)

작성 절차와 검증

절차는 다섯 단계다. ① 필요 파악(패턴, 프레임워크, 데이터, 상태) ② 산출물 선택(기본 컴포넌트 → 블루프린트 검색 → YAML 읽기 → 없으면 hook) ③ 스타일(색 역할 분류 → hook, 간격·배치는 유틸리티) ④ 아이콘 ⑤ 검증. 검증은 "필수, 건너뛰지 말 것"으로 표시돼 있고 네 단계다.

  1. npx @salesforce-ux/slds-linter@latest lint <component-path>. 위반 0이 목표이고, 위반을 "허용 가능"으로 합리화하지 말라고 적혀 있다
  2. 생성한 모든 --slds-g-*가 hooks-index.json에 있는지 확인 (지어낸 hook 금지)
  3. checklists.md로 Linter가 못 잡는 것 확인: fallback 유무(T002), surface·accent·feedback 색 짝(T010~T013), 간격의 px(T020~T021), font-scale(T031), 아이콘 대체 텍스트(A004), 클래스 접두사(Q010)
  4. (선택) design-systems-slds-validate로 점수 보고서. B(80점) 이상이 목표

범위 밖과 관점

  • 디자인 결정(시각 위계, 구성, 상호작용 패턴), LWC 동작(@wire·@api·수명주기), 전체 접근성(WCAG·ARIA·키보드·대비)은 다른 스킬 몫이라고 정의에 적혀 있다
  • 관점은 "SLDS 안에서 가장 가까운 것을 고르라"다. SLDS 의미 hook(surface, on-surface 등)은 Salesforce 색 체계이지 고객 디자인의 색이 아니다. 실습에서 --slds-g-color-on-surface-3이 남색 #03234d인 것을 이 스킬의 search-hooks.cjs로 확인했고, Slack 글자색 #1D1C1D를 거기에 대응시키면 Figma와 다른 색이 나온다는 것을 알았다(실습 발견). Figma를 그대로 따르려는 프로젝트에서는 이 관점이 충돌한다(밀버스와의 관계)
  • Linter 가이드는 이 스킬을 "custom instructions와 섞으면 에이전트가 Linter 단계를 건너뛸 수 있으니 단독으로 쓰라"고 경고한다

Figma 읽기 도구: 공식 Figma MCP와 Framelink

Figma를 읽는 서버는 둘이다. Salesforce 문서가 안내하는 것은 Framelink이고, Figma가 직접 제공하는 것은 공식 Figma MCP 서버다. 실습에서는 둘 다 썼다. 어느 쪽이든 한도는 Figma 요금제와 좌석에 걸린다.

항목공식 Figma MCP 서버Framelink (figma-developer-mcp)
제공자Figma. remote(https://mcp.figma.com/mcp, 권장)와 desktop(앱 Dev Mode에서 켬, http://127.0.0.1:3845/mcp) 두 가지서드파티 오픈소스(GLips/Figma-Context-MCP, MIT). Salesforce 제품이 아니다
인증OAuth 브라우저 로그인. Claude Code는 claude plugin install figma@claude-plugins-official 또는 claude mcp add --transport http figma https://mcp.figma.com/mcpFigma personal access token(file_content:read 범위면 충분). 명령줄 인자나 FIGMA_API_KEY 환경 변수로 전달
읽기 도구get_design_context(디자인 컨텍스트와 코드), get_metadata(가벼운 XML 윤곽), get_screenshot, get_variable_defs(변수·스타일), download_assets(remote 전용) 등get_figma_data(레이아웃·채우기·글꼴·변수 이름을 줄인 JSON), download_figma_images
쓰기use_figma, generate_figma_design 등 remote 전용. 초안 밖에 쓰려면 Full 좌석없음 (읽기 전용)
한도읽기 도구에 적용. View·Collab 좌석은 모든 플랜에서 월 20회. Full·Dev 좌석은 Professional 하루 200회·분당 10회, Organization 하루 200회·분당 15회, Enterprise 하루 600회·분당 20회. Starter의 Full·Dev는 표에 값이 없다Figma REST API 한도와 같다. 좌석 종류·엔드포인트 등급·파일이 속한 플랜에 따라 달라지고, View·Collab 좌석은 파일·노드·이미지 GET(1등급)이 월 20회. 넘으면 429와 Retry-After(초)
토큰 관리토큰을 직접 다루지 않는다설정 파일에 평문으로 남는다. Salesforce 문서도 "Figma 토큰이 외부 npm 패키지에 전달된다"는 뜻의 보안 검토 필요성을 암시하고, 실습에서 토큰이 대화에 여러 번 올라왔다
실습에서 겪은 한도 (2026-10-30)공식 Figma MCP는 아이콘을 하나씩 받다가 약 12번째 호출에서 Starter 플랜 한도 응답을 받았다. Framelink는 컴포넌트 세트 2개를 읽은 직후 429와 함께 392,229초(약 4.5일) 뒤 재시도하라는 응답을 받았고, "Viewer/Collaborator 좌석은 한도가 낮다"는 설명이 따라왔다. 공식 한도 표와 맞는다. View·Collab 좌석은 실사용이 어렵고, 실무 전제는 Dev 또는 Full 좌석이다. 호출 단위도 중요하다. 페이지 구조는 get_metadata 한 번으로 받되 이름·크기·위치만 있고 색과 글꼴은 없다. 컴포넌트 세트 하나를 읽으면 변형 전체(버튼 9개)가 한 번에 온다. 받은 데이터는 파일로 저장해 다시 쓴다.

Framelink에서 Windows는 "command": "cmd"와 ["/c", "npx", ...] 래퍼가 필요하다(README가 Windows 설정을 따로 적는다). 실습에서는 npx가 매번 패키지를 받아 30초 연결 시간 초과가 났고 전역 설치로 해결했다. MCP 연결이 끊긴 세션에서는 figma-developer-mcp의 명령줄로 같은 데이터를 읽었다(실습 기록, README에는 없는 기능이라 버전에 따라 다를 수 있다).

SLDS Linter: 잡는 것과 못 잡는 것

SLDS Linter(@salesforce-ux/slds-linter)는 코드를 SLDS 2 규칙에 견주는 npm 패키지다. HTML·CMP·CSS 파일만 본다. design-systems-slds-apply는 이것을 필수 검증 단계로 돌리고, design-systems-slds-validate는 Linter 결과를 점수의 30%로 쓴다(100 − 10×오류 − 5×경고). lint --fix는 확신이 높은 위반을 자동으로 고친다.

규칙심각도잡는 것
no-hardcoded-values-slds2경고색·배경·테두리·여백·크기·그림자·글꼴 속성의 직접 값. hook을 넣고 직접 값은 fallback으로 남기라고 제안
no-slds-var-without-fallback오류fallback 없는 var(--slds-*). 메타데이터에서 fallback 값을 제안
no-slds-class-overrides경고선택자 끝의 .slds-* 재정의
lwc-token-to-slds-hook, no-sldshook-fallback-for-lwctoken오류, 경고레거시 --lwc-* 토큰
no-unsupported-hooks-slds2, no-slds-private-var, no-slds-namespace-for-custom-hooks경고SLDS 2에 없는 hook, 내부용 --_slds-*, 커스텀 변수에 --slds·--sds 접두사
no-deprecated-classes-slds2, enforce-bem-usage, modal-close-button-issue오류SLDS 2에서 빠진 클래스, -- BEM, 모달 닫기 버튼 변형
실측: Linter만으로는 "직접 값 없음"을 보장하지 못한다① hook 변수에 넣은 직접 색은 경고 없이 통과한다. --slds-c-button-brand-color-background: #007a5a가 그 예다. no-hardcoded-values-slds2는 color·background 같은 속성만 보고, 커스텀 속성 정의는 보지 않는다. ② --fix가 fallback에 hex·rem을 넣는다. fallback 규칙과 "직접 값 금지"가 서로 당긴다. 그래서 실습 스킬은 grep -nE "#[0-9a-fA-F]{3,8}\b"로 따로 보도록 했고, 밀버스에는 컴포넌트 CSS의 직접 값 검사를 check에 넣는 일을 남겼다(밀버스와의 관계).

실습이 말해 주는 것생성 자체는 됐다. 품질을 가른 것은 도구가 아니라 입력(Figma에 상태·변수·레이아웃이 있는가)과 관문(직접 값·접근성·org 렌더를 누가 어떻게 확인하는가)이었다. 그리고 "Figma대로"와 "SLDS 기본 컴포넌트 우선"은 프로젝트마다 먼저 골라야 하는 선택이지 도구가 정해 주는 것이 아니다.

스스로 점검

Q1. "Figma to LWC MCP 도구를 설치해서 쓰라"는 문서를 받았다. 그대로 따르면 되나?

공식 문서가 그 MCP 도구(guide_figma_to_lwc_conversion)는 experience-lwc-design-generate 스킬로 대체됐다고 적는다. 스킬 경로를 기본으로 하고, MCP 도구 경로는 프롬프트와 호출 순서만 다른 이전 형태로 본다. 둘 다 Figma를 읽는 일은 Framelink나 공식 Figma MCP 서버가 한다.

Q2. design-systems-slds-apply가 플러그인에 없다. 플러그인이 깨진 건가?

아니다. 이 스킬은 sf-skills의 skills/ 아래 단독 스킬이고 experience-lwc 플러그인에 포함되지 않는다. npx skills add forcedotcom/sf-skills로 설치하거나 프로젝트 .claude/skills/에 복사한다.

Q3. Framelink로 컴포넌트 두 개를 읽자마자 429가 났다. 서버 버그인가?

Figma REST API 한도다. View·Collab 좌석은 파일·노드·이미지 읽기가 월 20회이고, Retry-After가 며칠 단위로 올 수 있다. 공식 Figma MCP도 같은 좌석 기준(월 20회)이다. 실무 전제는 Dev 또는 Full 좌석이고, 읽는 단위를 세트로 키우고 받은 데이터를 저장해 다시 쓴다.

Q4. SLDS Linter가 0건인데 CSS에 #007a5a가 있다. 왜 못 잡았나?

no-hardcoded-values-slds2는 color·background 같은 속성의 값만 보고, --slds-c-*: #007a5a처럼 커스텀 속성 정의에 넣은 값은 보지 않는다. 그래서 "직접 값 없음"은 Linter만으로 보장되지 않고, 밀버스 check에 컴포넌트 CSS 검사를 더하는 일(#94)이 남아 있다.

Q5. 스킬의 SLDS 결정 계층은 기본 컴포넌트가 1순위인데, 실습 규칙은 Figma 부품을 직접 만든다. 어느 쪽이 맞나?

둘 다 맞고, 프로젝트 시작 때 고르는 문제다. 기본 모드는 접근성·보안·업데이트를 Salesforce가 맡고, Figma 충실 모드는 화면이 Figma와 같다. 밀버스는 기본 모드를 기본값으로 두고 Figma 충실 모드를 선택지로 더한다(#95). 어느 모드든 직접 값은 한 곳에만, 컴포넌트 목록, check 통과는 같다.

Q6. 밀버스가 Figma 입력을 받으려면 무엇부터 해야 하나?

Figma 작성 규칙 문서(#92) → 역할 이름 토큰 층 설계안(#93) → 컴포넌트 CSS 직접 값 검사(#94) → 충실도 모드(#95) 순서다. 2번이 "값을 둘 수 있는 곳"을 정해야 3번이 위반을 판정할 수 있고, 1~3이 있어야 4번의 Figma 충실 모드도 같은 관문을 통과한다.
