pnpm 핵심 정리

밀버스는 pnpm만 쓴다. npm에 익숙한 사람이 pnpm에서 걸리는 지점, 특히 Storybook을 설치할 때 문제가 되는 부분을 중심으로 정리한다.

예상 1시간2026-10-09 기준 pnpm 최신 12.10.1로컬 설치 10.13.1 · Node 24.4.1

왜 pnpm인가

디스크 절약

패키지를 전역 저장소(content-addressable store)에 한 번만 저장하고, 프로젝트에는 하드 링크로 연결한다.

엄격함

최상단 node_modules에는 직접 선언한 패키지만 링크된다. 그래서 package.json에 선언하지 않은 패키지는 import할 수 없다. "우연히 되던 코드"가 사라진다.

보안 기본값

10부터 의존성의 설치 스크립트(postinstall)를 기본으로 실행하지 않는다.

규칙npm, yarn, npx 명령은 쓰지 않는다. 블로그나 공식 문서 예제에 npx가 나오면 아래 대응표로 바꿔 실행한다.

출처: pnpm — Motivation (확인 2026-10-09) · pnpm — Mitigating supply chain attacks (확인 2026-10-09)

node_modules 구조

npm은 모든 의존성을 node_modules 최상단에 평평하게 펼친다(hoisting). pnpm은 직접 선언한 패키지만 최상단에 심볼릭 링크로 두고, 실제 파일은 node_modules/.pnpm/ 아래에 둔다. 그 파일도 저장소로 이어진 하드 링크다.

node_modules/
├── storybook -> .pnpm/storybook@10.6.0/node_modules/storybook   ← 내가 선언한 것만 보인다
├── lwc -> .pnpm/lwc@9.4.3/node_modules/lwc
└── .pnpm/
    ├── storybook@10.6.0/node_modules/...
    ├── node_modules/        ← 숨겨진 hoist 영역 (hoistPattern: ['*'])
    └── ...
설정기본값의미
nodeLinkerisolated위와 같은 심볼릭 링크 구조
hoistPattern['*']숨겨진 영역(.pnpm/node_modules)으로 끌어올림. 내 코드에서는 안 보인다
publicHoistPattern[]최상단 node_modules로 끌어올릴 패턴. 도구가 hoisting을 전제할 때 쓴다
shamefullyHoistfalsetrue면 npm처럼 전부 펼침 (publicHoistPattern을 *로 둔 것과 같음)

publicHoistPattern의 기본값이 빈 목록이라 eslint와 prettier도 최상단에 올리지 않는다. 이 기본값은 pnpm 10.0.0에서 바뀌었다(10.0.0 릴리스 노트).

버전별 차이 (10 / 11+)

인터넷 자료 대부분은 pnpm 8~10 기준이다. 11부터 설정 위치와 빌드 승인 방식이 바뀌었으므로 자료를 볼 때 버전을 꼭 확인한다.

항목pnpm 10pnpm 11 이상 (최신 12.x)
설정 파일.npmrc, pnpm-workspace.yaml 둘 다 읽음.npmrc는 인증·레지스트리만. 나머지는 pnpm-workspace.yaml(camelCase). package.json의 pnpm 필드는 읽지 않는다
의존성 빌드 스크립트기본 미실행. 승인 목록 onlyBuiltDependencies (10.26부터 allowBuilds도 있음)기본 미실행. 승인 목록 allowBuilds (onlyBuiltDependencies 삭제)
미승인 빌드가 있으면경고만 (strictDepBuilds: false)설치 실패 (strictDepBuilds: true)
새로 나온 버전 설치제한 없음 (10.16에 생긴 minimumReleaseAge의 기본값 0)minimumReleaseAge 기본 1440분(1일). 나온 지 하루가 안 된 버전은 설치하지 않는다
Node 요구18+11은 22+. 12는 18+이고, npm으로 설치했을 때만 Node가 필요하다
환경 변수npm_config_*pnpm_config_*
결정 필요로컬에는 10.13.1이 설치돼 있고 package.json의 packageManager도 pnpm@10.13.1이다. 팀 표준 버전(10 / 12)은 아직 미정이다(README 6장). Node는 24.4.1이라 어느 쪽 요구도 충족한다. 새로 시작하는 프로젝트라 최신 메이저로 맞추는 쪽이 이후 문서와 차이가 적다.

빌드 스크립트 승인

pnpm 10부터 의존성의 postinstall 같은 설치 스크립트는 기본으로 실행되지 않는다. 악성 패키지가 설치만으로 코드를 실행하는 공격을 막기 위해서다.

  • Storybook/Vite를 설치하면 esbuild 같은 패키지가 "빌드 스크립트 무시됨" 목록에 뜰 수 있다. 우리 package.json에도 esbuild를 승인해 두었다
  • pnpm approve-builds를 실행해 필요한 것만 승인한다
  • 내 프로젝트 자신의 prepare/postinstall(예: husky)은 계속 실행된다. 막히는 것은 의존성의 스크립트다. 프로젝트 스크립트까지 끄는 것은 별도 설정 ignoreScripts(기본 false)다 (pnpm 10.13.1에서 실험으로도 확인)
allowBuilds:
  esbuild: true
"pnpm": {
  "onlyBuiltDependencies": ["esbuild"]
}
pnpm 11 이상에서는 설치가 멈춘다미승인 빌드가 있으면 경고가 아니라 오류로 설치가 중단된다(strictDepBuilds 기본 true). 당황하지 말고 pnpm approve-builds로 승인하고 다시 설치한다.

hoisting 문제 해결

일부 도구는 npm처럼 모든 패키지가 최상단에 있다고 가정하고 만들어졌다. pnpm에서는 이런 도구가 "모듈을 찾을 수 없음" 오류를 낸다. Storybook은 9에서 여러 패키지를 핵심 패키지 storybook 하나로 합쳐 선언할 패키지가 줄었다. 애드온에서도 이 오류가 나는지는 미확인이다.

해결 순서 (좁은 것부터)

  1. 오류 메시지에 나온 패키지를 직접 pnpm add -D로 선언한다 (가장 정석)
  2. 안 되면 해당 패턴만 최상단으로 올린다 
    public-hoist-pattern[]=*storybook*
    publicHoistPattern:
  - "*storybook*"
  3. 최후 수단: shamefullyHoist: true. pnpm의 엄격함을 포기하는 것이라 쓰지 않는 것을 목표로 한다

pnpm 10.13.1은 두 형식을 모두 읽는다(pnpm config get으로 로컬 확인). 11부터는 .npmrc의 이 설정을 읽지 않는다.

원칙설정은 실제로 깨졌을 때만 추가한다. 미리 넣어 두면 무엇 때문에 넣었는지 아무도 모르게 된다.

버전 고정과 lockfile

  • pnpm-lock.yaml은 반드시 커밋한다. 모두 같은 버전을 설치하게 된다
  • package-lock.json, yarn.lock은 .gitignore에 넣는다. 섞여 있으면 누군가 npm을 썼다는 신호다
  • pnpm 버전 고정: 최신 문서는 packageManager 필드를 "legacy"로 부른다. pnpm 11부터 쓸 수 있는 devEngines.packageManager는 범위를 지정할 수 있다
{
  "devEngines": {
    "packageManager": { "name": "pnpm", "version": ">=12.0.0 <13.0.0", "onFail": "download" }
  },
  "engines": { "node": ">=22" }
}

예시는 pnpm 문서의 형식을 따랐고 버전은 결정 전 자리표시자다. 팀이 정한 버전으로 바꾼다. 패키지 설계는 engines.node를 ^22.18.0 || >=23.6.0으로 바꿀 계획이다(설계 2장).

alpha 패키지는 정확한 버전으로lightning-base-components는 latest 태그가 1.28.19-alpha다. pnpm add -D -E lightning-base-components처럼 -E로 정확히 고정하고, 올릴 때는 명시적으로 올린다.

husky와 pnpm

husky hook 파일 안에서도 npm/npx를 쓰지 않는다.

cd learndoshare_1 && pnpm exec lint-staged
현재 hook이 동작하지 않는 이유git 루트는 상위 폴더 learndoshare/인데 package.json은 learndoshare_1/에 있다. husky 9.1.7은 현재 폴더에 .git이 없으면 설치하지 않고 ".git can't be found"를 돌려준다. prepare: "husky || true"라서 이 실패가 조용히 넘어간다. husky 문서의 "Project not in Git root directory" 방식대로 prepare를 cd .. && husky learndoshare_1/.husky로 바꿔야 한다(husky How To). Phase 1에서 처리한다. 2026-10-09 기준 .husky/pre-commit은 아직 npm run precommit이다.

GitHub Packages에서 설치 계획

밀버스는 CLI·템플릿·LWC·Storybook을 패키지 하나(@a40418a/milvus-design-system)에 담아 GitHub Packages에 비공개로 발행할 계획이다(설계 2장). 아직 발행 전이다.

  • GitHub Packages의 npm 레지스트리는 범위가 있는 이름(@NAMESPACE/PACKAGE-NAME)만 받는다
  • 설치에도 토큰이 필요하다. 공개 패키지도 마찬가지다. 토큰은 personal access token (classic)만 되고, 설치하려면 read:packages 권한이 있어야 한다
  • 레지스트리와 토큰은 .npmrc에 둔다. pnpm 11 이상에서도 .npmrc에 남는 인증·레지스트리 설정이다
  • 발행할 때는 package.json의 publishConfig.registry에 레지스트리를 적고, GitHub Actions에서는 GITHUB_TOKEN으로 발행한다
@a40418a:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
토큰은 파일에 쓰지 않는다토큰 값은 셸 환경 변수 NODE_AUTH_TOKEN에 두고 .npmrc에는 ${NODE_AUTH_TOKEN}만 쓴다. pnpm 11.5.3부터는 프로젝트 .npmrc의 ${...}를 풀지 않는다. 저장소에 딸려 온 파일이 토큰을 다른 레지스트리로 보내지 못하게 하려는 것이다. 그래서 토큰 줄은 사용자 파일 ~/.npmrc에 둔다. 레지스트리 줄처럼 값이 고정된 줄은 프로젝트 .npmrc에 둘 수 있다. 우리가 쓰는 pnpm 10.13.1에서 프로젝트 .npmrc의 치환이 되는지는 미확인이다(설계 14장, 10/12 확인 예정).

workspace는 쓰지 않는다 (2026-10-09 갱신). 이전 문서는 두 번째 프로젝트가 붙으면 토큰·컴포넌트·Storybook을 workspace 패키지로 나눈다고 적었다. 설계는 프로젝트에 추가되는 의존성을 하나로 두려고 패키지 하나로 정했다.

스스로 점검

Q1. 블로그에 npx storybook add @storybook/addon-a11y라고 나온다. 어떻게 실행하나?

Storybook이 이미 설치돼 있으므로 pnpm exec storybook add @storybook/addon-a11y.

Q2. Storybook 설치 후 "Ignored build scripts: esbuild"가 떴다. 무엇을 해야 하나?

pnpm approve-builds로 esbuild를 승인한다. pnpm 11 이상이면 승인 전까지 설치가 실패한다.

Q3. "Cannot find module"이 나서 shamefullyHoist를 켜려고 한다. 그 전에 할 일은?

1) 그 패키지를 직접 pnpm add -D로 선언, 2) 안 되면 publicHoistPattern으로 좁게 올리기. shamefullyHoist는 최후 수단이다.

Q4. pnpm 12에서 .npmrc에 public-hoist-pattern을 넣었는데 효과가 없다. 왜?

11부터 .npmrc는 인증·레지스트리 설정만 읽는다. pnpm-workspace.yaml에 publicHoistPattern으로 넣어야 한다.

Q5. husky의 prepare는 의존성 빌드 스크립트 차단에 걸리나?

걸리지 않는다. 차단 대상은 의존성의 스크립트이고, 루트 프로젝트 자신의 prepare는 실행된다.

Q6. 밀버스 패키지 설치가 GitHub Packages 인증 오류로 실패한다. 공개 저장소인데 토큰이 왜 필요한가?

GitHub Packages의 npm 레지스트리는 공개 패키지라도 설치에 토큰이 필요하다. read:packages 권한의 personal access token (classic)을 NODE_AUTH_TOKEN에 넣고, 토큰 줄은 ~/.npmrc에 둔다.
