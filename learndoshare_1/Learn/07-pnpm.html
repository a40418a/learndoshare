pnpm 핵심 정리

밀버스는 pnpm만 쓴다. npm에 익숙한 사람이 pnpm에서 걸리는 지점, 특히 Storybook을 설치할 때 문제가 되는 부분을 중심으로 정리한다.

예상 1시간2026-09-26 기준 pnpm 최신 12.6.0로컬 설치 10.13.1 · Node 24.4.1

왜 pnpm인가

디스크 절약

패키지를 전역 저장소(content-addressable store)에 한 번만 저장하고, 프로젝트에는 하드 링크로 연결한다.

엄격함

package.json에 선언하지 않은 패키지는 import할 수 없다. "우연히 되던 코드"가 사라진다.

보안 기본값

10부터 의존성의 설치 스크립트(postinstall)를 기본으로 실행하지 않는다.

규칙npm, yarn, npx 명령은 쓰지 않는다. 블로그나 공식 문서 예제에 npx가 나오면 아래 대응표로 바꿔 실행한다.

node_modules 구조

npm은 모든 의존성을 node_modules 최상단에 평평하게 펼친다(hoisting). pnpm은 직접 선언한 패키지만 최상단에 심볼릭 링크로 두고, 실제 파일은 node_modules/.pnpm/ 아래에 둔다.

node_modules/
├── storybook -> .pnpm/storybook@10.6.0/node_modules/storybook   ← 내가 선언한 것만 보인다
├── lwc -> .pnpm/lwc@9.4.3/node_modules/lwc
└── .pnpm/
    ├── storybook@10.6.0/node_modules/...
    ├── node_modules/        ← 숨겨진 hoist 영역 (hoistPattern: ['*'])
    └── ...
설정기본값의미
nodeLinkerisolated위와 같은 심볼릭 링크 구조
hoistPattern['*']숨겨진 영역(.pnpm/node_modules)으로 끌어올림. 내 코드에서는 안 보인다
publicHoistPattern[]최상단 node_modules로 끌어올릴 패턴. 도구가 hoisting을 전제할 때 쓴다
shamefullyHoistfalsetrue면 npm처럼 전부 펼침 (publicHoistPattern: ['*']와 같음)

pnpm 10부터는 eslint와 prettier도 기본으로 최상단에 올리지 않는다.

버전별 차이 (10 / 11+)

인터넷 자료 대부분은 pnpm 8~10 기준이다. 11부터 설정 위치와 빌드 승인 방식이 바뀌었으므로 자료를 볼 때 버전을 꼭 확인한다.

항목pnpm 10pnpm 11 이상 (최신 12.x)
설정 파일.npmrc, pnpm-workspace.yaml 둘 다 읽음.npmrc는 인증·레지스트리만. 나머지는 pnpm-workspace.yaml(camelCase)
의존성 빌드 스크립트기본 미실행. 승인 목록 onlyBuiltDependencies기본 미실행. 승인 목록 allowBuilds (onlyBuiltDependencies 삭제)
미승인 빌드가 있으면경고만 (strictDepBuilds: false)설치 실패 (strictDepBuilds: true)
새로 나온 버전 설치제한 없음minimumReleaseAge 기본 1일. 24시간 안에 나온 버전은 설치를 막는다
Node 요구18+22+
환경 변수npm_config_*pnpm_config_*
결정 필요로컬에는 10.13.1이 설치돼 있다. Node는 24.4.1이라 11 이상의 요구(22+)도 충족한다. 팀 표준 버전을 정해 package.json에 고정해야 한다 (README Phase 1). 새로 시작하는 프로젝트라 최신 메이저로 맞추는 쪽이 이후 문서와 차이가 적다.

명령어 대응표

하고 싶은 일npm (쓰지 않음)pnpm
의존성 설치npm installpnpm install
개발 의존성 추가npm i -D rolluppnpm add -D rollup
정확한 버전으로 추가npm i -E pkgpnpm add -E pkg
스크립트 실행npm run storybookpnpm storybook (또는 pnpm run storybook)
설치된 CLI 실행npx rollup -cpnpm exec rollup -c
설치 없이 일회성 실행npx create-xpnpm dlx create-x
프로젝트 생성기npm create storybook@latestpnpm create storybook@latest
패키지 정보 조회npm view lwc versionpnpm view lwc version

pnpm exec는 프로젝트에 설치된 실행 파일(node_modules/.bin)을 쓴다. pnpm dlx는 패키지를 임시로 받아 실행한다. 헷갈리면 "설치했으면 exec, 안 했으면 dlx"로 기억한다.

빌드 스크립트 승인

pnpm 10부터 의존성의 postinstall 같은 설치 스크립트는 기본으로 실행되지 않는다. 악성 패키지가 설치만으로 코드를 실행하는 공격을 막기 위해서다.

  • Storybook/Vite를 설치하면 esbuild 같은 패키지가 "빌드 스크립트 무시됨" 목록에 뜰 수 있다
  • pnpm approve-builds를 실행해 필요한 것만 승인한다
  • 내 프로젝트 자신의 prepare/postinstall(예: husky)은 계속 실행된다 (pnpm 10.13.1에서 실험으로 확인)
allowBuilds:
  esbuild: true
"pnpm": {
  "onlyBuiltDependencies": ["esbuild"]
}
pnpm 11 이상에서는 설치가 멈춘다미승인 빌드가 있으면 경고가 아니라 오류로 설치가 중단된다. 당황하지 말고 pnpm approve-builds로 승인하고 다시 설치한다.

hoisting 문제 해결

일부 도구는 npm처럼 모든 패키지가 최상단에 있다고 가정하고 만들어졌다. pnpm에서는 이런 도구가 "모듈을 찾을 수 없음" 오류를 낸다. Storybook 6~7 시절에 자주 보고됐다. 9~10은 패키지가 storybook 하나로 통합돼 크게 줄었지만, 애드온에서 여전히 생길 수 있다.

해결 순서 (좁은 것부터)

  1. 오류 메시지에 나온 패키지를 직접 pnpm add -D로 선언한다 (가장 정석)
  2. 안 되면 해당 패턴만 최상단으로 올린다 
    public-hoist-pattern[]=*storybook*
    publicHoistPattern:
  - "*storybook*"
  3. 최후 수단: shamefullyHoist: true. pnpm의 엄격함을 포기하는 것이라 쓰지 않는 것을 목표로 한다
원칙설정은 실제로 깨졌을 때만 추가한다. 미리 넣어 두면 무엇 때문에 넣었는지 아무도 모르게 된다.

버전 고정과 lockfile

  • pnpm-lock.yaml은 반드시 커밋한다. 모두 같은 버전을 설치하게 된다
  • package-lock.json, yarn.lock은 .gitignore에 넣는다. 섞여 있으면 누군가 npm을 썼다는 신호다
  • pnpm 버전 고정: 최신 문서는 packageManager 필드를 "legacy"로 부르고 devEngines.packageManager를 권장한다 (범위 지정 가능)
{
  "devEngines": {
    "packageManager": { "name": "pnpm", "version": "^12.0.0", "onFail": "error" }
  },
  "engines": { "node": ">=22" }
}

예시의 버전은 결정 전 자리표시자다. 팀이 정한 버전으로 바꾼다.

alpha 패키지는 정확한 버전으로lightning-base-components는 latest 태그가 1.28.19-alpha다. pnpm add -D -E lightning-base-components처럼 -E로 정확히 고정하고, 올릴 때는 명시적으로 올린다.

husky와 pnpm

husky hook 파일 안에서도 npm/npx를 쓰지 않는다.

cd learndoshare_1 && pnpm exec lint-staged
현재 hook이 동작하지 않는 이유git 루트는 상위 폴더 learndoshare/인데 package.json은 learndoshare_1/에 있다. prepare: "husky"는 현재 폴더에서 .git을 찾으므로 실패하고, || true 때문에 조용히 넘어간다. prepare를 cd .. && husky learndoshare_1/.husky로 바꿔야 한다. Phase 1에서 처리한다.

workspace (나중에)

지금은 단일 패키지로 시작한다. 두 번째 프로젝트가 붙어서 토큰, 컴포넌트, Storybook을 나눌 때 workspace로 전환한다.

packages:
  - packages/*

workspace 안의 패키지끼리는 "@milvus/tokens": "workspace:*"처럼 참조한다. 배포할 때는 실제 버전 번호로 바뀐다.

스스로 점검

Q1. 블로그에 npx storybook add @storybook/addon-a11y라고 나온다. 어떻게 실행하나?

Storybook이 이미 설치돼 있으므로 pnpm exec storybook add @storybook/addon-a11y.

Q2. Storybook 설치 후 "Ignored build scripts: esbuild"가 떴다. 무엇을 해야 하나?

pnpm approve-builds로 esbuild를 승인한다. pnpm 11 이상이면 승인 전까지 설치가 실패한다.

Q3. "Cannot find module"이 나서 shamefullyHoist를 켜려고 한다. 그 전에 할 일은?

1) 그 패키지를 직접 pnpm add -D로 선언, 2) 안 되면 publicHoistPattern으로 좁게 올리기. shamefullyHoist는 최후 수단이다.

Q4. pnpm 12에서 .npmrc에 public-hoist-pattern을 넣었는데 효과가 없다. 왜?

11부터 .npmrc는 인증·레지스트리 설정만 읽는다. pnpm-workspace.yaml에 publicHoistPattern으로 넣어야 한다.

Q5. husky의 prepare는 의존성 빌드 스크립트 차단에 걸리나?

걸리지 않는다. 차단 대상은 의존성의 스크립트이고, 루트 프로젝트 자신의 prepare는 실행된다.
