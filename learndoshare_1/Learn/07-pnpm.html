pnpm 핵심 정리

밀버스는 pnpm만 쓴다. npm에 익숙한 사람이 pnpm에서 걸리는 지점, 특히 Storybook을 설치할 때 문제가 되는 부분을 중심으로 정리한다.

예상 1시간2026-10-09 기준 pnpm 최신 12.10.1로컬 설치 10.13.1 · Node 24.4.1

왜 pnpm인가

디스크 절약

패키지를 전역 저장소(content-addressable store)에 한 번만 저장하고, 프로젝트에는 하드 링크로 연결한다.

엄격함

최상단 node_modules에는 직접 선언한 패키지만 링크된다. 그래서 package.json에 선언하지 않은 패키지는 import할 수 없다. "우연히 되던 코드"가 사라진다.

보안 기본값

10부터 의존성의 설치 스크립트(postinstall)를 기본으로 실행하지 않는다.

규칙npm, yarn, npx 명령은 쓰지 않는다. 블로그나 공식 문서 예제에 npx가 나오면 아래 대응표로 바꿔 실행한다.

출처: pnpm — Motivation (확인 2026-10-09) · pnpm — Mitigating supply chain attacks (확인 2026-10-09)

node_modules 구조

npm은 모든 의존성을 node_modules 최상단에 평평하게 펼친다(hoisting). pnpm은 직접 선언한 패키지만 최상단에 심볼릭 링크로 두고, 실제 파일은 node_modules/.pnpm/ 아래에 둔다. 그 파일도 저장소로 이어진 하드 링크다.

node_modules/
├── storybook -> .pnpm/storybook@10.6.0/node_modules/storybook   ← 내가 선언한 것만 보인다
├── lwc -> .pnpm/lwc@9.4.3/node_modules/lwc
└── .pnpm/
    ├── storybook@10.6.0/node_modules/...
    ├── node_modules/        ← 숨겨진 hoist 영역 (hoistPattern: ['*'])
    └── ...
설정기본값의미
nodeLinkerisolated위와 같은 심볼릭 링크 구조
hoistPattern['*']숨겨진 영역(.pnpm/node_modules)으로 끌어올림. 내 코드에서는 안 보인다
publicHoistPattern[]최상단 node_modules로 끌어올릴 패턴. 도구가 hoisting을 전제할 때 쓴다
shamefullyHoistfalsetrue면 npm처럼 전부 펼침 (publicHoistPattern을 *로 둔 것과 같음)

publicHoistPattern의 기본값이 빈 목록이라 eslint와 prettier도 최상단에 올리지 않는다. 이 기본값은 pnpm 10.0.0에서 바뀌었다(10.0.0 릴리스 노트).

빌드 스크립트 승인

pnpm 10부터 의존성의 postinstall 같은 설치 스크립트는 기본으로 실행되지 않는다. 악성 패키지가 설치만으로 코드를 실행하는 공격을 막기 위해서다.

  • Storybook/Vite를 설치하면 esbuild 같은 패키지가 "빌드 스크립트 무시됨" 목록에 뜰 수 있다. 우리 package.json에도 esbuild를 승인해 두었다
  • pnpm approve-builds를 실행해 필요한 것만 승인한다
  • 내 프로젝트 자신의 prepare/postinstall(예: husky)은 계속 실행된다. 막히는 것은 의존성의 스크립트다. 프로젝트 스크립트까지 끄는 것은 별도 설정 ignoreScripts(기본 false)다 (pnpm 10.13.1에서 실험으로도 확인)
allowBuilds:
  esbuild: true
"pnpm": {
  "onlyBuiltDependencies": ["esbuild"]
}
pnpm 11 이상에서는 설치가 멈춘다미승인 빌드가 있으면 경고가 아니라 오류로 설치가 중단된다(strictDepBuilds 기본 true). 당황하지 말고 pnpm approve-builds로 승인하고 다시 설치한다.

hoisting 문제 해결

일부 도구는 npm처럼 모든 패키지가 최상단에 있다고 가정하고 만들어졌다. pnpm에서는 이런 도구가 "모듈을 찾을 수 없음" 오류를 낸다. Storybook은 9에서 여러 패키지를 핵심 패키지 storybook 하나로 합쳐 선언할 패키지가 줄었다. 애드온에서도 이 오류가 나는지는 미확인이다.

해결 순서 (좁은 것부터)

  1. 오류 메시지에 나온 패키지를 직접 pnpm add -D로 선언한다 (가장 정석)
  2. 안 되면 해당 패턴만 최상단으로 올린다 
    public-hoist-pattern[]=*storybook*
    publicHoistPattern:
  - "*storybook*"
  3. 최후 수단: shamefullyHoist: true. pnpm의 엄격함을 포기하는 것이라 쓰지 않는 것을 목표로 한다

pnpm 10.13.1은 두 형식을 모두 읽는다(pnpm config get으로 로컬 확인). 11부터는 .npmrc의 이 설정을 읽지 않는다.

원칙설정은 실제로 깨졌을 때만 추가한다. 미리 넣어 두면 무엇 때문에 넣었는지 아무도 모르게 된다.

버전 고정과 lockfile

  • pnpm-lock.yaml은 반드시 커밋한다. 모두 같은 버전을 설치하게 된다
  • package-lock.json, yarn.lock은 .gitignore에 넣는다. 섞여 있으면 누군가 npm을 썼다는 신호다
  • pnpm 버전 고정: 최신 문서는 packageManager 필드를 "legacy"로 부른다. pnpm 11부터 쓸 수 있는 devEngines.packageManager는 범위를 지정할 수 있다
{
  "devEngines": {
    "packageManager": { "name": "pnpm", "version": ">=12.0.0 <13.0.0", "onFail": "download" }
  },
  "engines": { "node": ">=22" }
}

예시는 pnpm 문서의 형식을 따랐고 버전은 결정 전 자리표시자다. 팀이 정한 버전으로 바꾼다. 저장소 package.json의 engines.node는 패키지 설계대로 ^22.18.0 || >=23.6.0으로 바꿨다(설계 2장, 2026-10-09 갱신).

alpha 패키지는 정확한 버전으로lightning-base-components는 latest 태그가 1.28.19-alpha다. pnpm add -D -E lightning-base-components처럼 -E로 정확히 고정하고, 올릴 때는 명시적으로 올린다.

husky와 pnpm

husky hook 파일 안에서도 npm/npx를 쓰지 않는다.

cd learndoshare_1 && pnpm exec lint-staged
현재 hook이 동작하지 않는 이유git 루트는 상위 폴더 learndoshare/인데 package.json은 learndoshare_1/에 있다. husky 9.1.7은 현재 폴더에 .git이 없으면 설치하지 않고 ".git can't be found"를 돌려준다. prepare: "husky || true"라서 이 실패가 조용히 넘어간다. husky 문서의 "Project Not in Git Root Directory" 방식대로 prepare를 cd .. && husky learndoshare_1/.husky로 바꿔야 한다. 그러면 hook은 git 루트에서 돌기 때문에, 위 예처럼 hook 안에서 다시 cd learndoshare_1을 한다.

언제 고치나 (2026-10-09 갱신). .husky/pre-commit의 npm run precommit은 패키지 구현 계획 Task 1에서 pnpm precommit으로 바꿨다(구현 계획 Task 1). prepare 경로 수정은 README 4장 Phase 1 체크리스트에만 있고 구현 계획에는 없어서, 언제 할지는 미정이다.

GitHub Packages에서 설치

밀버스는 CLI·템플릿·LWC·Storybook을 패키지 하나(@a40418a/milvus-design-system)에 담아 GitHub Packages에 발행한다(설계 2장). 2026-10-09 갱신: 계획이던 발행과 설치를 실제로 해 봤다.

GitHub 문서가 정한 것

  • GitHub Packages의 npm 레지스트리는 범위가 있는 이름(@NAMESPACE/PACKAGE-NAME)만 받는다
  • 발행·설치·삭제에는 토큰이 필요하다. 비공개·내부·공개 패키지 모두 마찬가지다. 토큰은 personal access token (classic)만 되고, 설치하려면 read:packages 권한이 있어야 한다
  • 발행할 때는 package.json의 publishConfig.registry에 레지스트리를 적고, GitHub Actions에서는 GITHUB_TOKEN으로 워크플로 저장소에 딸린 패키지를 발행한다
  • 처음 발행한 패키지의 기본 공개 범위는 비공개다. 예외로, npm 레지스트리처럼 granular permissions를 지원하는 레지스트리에서 워크플로가 GITHUB_TOKEN으로 만든 패키지는 워크플로를 실행한 저장소의 공개 범위와 권한 모델을 물려받는다. 한 번 공개로 바꾼 패키지는 다시 비공개로 바꿀 수 없다

2026-10-09에 실제로 한 것

단계결과
발행태그 v0.0.1을 push하자 GitHub Actions의 발행 워크플로가 GITHUB_TOKEN으로 0.0.1을 발행했다(32초)
공개 범위패키지가 공개로 생겼다. 로그인하지 않아도 패키지 페이지와 설치 명령이 보인다. 문서상 워크플로가 GITHUB_TOKEN으로 만든 패키지는 저장소 공개 범위를 물려받는다. 저장소(a40418a/learndoshare)가 공개라 공개로 생긴 것으로 보인다. 내용이 공개 저장소와 같고 org ID·인증 정보가 없어서 공개로 두기로 했다. 회사 GitHub 조직으로 옮길 때 다시 정한다(설계 1장)
설치새 SFDX 프로젝트(설치 시험용, 커밋하지 않음)에 프로젝트 .npmrc 두 줄(아래 예와 같은 내용)을 두고, 셸 환경 변수 NODE_AUTH_TOKEN에 read:packages classic 토큰을 넣었다. pnpm 10.13.1이 ${NODE_AUTH_TOKEN}을 치환해 pnpm add -D @a40418a/milvus-design-system@0.0.1이 됐고, pnpm milvus --version이 0.0.1을 출력했다. 설치 중 esbuild 빌드 스크립트를 건너뛰었다는 경고가 나왔다(빌드 스크립트 승인, 영향은 설계 14장에 미확인으로 남김)

공개 패키지가 됐어도 GitHub 문서대로라면 설치에는 토큰이 필요하다. 토큰 없이 설치되는지는 시험하지 않았다.

레지스트리와 토큰을 적는 곳은 pnpm 버전마다 다르다(2026-10-09 갱신).

무엇pnpm 10 (이 저장소 10.13.1)pnpm 11 이상
범위 레지스트리.npmrc의 @a40418a:registry= 줄pnpm-workspace.yaml의 registries 설정(11.0.0에 추가). 11.0 릴리스 노트는 이 설정이 @scope:registry= 줄을 대체한다고 적는다. 11도 .npmrc의 레지스트리 설정은 계속 읽는다
토큰.npmrc의 //npm.pkg.github.com/:_authToken= 줄같다. 인증 값은 registries에 넣을 수 없고 .npmrc에 둔다. ~/.npmrc도 npm에서 옮기기 쉽게 계속 읽는다
@a40418a:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}
registries:
  default: https://registry.npmjs.org/
  "@a40418a": https://npm.pkg.github.com

yaml 예는 범위를 키로 쓰는 형식이다. 11.23.0부터는 레지스트리 URL을 키로 쓰는 형식이 생겼고, 이 형식도 계속 받는다. 두 형식을 섞을 수는 없다.

토큰은 파일에 쓰지 않는다토큰 값은 셸 환경 변수 NODE_AUTH_TOKEN에 두고 .npmrc에는 ${NODE_AUTH_TOKEN}만 쓴다. 사용자 파일 ~/.npmrc의 ${NAME}은 pnpm 10.x 문서와 최신 문서 모두 환경 변수로 바꾼다고 적는다. 프로젝트 .npmrc는 다르다. pnpm 11.5.3부터(10.x는 10.34.2부터) 프로젝트 .npmrc의 레지스트리 주소, //로 시작하는 키, 인증 값에 ${...}가 있으면 풀지 않고 그 설정을 무시한다. 저장소에 딸려 온 파일이 토큰을 다른 레지스트리로 보내지 못하게 하려는 것이다. 우리가 쓰는 10.13.1은 그 전 버전이라 문서상 프로젝트 .npmrc도 치환한다(2026-10-09 갱신). 그래도 버전을 올리면 막히므로 토큰 줄은 ~/.npmrc에 둔다. 레지스트리 줄처럼 값이 고정된 줄은 프로젝트 .npmrc에 둘 수 있다. 2026-10-09 설치 확인에서 10.13.1이 프로젝트 .npmrc의 ${NODE_AUTH_TOKEN}을 치환하는 것을 봤다(설계 13장). 더 새 pnpm에서의 동작은 설계 14장에 미확인으로 남겼다.

토큰을 키체인에 두고 셸에서 읽기 (macOS)

GitHub 문서는 personal access token을 비밀번호처럼 다루고 만료일을 두라고 권한다. 토큰 값은 .npmrc에도 ~/.zshrc에도 쓰지 않는다. macOS에서는 토큰을 키체인에 한 번 넣어 두고, 셸이 시작할 때 꺼내 NODE_AUTH_TOKEN에 넣을 수 있다.

# -w를 맨 끝에 두면 토큰을 입력하라고 묻는다. 명령 줄과 셸 기록에 토큰이 남지 않는다
security add-generic-password -a "$USER" -s milvus-npm-token -w
export NODE_AUTH_TOKEN="$(security find-generic-password -a "$USER" -s milvus-npm-token -w)"
  • milvus-npm-token은 예로 든 서비스 이름이다. 두 명령에서 같기만 하면 된다. -a(계정)와 -s(서비스)는 add-generic-password에서 필수다
  • find-generic-password -w는 찾은 항목의 비밀번호만 출력한다. 그 값이 환경 변수로 들어가고 파일에는 남지 않는다
  • zsh는 대화형 셸을 시작할 때 ~/.zshrc를 읽는다. 그래서 새로 연 터미널부터 적용된다
  • 토큰을 새로 만들면 add-generic-password에 -U를 붙여 같은 항목을 갱신한다(-U가 없으면 이미 있는 항목에 다시 넣을 수 없다)

security 명령의 옵션은 macOS 내장 매뉴얼(man security)로 확인했다(2026-10-09, 로컬). zsh가 ~/.zshrc를 읽는 시점은 zsh 매뉴얼: Startup/Shutdown Files에 있다. 두 자료는 Learn 출처 허용 도메인 밖이라 아래 출처 줄에는 넣지 않았다.

workspace는 쓰지 않는다 (2026-10-09 갱신). 이전 문서는 두 번째 프로젝트가 붙으면 토큰·컴포넌트·Storybook을 workspace 패키지로 나눈다고 적었다. 설계는 프로젝트에 추가되는 의존성을 하나로 두려고 패키지 하나로 정했다.

스스로 점검

Q1. 블로그에 npx storybook add @storybook/addon-a11y라고 나온다. 어떻게 실행하나?

Storybook이 이미 설치돼 있으므로 pnpm exec storybook add @storybook/addon-a11y.

Q2. Storybook 설치 후 "Ignored build scripts: esbuild"가 떴다. 무엇을 해야 하나?

pnpm approve-builds로 esbuild를 승인한다. pnpm 11 이상이면 승인 전까지 설치가 실패한다.

Q3. "Cannot find module"이 나서 shamefullyHoist를 켜려고 한다. 그 전에 할 일은?

1) 그 패키지를 직접 pnpm add -D로 선언, 2) 안 되면 publicHoistPattern으로 좁게 올리기. shamefullyHoist는 최후 수단이다.

Q4. pnpm 12에서 .npmrc에 public-hoist-pattern을 넣었는데 효과가 없다. 왜?

11부터 .npmrc는 인증·레지스트리 설정만 읽는다. pnpm-workspace.yaml에 publicHoistPattern으로 넣어야 한다.

Q5. husky의 prepare는 의존성 빌드 스크립트 차단에 걸리나?

걸리지 않는다. 차단 대상은 의존성의 스크립트이고, 루트 프로젝트 자신의 prepare는 실행된다.

Q6. 밀버스 패키지 설치가 GitHub Packages 인증 오류로 실패한다. 공개 저장소인데 토큰이 왜 필요한가?

GitHub Packages의 npm 레지스트리는 공개 패키지라도 설치에 토큰이 필요하다. read:packages 권한의 personal access token (classic)을 NODE_AUTH_TOKEN에 넣고, 토큰 줄은 ~/.npmrc에 둔다.
