LWC 기초

Lightning Web Components(LWC)의 번들 구조, 데코레이터, 템플릿, 이벤트, Shadow DOM을 정리한다. 특히 "Storybook에서 org 없이 렌더되는 컴포넌트"를 만들기 위해 알아야 할 부분에 집중한다.

예상 2시간선행: 01 SLDS2026-10-09 갱신 · 공식 문서로 다시 확인lwc 9.4.3

왜 알아야 하나

밀버스 디자인 시스템의 컴포넌트는 전부 LWC다. Storybook에서 보여 주든, org에 배포하든 코드는 하나다. 그런데 org 안에서는 당연하게 동작하던 것들(@wire, @salesforce/* import, synthetic shadow)이 org 밖에서는 없다.

어떤 기능이 LWC 엔진 자체의 것이고 어떤 기능이 Salesforce 플랫폼이 제공하는 것인지 구분할 수 있어야, Storybook(04 통합)과 Jest 테스트에서 무엇을 대체(stub)해야 하는지 판단할 수 있다.

엔진 (어디서나 동작)

LightningElement, @api, @track, 템플릿 지시어, 라이프사이클 훅, CustomEvent

플랫폼 (org 안에서만)

@salesforce/apex, @salesforce/label 등 scoped 모듈, lightning/uiRecordApi 같은 데이터 어댑터

그 사이

lightning-* 기본 컴포넌트. org에는 있고, 밖에서는 npm 패키지(lightning-base-components)나 Jest stub으로 채운다

컴포넌트 번들과 이름 규칙

컴포넌트 하나는 폴더 하나다. 폴더와 그 안의 파일은 대소문자까지 같은 이름이어야 한다. SFDX 프로젝트에서는 force-app/main/default/lwc/ 바로 아래에 두며, 컴포넌트 폴더 안에 다른 컴포넌트를 중첩할 수 없다.

milvusBadge/
├── milvusBadge.js          ← 클래스 (필수)
├── milvusBadge.html        ← 템플릿
├── milvusBadge.css         ← 컴포넌트 스타일 (shadow 안에만 적용)
├── milvusBadge.js-meta.xml ← 설정 파일 (필수. 노출 여부, 대상 등)
└── __tests__/
    └── milvusBadge.test.js

폴더 이름 → 태그 이름

HTML 표준은 커스텀 요소 이름에 하이픈을 요구하지만, 플랫폼은 폴더 이름에 하이픈을 허용하지 않는다. 그래서 camelCase 폴더 이름이 kebab-case 태그로 바뀌고, 앞에 네임스페이스가 붙는다. 기본 네임스페이스는 c다.

폴더import 경로마크업 태그
milvusBadgec/milvusBadge<c-milvus-badge>
milvusRecordBadgec/milvusRecordBadge<c-milvus-record-badge>

속성도 같은 규칙이다. JS의 itemName은 마크업에서 item-name으로 쓴다.

이름 규칙소문자로 시작, 영숫자와 밑줄만, 공백·하이픈 금지, 밑줄로 끝나거나 연속 밑줄 금지. 네임스페이스 안에서 유일해야 한다.

LightningElement와 데코레이터

모든 컴포넌트 클래스는 lwc 모듈의 LightningElement를 상속한다. 필드에는 데코레이터를 하나만 붙일 수 있다.

import { LightningElement, api } from 'lwc';

export default class MilvusBadge extends LightningElement {
  @api label = '';          // 공개 속성: 부모가 값을 넣는다
  @api variant = 'neutral'; // 'neutral' | 'success' | 'warning' ...

  get badgeClass() {        // getter도 템플릿에서 쓰면 반응형
    return `badge badge_${this.variant}`;
  }
}

이 문서의 milvusBadge·milvusRecordBadge 코드는 개념을 보이기 위한 예시다. 저장소의 실제 milvusBadge는 lightning-badge를 감싸고 variant를 SLDS 클래스로 바꾼다 (2026-10-09 갱신).

@api — 공개 속성

  • 컴포넌트의 공개 API다. 템플릿에서 쓰이는 @api 값이 바뀌면 다시 렌더된다
  • 데이터는 부모 → 자식 한 방향으로 흐른다. 컴포넌트는 초기화할 때만 자기 @api 필드를 설정하고, 그 뒤로는 소유자(부모)만 값을 바꾼다. 전달받은 값은 읽기 전용으로 다룬다
  • 객체나 배열을 넘기면 자식 쪽에서는 읽기 전용 프록시다. 내부를 바꾸려 하면 Invalid mutation 오류가 난다. 바꿔야 하면 얕은 복사본을 만들거나, 이벤트로 부모에게 요청한다
  • 공식 문서는 객체보다 원시값(문자열, 숫자, 불리언) 속성을 권장한다. 데이터 모양이 속성 이름으로 드러나고, 모양이 바뀌어도 소비자가 덜 깨진다

@track — 대부분 필요 없다

현재 LWC에서 필드는 기본으로 반응형이다. 다만 비교는 얕다(===). 그래서 동작이 이렇게 갈린다.

this.count = 43;                          // 감지됨
this.obj.name = 'Bob';                    // 감지 안 됨 (필드 자체는 그대로)
this.obj = { ...this.obj, name: 'Bob' };  // 감지됨 (새 객체 대입)
this.arr.push('c');                       // 감지 안 됨

@track은 평범한 객체({})나 배열([])의 내부 변경까지 추적하고 싶을 때만 쓴다. Date, Set, Map, 클래스 인스턴스의 내부 변경은 @track을 붙여도 추적되지 않는다. 밀버스에서는 "새 객체를 대입한다"를 기본 습관으로 삼고 @track은 쓰지 않는 것을 목표로 한다.

@wire — 반응형 데이터

@wire는 데이터 어댑터를 필드나 함수에 연결한다. 설정 객체의 값 앞에 $를 붙이면 그 속성이 바뀔 때마다 다시 조회한다.

import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import STATUS_FIELD from '@salesforce/schema/Case.Status';

export default class MilvusRecordBadge extends LightningElement {
  @api recordId;

  @wire(getRecord, { recordId: '$recordId', fields: [STATUS_FIELD] })
  record; // { data, error } 형태로 채워진다
}
핵심@wire로 쓰는 데이터 어댑터(lightning/uiRecordApi 등)와 @salesforce/schema는 플랫폼이 제공한다. org 밖(Storybook)에서는 없다. 그래서 @wire를 쓰는 컴포넌트는 표현 컴포넌트가 될 수 없다 (표현 / 컨테이너 분리).

라이프사이클 훅

프레임워크가 컴포넌트를 만들고, DOM에 넣고, 렌더하고, 제거한다. 각 단계에서 호출되는 메서드가 훅이다.

constructor()인스턴스 생성. 반드시 super()를 먼저 호출한다
→
connectedCallback()DOM에 삽입됨. 초기화, 구독 시작
→
renderedCallback()렌더 완료. 다시 렌더될 때마다 또 호출된다
→
disconnectedCallback()DOM에서 제거됨. 구독, 타이머 정리
훅주로 하는 일주의
constructor()필드 기본값이 시점에는 자식 요소도, 부모가 넣은 @api 값도 아직 없다
connectedCallback()초기 데이터 준비, 이벤트 리스너 등록요소가 옮겨지면 여러 번 호출될 수 있다
renderedCallback()렌더된 DOM을 봐야 하는 작업여기서 반응형 필드를 바꾸면 다시 렌더 → 무한 루프 위험. 한 번만 실행할 작업은 플래그로 막는다
disconnectedCallback()정리connected에서 만든 것은 여기서 해제한다
errorCallback(error, stack)하위 컴포넌트에서 난 오류 처리 (error boundary)자기 자신의 오류가 아니라 자손의 오류를 잡는다

공식 문서 목차에는 render()(템플릿을 조건에 따라 바꿔 끼우는 메서드)도 이 장에 함께 있다. 표현 컴포넌트에서는 거의 쓸 일이 없다.

템플릿 지시어

템플릿은 루트 <template> 하나로 감싼다. 루트에는 지시어를 붙이지 않고, 안쪽의 중첩된 <template>이나 일반 태그에 붙인다.

조건부 렌더링: lwc:if / lwc:elseif / lwc:else

<template>
  <template lwc:if={label}>
    <span class={badgeClass}>{label}</span>
  </template>
  <template lwc:elseif={placeholder}>
    <span class="badge badge_empty">{placeholder}</span>
  </template>
  <template lwc:else></template>
</template>
옛 문법은 쓰지 않는다if:true / if:false는 공식 문서에서 더 이상 권장하지 않는다. 인터넷 예제에서 보이면 lwc:if로 바꾼다.

목록: for:each와 key, iterator

<template for:each={items} for:item="item">
  <li key={item.id}>{item.label}</li>
</template>

<template iterator:it={items}>
  <li key={it.value.id} class={it.value.cls}>
    {it.value.label}
    <template lwc:if={it.last}> (마지막)</template>
  </li>
</template>
  • 어느 쪽이든 반복되는 첫 요소에 key가 필수다. 문자열이나 숫자여야 하고, 인덱스를 key로 쓰면 안 된다
  • iterator는 value, index, first, last를 제공한다. 이름(it)은 소문자여야 한다

이벤트 핸들러

<button onclick={handleClick}>{label}</button>
<c-milvus-badge onselect={handleSelect}></c-milvus-badge>

핸들러는 on + 이벤트 이름으로 쓰고, 값은 클래스의 메서드를 가리킨다({handleClick}). 필요한 값은 data-* 속성에 넣고 event.currentTarget.dataset으로 읽는다(data-item-id → dataset.itemId).

템플릿 식 (2026-10-09 갱신)기본 바인딩 { } 안에는 식별자나 멤버 식만 쓸 수 있고, 계산은 getter로 한다. Spring '26부터는 컴포넌트 apiVersion이 66.0 이상이면 함수 호출, 화살표 함수 같은 복잡한 식을 템플릿에 쓸 수 있다. 밀버스는 단위 테스트가 쉬운 getter와 메서드 참조를 기본으로 쓴다. 로컬 도구(Storybook용 컴파일, Jest)가 이 새 문법을 지원하는지는 미확인이다.

이벤트로 부모와 대화하기

데이터는 부모 → 자식 한 방향으로 흐르고, 자식이 부모 데이터를 바꾸고 싶으면 직접 바꾸지 않고 이벤트를 보낸다. 흔히 "속성은 아래로, 이벤트는 위로"라고 줄여 말한다.

handleClick() {
  this.dispatchEvent(new CustomEvent('select', {
    detail: { value: this.label }, // 원시값 또는 새로 만든 객체만
  }));
}
<c-milvus-badge label="진행 중" onselect={handleSelect}></c-milvus-badge>
옵션기본값의미
bubblesfalseDOM 위쪽으로 전파되는지
composedfalseshadow 경계를 넘어가는지
  • 이벤트 이름에는 대문자를 쓰지 않고, on으로 시작하지 않는다. 템플릿의 핸들러 이름이 on으로 시작해야 해서 ononselect가 되어 버린다
  • detail에 객체를 그대로 넣으면 받는 쪽이 원본을 바꿀 수 있다. 원시값만 넣거나 새 객체로 복사해서 넣는다
  • 버블링하는 이벤트는 경로 위의 모든 소비자에게 API가 된다. 가장 제한적인 설정(기본값 둘 다 false)부터 시작한다
  • LWC는 버블링 단계만 쓴다. capture 단계는 지원하지 않는다

Shadow DOM 모드

각 컴포넌트의 내부 DOM은 shadow tree로 감싸여 바깥과 분리된다. 그런데 "shadow DOM"에는 구현이 여러 가지다.

모드선언상태특징
synthetic shadow(플랫폼 기본)LEX · Experience Cloud 기본브라우저의 native shadow를 흉내 내는 폴리필. CSS는 스코프 토큰(예: lwc-12abcdefg-host 속성)으로 격리한다
native shadow (mixed shadow)static shadowSupportMode = 'native'Beta브라우저 표준 shadow DOM. any 값은 deprecated, reset 값이 있다. synthetic 컴포넌트 안에 native 컴포넌트를 둘 수 있지만 그 반대는 지원하지 않는다
light DOMstatic renderMode = 'light'Beta 아님shadow 없이 렌더. 문서의 스타일이 들어오고, LWC가 스타일을 자동으로 가두지 않아 컴포넌트 CSS도 밖으로 샐 수 있다(*.scoped.css로 막는다)

공식 문서(Light DOM 페이지) 기준으로 Lightning Experience와 Experience Cloud는 synthetic shadow를 쓴다. 우리 org에서도 2026-10-07에 실측했다. 기본 컴포넌트가 전부 synthetic으로 그려졌다(README 3장). 다만 npm lightning-base-components는 156개 컴포넌트를 native 지원 목록(lwc.nativeShadowEnabledComponents)에 올려 두었다. Salesforce가 이 목록을 org에 적용하는 시점은 미확인이다.

스타일 격리가 어떻게 다른가

  • synthetic: 컴포넌트 CSS에 스코프 속성을 붙여 격리한다. 실제로는 한 문서 안에 있으므로 전역 스타일시트(예: SLDS CSS)가 컴포넌트 안까지 적용될 수 있다. SLDS 클래스를 컴포넌트 안에서 쓸 수 있는 이유다
  • native: 브라우저가 진짜로 경계를 만든다. 문서 전역 스타일시트는 안으로 들어가지 않는다. 그래서 같은 코드라도 SLDS 클래스가 안 먹는 결과가 나올 수 있다
Storybook도 synthetic으로 맞춘다synthetic 폴리필이 없으면 LWC는 native shadow로 렌더된다. org와 같은 모습을 보려면 @lwc/synthetic-shadow를 엔진보다 먼저 실행해서 플랫폼과 같은 모드로 맞춘다. lightning-base-components 패키지 README도 "SLDS 스타일을 앱 전역에 정의"와 "@lwc/synthetic-shadow"를 필수 조건으로 적고 있다. 우리 Storybook은 org처럼 모든 LWC를 synthetic으로 그린다(#16). 자세한 구성은 04 통합에서 다룬다.

CSS 변수와 shadow 경계

shadow DOM에서 부모의 CSS 선택자는 자식 안으로 들어가지 못한다. 부모는 자식을 "요소 하나"로만 꾸밀 수 있다. 반면 공식 문서에 따르면 CSS 사용자 정의 속성(custom properties)은 부모에게서 값을 상속받고, 상속되는 속성은 shadow DOM을 뚫고 들어간다.

/* 1) 선택자로 자식 내부를 건드리기: 동작하지 않는다 */
c-milvus-button button { font-weight: 700; }

/* 2) 자식 요소 자체를 꾸미기: 동작한다 (요소 하나로서) */
c-milvus-button { display: inline-block; margin: 4px; }

3) 조상에 변수를 선언하면 자식 내부까지 상속된다. 저장소의 실제 예가 브랜드 util.css와 milvusButton이다.

:root {
  --milvus-button-custom: on;
  --milvus-button-font-weight: var(--slds-g-font-weight-7);
}
.milvus-button {
  /* 브랜드 변수를 읽고, 없으면 SLDS global hook, 그것도 없으면 고정값 */
  font-weight: var(--milvus-button-font-weight, var(--slds-g-font-weight-6, 600));
}
그래서 브랜드 변수가 동작한다--milvus-*를 :root에 한 번 선언하면, 그 아래 모든 컴포넌트가 shadow 안에서 같은 값을 읽는다. 컴포넌트마다 값을 넘길 필요가 없다. milvusButton은 JS에서도 getComputedStyle(this.template.host)로 --milvus-button-custom을 읽어 그리는 방식을 고른다.

표현 / 컨테이너 분리

표현 컴포넌트 (presentational)

@api로 받고, 이벤트로 알린다. @wire, Apex, LDS를 쓰지 않는다. Storybook에서 그대로 렌더된다.

컨테이너 컴포넌트 (container)

데이터를 가져와 표현 컴포넌트에 넘긴다. @wire, Apex 호출은 여기에만 둔다. Storybook 대상이 아니다.

import { LightningElement, api } from 'lwc';

export default class MilvusBadge extends LightningElement {
  @api label = '';
  @api variant = 'neutral';

  get badgeClass() {
    return `badge badge_${this.variant}`;
  }

  handleClick() {
    this.dispatchEvent(new CustomEvent('select', { detail: { value: this.label } }));
  }
}
import { LightningElement, api, wire } from 'lwc';
import { getRecord, getFieldValue } from 'lightning/uiRecordApi';
import STATUS_FIELD from '@salesforce/schema/Case.Status';

const VARIANT_BY_STATUS = { New: 'neutral', Working: 'warning', Closed: 'success' };

export default class MilvusRecordBadge extends LightningElement {
  @api recordId;

  @wire(getRecord, { recordId: '$recordId', fields: [STATUS_FIELD] })
  record;

  get status() {
    return this.record?.data ? getFieldValue(this.record.data, STATUS_FIELD) : '';
  }

  get variant() {
    return VARIANT_BY_STATUS[this.status] ?? 'neutral';
  }
}
<template>
  <c-milvus-badge label={status} variant={variant}></c-milvus-badge>
</template>
판단 기준 한 줄"Storybook에서 org 없이 렌더되지 않으면 표현 컴포넌트가 아니다." 표현 컴포넌트에 @wire나 @salesforce/apex import가 들어오면 리뷰에서 막는다. 이 분리는 밀버스의 결정이다(README 1.3). 아래 출처는 그 근거가 되는 LWC 규칙이다.

Jest 테스트

프로젝트의 package.json에는 "test:unit": "sfdx-lwc-jest"가 이미 있다. pnpm test:unit으로 실행한다 (pnpm test:unit:watch, pnpm test:unit:coverage도 있다).

문제@salesforce/sfdx-lwc-jest (최신·설치 버전 7.9.0)가 해 주는 것
lightning-* 기본 컴포넌트가 없다lightning 기본 컴포넌트의 stub(lightning-stubs)을 설치하고 자동으로 쓴다. stub은 실제 컴포넌트와 API가 같지만 기능은 다 갖추지 않았고 이벤트를 스스로 보내지 않는다. 바꾸고 싶으면 Jest 설정의 moduleNameMapper로 덮어쓴다
@salesforce/* import가 없다@lwc/jest-transformer가 이 import를 테스트용 값으로 바꿔 준다
Apex 호출2026-10-09 정정 @salesforce/apex/Class.method 기본 import는 Promise.resolve()를 돌려주는 함수가 된다(jest.fn()이 아니다). 호출을 검사하려면 테스트에서 jest.mock으로 바꾼다. import { getSObjectValue } from '@salesforce/apex' 같은 이름 import는 jest.fn(), refreshApex는 Promise.resolve() 함수로 대체된다
@wire 데이터@salesforce/wire-service-jest-util의 API로 테스트에서 값을 흘려 넣는다. sfdx-lwc-jest README에 따르면 이 API가 패키지를 통해 노출되므로 별도 의존성을 추가하지 않아도 된다
import { createElement } from 'lwc';
import MilvusBadge from 'c/milvusBadge';

describe('c-milvus-badge', () => {
  afterEach(() => {
    while (document.body.firstChild) document.body.removeChild(document.body.firstChild);
  });

  it('label을 렌더하고 클릭하면 select 이벤트를 보낸다', () => {
    const el = createElement('c-milvus-badge', { is: MilvusBadge });
    el.label = '진행 중';
    const handler = jest.fn();
    el.addEventListener('select', handler);
    document.body.appendChild(el);

    const span = el.shadowRoot.querySelector('span');
    expect(span.textContent).toBe('진행 중');
    span.click();
    expect(handler).toHaveBeenCalled();
  });
});

위 테스트는 템플릿에 onclick={handleClick}이 span에 걸려 있다고 가정한 예시다.

표현 컴포넌트는 stub이 거의 필요 없어서 테스트가 짧다. 이것도 분리의 이점이다.

우리 프로젝트 적용

밀버스 규칙 정리
  • 컴포넌트는 force-app/main/default/lwc/에 두고, 이름은 milvus 접두어 + camelCase. 태그는 <c-milvus-*>가 된다
  • 디자인 시스템 컴포넌트는 표현 컴포넌트로 만든다. @api 입력, CustomEvent 출력만. @wire, Apex, LDS는 컨테이너에만
  • 공개 속성은 가능하면 원시값. 객체를 받으면 절대 내부를 바꾸지 않는다
  • 컴포넌트 CSS는 var(--slds-g-*, fallback), var(--slds-s-*, fallback), var(--milvus-*, fallback)를 읽기만 한다. hex 색과 브랜드 값을 넣지 않고, hook을 재정의하지 않는다 (CLAUDE.md 3장, 2026-10-09 갱신)
  • 브랜드 값은 브랜드 util.css의 :root에 선언하고 상속으로 컴포넌트 안에 들어온다. 브랜드 색은 org 테마가 원본이다 (01 SLDS)
  • Storybook은 LWC를 Rollup으로 미리 컴파일해서 렌더한다. 플랫폼과 같은 모습을 위해 모든 LWC를 synthetic shadow로 그린다 (04 통합)
  • 단위 테스트는 pnpm test:unit
버전 정보2026-10-09 기준 npm lwc latest는 9.4.3이고 저장소도 9.4.3을 쓴다. dist-tag로 summer26 9.1.5, winter27 9.3.10이 있다. 로컬 도구(Storybook용 Rollup 빌드)의 lwc 버전과 org 릴리스 버전이 다르면 미세한 동작 차이가 있을 수 있다. 어느 태그에 맞출지는 04 통합 단계에서 정한다.

스스로 점검

Q1. 폴더 milvusStatusPill의 마크업 태그와 import 경로는?

태그는 <c-milvus-status-pill>, import는 c/milvusStatusPill. camelCase가 kebab-case로 바뀌고 네임스페이스 c가 붙는다.

Q2. this.items.push(x) 후 화면이 안 바뀐다. @track을 붙이는 것 말고 권장하는 방법은?

새 배열을 대입한다: this.items = [...this.items, x]. 필드는 기본으로 반응형이지만 ===로 얕게 비교하므로 새 값을 대입해야 감지된다.

Q3. 자식이 @api로 받은 객체의 속성을 바꾸려 한다. 무슨 일이 일어나고, 어떻게 해야 하나?

읽기 전용 프록시라 Invalid mutation 오류가 난다. 부모에게 CustomEvent를 보내 부모가 값을 바꾸게 하거나, 자기 필드에 복사본을 만들어 쓴다.

Q4. 부모 CSS의 c-milvus-button button { ... }은 왜 안 먹고, util.css의 --milvus-button-font-weight는 왜 먹나?

선택자는 shadow 경계를 넘지 못한다. CSS 사용자 정의 속성은 상속되므로 shadow 경계를 통과해 컴포넌트 안에서 var()로 읽힌다.

Q5. Storybook에서 SLDS 클래스가 컴포넌트 안에 적용되지 않는다. 가장 먼저 의심할 것은?

synthetic shadow가 켜져 있지 않아 native shadow로 렌더되고 있을 가능성. org(LEX)는 synthetic shadow를 쓰므로 @lwc/synthetic-shadow를 엔진보다 먼저 실행해서 맞춘다.

Q6. Jest에서 Apex 메서드를 부른 횟수를 검사하려 한다. import만 하면 jest.fn()인가?

아니다. @salesforce/apex/Class.method 기본 import는 Promise.resolve()를 돌려주는 함수로 바뀐다. 횟수나 인자를 검사하려면 jest.mock으로 그 모듈을 jest.fn()으로 바꾼다.
