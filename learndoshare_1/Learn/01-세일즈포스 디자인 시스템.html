세일즈포스 디자인 시스템

SLDS가 무엇으로 이루어져 있는지, SLDS 2에서 무엇이 바뀌었는지, 그리고 밀버스가 SLDS 위에서 무엇을 추가하고 무엇을 건드리지 않는지 정리한다. 개념(디자인 토큰, styling hook, shadow DOM)을 처음 본다면 00 개념을 먼저 읽는다.

왜 알아야 하나

밀버스의 첫 번째 원칙은 "SLDS가 제공하는 것을 최대한 쓴다"이다(README 1.3, 2026-10-09 갱신). 밀버스는 SLDS에 없는 것만 더한다. 무엇이 SLDS에 없는지 판단하려면 SLDS가 무엇을 제공하는지 먼저 알아야 한다. Salesforce도 기본 컴포넌트(lightning-*)를 가장 먼저 쓰라고 권한다.

기본 우선 (2026-10-09 갱신). 기본 상태는 Salesforce 기본 모양에 브랜드 색과 로고만 org 테마로 바꾼 것이다. 모양을 바꾸는 util.css는 브랜드 요청이 있을 때만 쓴다. 공식 권고 밖의 방법이기 때문이다. 결정 기록은 설계 문서 1장에 있다.

우리 org는 SLDS 2 테마(Milvus_DesignSystem, brands/Milvus_DesignSystem/theme.json의 designSystemVersion이 SLDS_v2)를 쓴다. 인터넷 자료 상당수는 SLDS 1 기준이라, 그대로 따라 하면 SLDS 2에서 동작하지 않거나 가이드라인을 어기게 된다.

무엇을 가져다 쓰나

org 테마(브랜드 색·로고), base 컴포넌트(lightning-*), 블루프린트, styling hook

무엇을 하지 않나

컴포넌트 CSS에서 --slds-g-* 재정의, SLDS 클래스 덮어쓰기, 하드코딩 색. 지금 예외는 브랜드 util.css 하나뿐이다(styling hook). 클래스 규칙을 갖는 파일은 둘이다. milvusBridge.css는 패키지가 SLDS 2 CSS에서 생성해 관리하고(Task 15·16, 브리지, 2026-10-13 갱신), opt-in milvusOverride.css는 init이 빈 틀을 프로젝트에 넣는다(Task 11)

무엇을 추가하나

SLDS에 없는 기능을 맡는 밀버스 컴포넌트와 --milvus-* 변수. 모양만 바꾸려고 컴포넌트를 만들지 않는다 (2026-10-09 갱신)

SLDS 1과 SLDS 2

SLDS 2는 Spring '25에 소개됐다. 구조와 시각 디자인을 분리하는 새 CSS 프레임워크 위에 만들어졌고, 시각 디자인은 styling hook으로 바뀐다.

현재 상태org learndoshare_1은 SLDS 2 테마 Milvus_DesignSystem을 쓴다 (05 테마 동기화에서 조회). 그래서 밀버스 컴포넌트 CSS는 --lwc-* token과 --slds-c-* hook에 기대면 안 된다.

styling hook

공식 입장과 밀버스가 실제로 쓰는 범위가 다르다. 둘을 나눠 적는다.

접두사종류공식 입장밀버스 (2026-10-09 갱신)
--slds-g-*global hook. 공식 범주는 색, 그림자, 테두리·반경, 글자, 간격, 크기 6개다. 패키지에는 --slds-g-duration-* 8개도 정의돼 있지만 SLDS 2 CSS와 기본 컴포넌트 CSS 어디에서도 읽지 않는다 (2026-10-09 갱신)재정의하지 말고 읽기 전용으로 쓴다읽기 컴포넌트 CSS에서는 읽기만. 예외 브랜드 util.css의 :root에서 이름에 color가 없는 것(글꼴 제외), 포커스 그림자, 중립 색, 피드백 색만 재정의한다. 브랜드 색 계열(accent 등)은 금지다(설계 5.2, 아래 규칙 표, 2026-10-09 갱신)
--slds-s-*컴포넌트 묶음 hook. SLDS 2 CSS가 .slds-button 같은 규칙 안에서 읽는다공식 패키지인 SLDS Linter ESLint 플러그인의 README는 --_slds-*와 함께 Salesforce 내부용(private) hook으로 분류한다(no-slds-private-var)예외 util.css에서 SLDS 2 CSS나 기본 컴포넌트 CSS가 var()로 읽는 이름만 쓴다. 색 s hook은 hover·선택 바탕 6개만, 값은 중립 g hook만 참조한다(설계 5.2, 2026-10-09 갱신. PR #19의 "이름에 color가 없고 SLDS 2 CSS가 정의하는 것"을 바꿨다). 기본 컴포넌트가 native shadow로 바뀌면 효과가 사라질 수 있다
--slds-c-*component hook. 특정 컴포넌트 하나의 모양 조절LWC 개발자 가이드: SLDS 2에서 아직 지원하지 않는다. SLDS 사이트(Styling API): Developer Preview, 운영에 쓰지 말 것금지
--_slds-*private. Salesforce 내부용지워야 한다금지
--milvus-*밀버스가 정의하는 변수(사내 변수는 자기 접두사를 쓰라는 규칙에 맞음)사용 util.css에서 정의하고 밀버스 컴포넌트가 읽는다
component hook에 대한 공식 입장 (2026-10-09 갱신)공식 문서 두 곳의 표현이 다르다. LWC 개발자 가이드는 "component styling hook은 SLDS 2에서 아직 지원되지 않으며, 커스텀 컴포넌트가 이를 쓴다면 당분간 org를 SLDS 1 테마로 유지하라"고 안내한다. SLDS 사이트의 Styling API 페이지는 SLDS 2의 component-level styling hook을 Developer Preview로 두고, 정식 출시 전에는 운영에 쓰지 말라고 적는다. 어느 쪽이든 우리 org(SLDS 2)에서 component hook은 선택지가 아니다.
util.css 예외는 알고 택한 것이다global hook 재정의와 --slds-s-* 사용은 공식 권고 밖이다. 특히 --slds-s-*는 Salesforce가 내부용(private)으로 분류한 hook이다. 밀버스는 #18에서 공식 권고 밖인 것을 알고 허용했고, private 분류를 확인한 뒤에도 기본 우선에서는 요청이 있을 때만 쓰므로 당장 바꾸지 않는다(설계 15장 미정 항목). 지금 org는 기본 컴포넌트를 synthetic shadow로 그려서 문서에 넣은 util.css가 컴포넌트 안까지 닿는다(2026-10-08 org 프로브에서 --slds-s-input-radius-border까지 닿음). 그래서 기본 우선으로, 브랜드 요청이 있을 때만 쓴다. 허용 범위(중립 색, 포커스 그림자, 색 s hook 6개 등)는 2026-10-09에 설계 5.2·5.3 규칙으로 통합해 lib/rules.ts로 구현했고, pnpm test:brands(scripts/check-brands.ts)가 저장소의 brands/*/util.css를 검사한다(규칙 표).

SLDS 1 시절의 global 색 hook도 SLDS 2에서 그대로 쓸 수 있지만, Salesforce는 새로운 의미 기반(semantic) UI 색 hook으로 바꾸라고 권장한다. 아래 계열이 그것이다.

hook 사용 규칙

컴포넌트 CSS에서 global hook을 재정의하지 않는다공식 Color Modes 페이지의 구현 규칙은 "--slds-g-*로 시작하는 hook을 재정의하지 말고 읽기 전용으로 소비하라. 재정의하면 UI가 깨질 수 있다"이다. 밀버스의 예외는 브랜드 util.css 하나다(styling hook).

또 hook을 쓸 때는 항상 fallback을 둔다. SLDS 1과 SLDS 2를 오가는 org나 Storybook 설정 누락처럼 hook이 없는 환경에서도 깨지지 않게 하기 위해서다.

/* 좋음: 의미 hook + fallback */
.card {
  background: var(--slds-g-color-surface-container-1, #fff);
  border-color: var(--slds-g-color-border-1, #c9c9c9);
}

/* 나쁨 */
:host { --slds-g-color-accent-1: #e4002b; }   /* global hook 재정의 */
.title { color: #0176d3; }                      /* 하드코딩 색 */
.x { color: var(--slds-g-color-accent-1); }     /* fallback 없음 */

옛 --lwc token을 쓰던 코드를 옮길 때는 SLDS 2 hook을 앞에, 옛 token을 fallback으로 둔다. SLDS Linter 규칙 문서의 예는 padding: var(--slds-g-spacing-4, var(--lwc-cardBodyPadding));이다. 반대로 --lwc token의 fallback에 SLDS hook을 넣는 것은 규칙 위반이다.

base 컴포넌트의 빈틈

SLDS에 없는 것만 더하는 실제 예다. 아래 두 가지는 공식 문서로 빈틈을 확인했기 때문에 밀버스 컴포넌트로 만든다.

lightning-badge: 의미색을 고를 속성이 없다

  • 속성은 label, icon-name, icon-position(start·end), icon-alternative-text 네 개뿐이다. variant 속성이 없다
  • 색은 유틸리티 클래스로 바꾼다. 예: <lightning-badge label="완료" class="slds-theme_success"></lightning-badge>
  • SLDS 1 badge 블루프린트에는 기본, 진한(slds-badge_inverse), 가장 밝은(slds-badge_lightest), 성공·경고·오류(slds-theme_success·_warning·_error) 변형이 있다. 정보(info) 변형은 없다
  • badge의 component hook은 SLDS 1에서만 지원된다

그래서 "상태값을 넣으면 알맞은 의미색이 나오는 뱃지"를 milvusBadge로 만든다. 사용하는 쪽이 클래스 이름을 외울 필요가 없다.

lightning-combobox: 다중 선택이 안 된다

  • 공식 문서: "Multiple selection is not supported." 다중 선택이 필요하면 lightning-dual-listbox를 쓰라고 안내한다
  • lightning-select는 multiple(+ size)을 지원하지만 HTML select 요소라서 대부분의 브라우저가 스크롤 목록 상자로 그린다
  • 즉 검색 가능한 다중 선택 콤보박스는 base 컴포넌트에 없다

그래서 milvusMultiSelect를 만든다.

설계 원칙과의 연결두 컴포넌트 모두 표현 컴포넌트로 만든다(README 1.3). 데이터 조회(@wire, Apex)는 이를 감싸는 컨테이너가 맡는다. 그래야 Storybook에서 org 없이 모든 상태를 나열할 수 있다 (02 LWC의 표현 / 컨테이너 분리).

브리지: hook이 없는 항목 잇기

개념

브리지는 CSS의 세 가지 규칙 위에 서 있다. 셋을 먼저 정리한다 (2026-10-13 작성).

  • 캐스케이드 순서: 같은 요소의 같은 속성에 선언이 여럿이면 캐스케이드가 하나를 고른다. 비교 순서는 출처와 중요도(!important), 맥락, 요소에 직접 붙은 스타일, layer, 우선순위(specificity), 나타난 순서다. 앞의 기준이 모두 같으면 문서에서 나중에 나온 선언이 이긴다
  • 우선순위(specificity): 선택자의 ID, 클래스(속성 선택자·의사 클래스 포함), 타입(의사 요소 포함) 개수를 세 칸으로 센다. 예: 한 요소에 붙은 .slds-button__icon과 .slds-button__icon_large는 둘 다 0-1-0이라 문서에서 나중에 나온 규칙이 이긴다. 설치된 SLDS 2 CSS는 @layer를 쓰지만 layer 안에는 hook 정의만 있고, 일반 속성을 정하는 .slds-* 클래스 규칙은 모두 layer 밖이다(설치본 확인). 그래서 layer 밖에 있는 브리지 규칙과는 우선순위와 순서로 겨룬다
  • 사용자 정의 속성(custom property): --로 만든 속성은 캐스케이드를 따르고 부모에서 상속된다. var(--이름, 기본값)의 두 번째 인자는 그 속성이 정해지지 않았을 때 쓰는 대체 값이다. 그래서 클래스 규칙이 값을 직접 갖지 않고 var(--변수, 원래 값)을 읽으면, 변수를 정하지 않은 화면은 원래 값 그대로다

움직임을 다룰 때는 세 가지가 더 필요하다.

  • @media (prefers-reduced-motion: reduce)는 사용자가 기기에서 불필요한 움직임을 줄이는 설정을 켰는지 알려 준다. WCAG 2.3.3(AAA)은 상호작용으로 생기는 움직임을 끌 수 있게 하라고 하고, 이 미디어 쿼리를 충분한 기법(C39)으로 든다
  • max()는 쉼표로 나눈 값 가운데 가장 큰 값을 쓴다. <time> 자리에도 쓸 수 있다. max(var(--x, 0.1s), 0.01ms)는 --x에 0s나 0ms처럼 단위가 있는 값을 넣으면 0.01ms 아래로 내려가지 않는다. 단위 없는 0은 <number>라서 <time>과 섞을 수 없다(CSS Values 4, 10.2·10.9). 이 경우 선언 전체가 계산 시점에 무효가 되고(CSS Variables 3.1), 상속되지 않는 transition-duration은 초기값 0s로 돌아간다
  • transition은 지속 시간과 지연을 합한 값이 0s보다 커야 시작한다. 둘 다 0s면 transition이 없고 transitionend를 포함한 이벤트가 하나도 오지 않는다. animation은 지속 시간이 0s여도 시작·끝 이벤트를 보낸다고 스펙이 적는다. 다만 끝나기 전에 animation이 제거되면 animationend는 오지 않는다

hook이 없는 항목: 확인된 것

  • 공식 범주가 정해져 있다: SLDS 2 global hook은 색, 그림자, 테두리·반경, 글자(글꼴·크기·굵기·줄 간격), 간격, 크기 6개 범주로 나뉜다. 문서의 범주 목록에 움직임·커서·대소문자·자간이 없다. hook 값은 SLDS가 정하고 Salesforce가 언제든 바꿀 수 있다
  • 컴포넌트 hook: 컴포넌트 하나만 바꾸는 --slds-c-*는 SLDS 2에서 아직 지원하지 않는다(LWC 개발자 가이드). SLDS 사이트는 Developer Preview로 두고 운영에 쓰지 말라고 한다(styling hook)
  • 링크와 폼 요소는 지원하지 않는다: LWC 개발자 가이드의 Support Limitations는 링크(lightning-breadcrumb, lightning-formatted-* 등)와 폼 요소(lightning-input-*, lightning-textarea 등)를 custom property로 꾸미는 것을 지원하지 않는다고 적는다. 링크 밑줄, 입력창 두께가 여기에 걸린다고 본다(우리 해석)
  • 패키지 CSS에서 확인한 것: --slds-g-duration-* 8개는 정의만 있고 읽는 곳이 0이다. 컨트롤 높이 1.875rem, 입력창 두께 1px, Path 양 끝 2rem, 대문자 제목 자간 0.0625rem, 세로 내비 선택 바탕 rgb(21, 137, 238, 0.1)은 값이 박혀 있다. 팝오버 꼬리 그림자는 내부 전용 --_slds-*만 읽는다. 개체 아이콘 배경은 규칙 973개(클래스 이름 1,087개)가 --slds-c-icon-color-background에 색을 직접 정한다(설치된 2.264.2)

클래스 덮어쓰기에 대한 공식 입장

LWC 개발자 가이드의 Anti-Patterns는 SLDS 클래스의 속성을 덮어쓰는 것(예: .slds-button { padding: 16px; })을 지원하지 않는다고 적는다. SLDS가 바뀌면 예상과 다른 결과가 날 수 있고, 기본 컴포넌트의 스타일 덮어쓰기는 문서화된 styling hook을 쓸 때만 지원한다. 브리지도 클래스 규칙이라 이 입장 밖에 있다.

움직임이 끝나기를 기다리는 기본 컴포넌트

  • 토스트(toast.html·toast.js): 닫히는 중일 때 animationend에서 close 이벤트를 보낸다

만드는 방법과 화면 불변

  • 생성: scripts/bridge/generate.ts(pnpm bridge:generate)가 설치된 SLDS 2 CSS에서 각 항목의 리터럴 선언을 모두 찾는다. 원본 선택자 목록과 @media·@supports 맥락을 그대로 복사하고, 움직임은 shorthand를 두고 -duration·-timing-function만 정한다. 결과는 패키지가 관리하는 templates/force-app/main/default/staticresources/milvusBridge.css다(설계 5.6 "생성 방식")
  • 기본값 = 원래 값: 브리지 규칙은 모두 var(--milvus-*, 원래 값)을 읽는다. 브랜드가 변수를 정하지 않으면 화면이 바뀌지 않는다. tests/bridge.test.ts가 생성된 모든 선언의 기본값이 같은 선택자·맥락의 SLDS 2 원본 값과 같은지 본다
  • 원래 이기던 규칙 다시 넣기: 브리지는 SLDS 2 CSS보다 뒤에 들어온다. 같은 선택자를 복사하면 우선순위가 같은 원본 규칙을 모두 이긴다. 예: .slds-button__icon { width }를 이으면, 원래 뒤에서 이기던 .slds-button__icon_large(같은 0-1-0)가 진다. 그러면 변수를 정하지 않아도 큰 버튼 아이콘이 작아진다. 그래서 원래 이기던 같은 우선순위 규칙을 원래 값 그대로 다시 넣는다(1,110규칙)
  • 구조 변경 감지: 대상 선택자·속성·바꿀 값이 원본에서 사라지면 생성이 실패한다. 이미 만든 파일의 선택자가 원본에서 사라지면 pnpm test의 audit:brand가 실패한다(00 개념 7절)

움직임 규칙

  • 최소 0.01ms: 시간 묶음에 드는 모든 시간을 max(var(--milvus-motion-duration-*, 원래 값), 0.01ms)로 감싼다. 0을 넣으면 transition이 시작하지 않아 transitionend를 기다리는 모달이 닫히지 않을 수 있기 때문이다. animation은 스펙상 0s여도 끝 이벤트가 오지만, 선택자로 모달류를 고르지 않고 같은 규칙을 모든 시간에 쓴다. 0과 0.01ms는 눈으로 같다. 브랜드 변수에는 0.2s처럼 단위를 붙인다(단위 없는 0은 위 개념처럼 선언을 무효로 만든다). lightning 토스트의 등장 0.4s는 기본 컴포넌트 CSS에 있어 생성기 입력 밖이고 "Salesforce 고정"이다
  • 바꾸지 않는 시간: 묶음 밖 시간(아이콘·알림 애니메이션 등)과 계단 곡선은 원래 값으로 둔다(고정). 스피너는 점마다 지연이 맞물려 있어 시간을 바꾸면 순서가 어긋난다. 그래서 시간 규칙에서 빼고 줄인 움직임만 다룬다
  • 줄인 움직임: 파일 끝에 @media (prefers-reduced-motion: reduce)를 항상 넣는다. transition·animation이 있는 원본 규칙 141개(선택자 382개, 스피너 포함)의 선택자 목록에 transition-duration: 0.01ms; animation-duration: 0.01ms; animation-iteration-count: 1을 준다. 원본과 같은 선택자를 파일 마지막에 두므로 원래 이기던 규칙보다 늦게 와서 이긴다. 브랜드 선택이 아니라 항상 켜 두는 접근성 규칙이다

한계

  • native 전환 시 잃는다: 클래스 규칙은 native shadow 안으로 들어가지 않는다(00 개념 5절). 기본 컴포넌트가 native로 바뀌면 그 안에는 브리지가 닿지 않는다. 그래서 명세 항목에 "native 전환 시 잃음"을 표시하고(lib/spec-items.ts의 nativeLoss), 정적 검사의 native 열은 브리지 없이 센다
  • 공식 권고 밖이다: 위 Anti-Patterns가 말한 위험을 그대로 갖는다. SLDS 선택자나 값이 바뀌면 브리지가 효과를 잃거나 어긋날 수 있다. 위의 구조 변경 감지가 이것을 먼저 알리려는 장치다
  • npm 값으로 고정된다: 기본값과 다시 넣은 규칙은 npm SLDS 2(2.264.2) 값이다. 그 선택자에 맞는 LEX 요소 전체가 이 값을 받는다. org가 클래스 규칙에 다른 값을 내려주면 그 값이 덮인다. 브랜드 계열을 뺀 잰 표본(중립·피드백·모양·간격)에서 hook 기본값은 org와 npm이 같았지만(10/9 프로브 3.9), 클래스 규칙의 리터럴 값까지 같은지는 재지 않았다 미확인. 문제가 보이면 다시 넣는 규칙을 :where(대상 선택자)로 좁힌다(설계 5.6)
  • 파일 크기: 358,310바이트, gzip 33,491바이트다. 브리지 규칙 175개, 개체 아이콘 973규칙, 다시 넣은 원본 규칙 1,110개, 줄인 움직임 141규칙이다.   • org에서 직접 재지 않았다: 클래스 규칙이 닿는 것은 10/9 프로브에서 .slds-button 한 줄로 확인했다(lightning-button 안과 표준 헤더 버튼 대부분, 더 구체적인 선택자가 이기는 버튼은 예외). 생성된 브리지 파일을 org에 올려 화면을 비교하지는 않았다 미확인. lightning-icon이 JS 색보다 이 hook을 먼저 읽는다는 것도 소스를 읽어 확인했을 뿐 org에서는 보지 않았다

스스로 점검

Q1. 우리 org(SLDS 2)에서 --slds-c-button-radius-border로 버튼 모서리를 바꾸면 되나?

안 된다. component hook(--slds-c-*)은 LWC 개발자 가이드 기준 SLDS 2에서 아직 지원되지 않고, SLDS 사이트도 Developer Preview로 두고 운영에 쓰지 말라고 한다. 먼저 정말 모양이 달라야 하는지 묻는다(기본 우선). 필요하면 util.css에 --slds-s-button-radius-border나 global hook을 쓰되 공식 권고 밖임을 알고 쓴다(--slds-s-*는 Salesforce 내부용 private hook으로 분류된다). hook·브리지로 안 되는 모양이면 opt-in milvusOverride.css(마지막 수단, 공식 권고 밖)를 쓴다. 모양만 바꾸려고 새 컴포넌트를 만들지 않는다 (2026-10-09 갱신).

Q2. 브랜드 A만 강조색을 빨강으로 하고 싶다. --slds-g-color-accent-1을 util.css에서 바꾸면 되나?

안 된다. 색의 원본은 org 테마다. Themes and Branding(또는 BrandingSet 메타데이터)의 브랜드 색으로 정하고 accent 계열이 그것을 따라가게 둔다. lib/rules.ts의 util.css 규칙(검사는 pnpm test:brands)도 accent 계열 재정의를 막는다 (2026-10-09 갱신).

Q3. var(--slds-g-color-surface-container-1)만 쓰면 무엇이 문제인가?

fallback이 없다. hook이 없는 환경에서 값이 비어 깨진다. no-slds-var-without-fallback 규칙에 걸린다. var(--slds-g-color-surface-container-1, #fff)처럼 쓴다.

Q4. 상태별 색 뱃지가 필요하다. 왜 lightning-badge에 variant="success"를 주지 않나?

lightning-badge에는 variant 속성이 없다(label, icon-name, icon-position, icon-alternative-text뿐). 유틸리티 클래스로 색을 바꿀 수는 있지만, 상태값만으로 의미색을 고르게 하려고 milvusBadge를 만든다.

Q5. 공식 문서에 npx @salesforce-ux/slds-linter lint라고 나온다. 어떻게 실행하나?

pnpm dlx @salesforce-ux/slds-linter lint force-app. 프로젝트에 설치했다면 pnpm exec slds-linter lint force-app. pnpm dlx는 패키지를 의존성으로 설치하지 않고 받아서 실행한다.

Q6. VF 페이지에서 util.css가 효과가 없다. util.css를 고쳐야 하나?

아니다. 2026-10-08 프로브에서 원인은 <apex:slds/>가 SLDS 1로 그려진 것이었다. SLDS 2 CSS를 넣으면 util.css가 작동했다.
