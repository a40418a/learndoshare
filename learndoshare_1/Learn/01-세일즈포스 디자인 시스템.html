세일즈포스 디자인 시스템

SLDS가 무엇으로 이루어져 있는지, SLDS 2에서 무엇이 바뀌었는지, 그리고 밀버스가 SLDS 위에서 무엇을 추가하고 무엇을 건드리지 않는지 정리한다.

예상 1.5시간선행 없음2026-09-26 공식 문서 · 패키지로 확인SLDS 사이트 표기 Summer '26 v3.3.3

왜 알아야 하나

밀버스의 첫 번째 원칙은 "SLDS를 최대한 쓰고, 없는 것만 추가한다"이다. 무엇이 "없는 것"인지 판단하려면 SLDS가 무엇을 제공하는지 먼저 알아야 한다.

또 우리 org는 SLDS 2 테마(Milvus_DesignSystem)를 쓴다. 인터넷 자료 상당수는 SLDS 1 기준이라, 그대로 따라 하면 SLDS 2에서 동작하지 않거나 가이드라인을 어기게 된다.

무엇을 가져다 쓰나

블루프린트, base 컴포넌트(lightning-*), styling hook

무엇을 하지 않나

--slds-g-* 재정의(opt-in override.css 예외), SLDS 클래스 덮어쓰기, 하드코딩 색

무엇을 추가하나

SLDS에 없는 컴포넌트, 브랜드 차이를 담는 --milvus-* 변수

SLDS 2는 SLDS 1의 블루프린트를 그대로 재사용한다. 바뀐 것은 블루프린트가 아니라 그 아래의 CSS 구조와 hook이다.

SLDS 1과 SLDS 2

SLDS 2는 Spring '25에 소개됐다. 구조와 시각 디자인을 분리하는 새 CSS 프레임워크 위에 만들어졌고, 시각 디자인은 styling hook으로 바뀐다.

항목SLDS 1SLDS 2
기본 테마Lightning BlueCosmos (Winter '25에 "Enhanced Lightning UI"라는 이름으로 베타)
제공 상태계속 사용 가능Winter '26부터 모든 에디션 GA. 새 org는 기본, 기존 org는 Themes and Branding에서 선택(opt-in)
다크 모드없음Winter '26부터 SLDS 2 테마에서 지원
design token (--lwc-*)사용 가능지원 안 함 deprecated. 예: --lwc-colorBackgroundAlt
component hook (--slds-c-*)사용 가능아직 지원 안 함
SLDS 2가 적용되지 않는 곳모바일 앱, 빌더(Flow Builder, Lightning App Builder), Lightning Out, Experience Cloud는 SLDS 2를 지원하지 않고 계획도 없다고 공식 문서에 적혀 있다. 이 화면들에서는 SLDS 1 기준으로 보인다는 점을 기억한다.
현재 상태org learndoshare_1은 SLDS 2 테마 Milvus_DesignSystem을 쓴다 (05 테마 동기화에서 조회). 그래서 밀버스 컴포넌트 CSS는 --lwc-* token과 --slds-c-* hook에 기대면 안 된다.

styling hook

접두사종류우리가 써도 되나
--slds-g-*global hook. 색, 폰트, 간격, 크기, 반경, 그림자, 시간(duration)읽기만 재정의 금지
--slds-c-*component hook. 특정 컴포넌트 하나의 모양 조절SLDS 2에서 안 됨 SLDS 1에서만 사용 가능
--_slds-*, --slds-s-*private / 내부용금지 내부 구현이라 예고 없이 바뀐다
--milvus-*밀버스가 정의하는 사내 변수사용 브랜드 root에서만 정의
component hook에 대한 공식 입장Salesforce 문서는 "component styling hook은 SLDS 2에서 아직 지원되지 않으며, 커스텀 컴포넌트가 이를 쓴다면 당분간 org를 SLDS 1 테마로 유지하라"고 안내한다. 우리 org는 이미 SLDS 2이므로 component hook은 선택지가 아니다.

SLDS 1 시절의 global 색 hook도 SLDS 2에서 여전히 동작하지만, Salesforce는 새로운 의미 기반(semantic) UI 색 hook을 쓰라고 권장한다. 아래 계열이 그것이다.

색 hook 계열

모두 --slds-g-color-로 시작한다. 표에는 접두사를 뺀 나머지만 적었다.

계열hook (접두사 생략)용도
Accentaccent-1..3, accent-container-1..3, accent-dark-1..2, accent-light-1..2, on-accent-1..3, border-accent-1..3브랜드 강조색. org 브랜드 색을 따라간다
Surfacesurface-1..3, surface-container-1..3, surface-inverse-1..2, surface-container-inverse-1..2, on-surface-1..3, on-surface-inverse-1..2배경과 그 위의 글자
Borderborder-1..2, border-error-1..2, border-success-1..2, border-inverse-1..2, border-disabled-1..2, border-warning-1테두리
Feedbackerror-1, success-1, warning-1, info-1, error-container-1..2, success-container-1..2, warning-container-1, info-container-1, on-error-1..2, on-success-1..2, on-warning-1, on-info-1성공·경고·오류·정보 의미색

  • 이름 규칙: container는 면(배경), on-*는 그 위에 올라가는 글자·아이콘 색이다. success-container-1 배경에는 on-success-1 글자를 쓴다
  • 의미 hook 우선: neutral-base-100(유틸리티)보다 surface-container-1(의미)을 쓴다. 다크 모드나 테마가 바뀌어도 의미에 맞는 색으로 따라간다
  • accent는 브랜드 색: accent-1은 org의 브랜드 색으로 결정된다(themeOwned). 관리자가 브랜드 색을 바꾸면 accent 계열이 함께 바뀐다

패키지 @salesforce-ux/design-system 2.264.1의 CSS에서 직접 세어 보니 --slds-g-color-* hook이 330개 정의돼 있다. 이 CSS를 Storybook에 넣으면 org 없이도 hook을 쓸 수 있다. 실제로 확인한 값의 예는 다음과 같다.

--slds-g-color-accent-1: var(--lwc-brandPrimary, var(--slds-r-color-brand-60));
--slds-g-color-surface-container-1: #fff;
--slds-g-color-on-accent-1: var(--slds-g-color-neutral-base-100);
--slds-g-color-border-1: var(--slds-g-color-neutral-base-80);

관련 패키지: hook·token 패키지는 @salesforce-ux/design-tokens (4.1.0). @salesforce-ux/sds-styling-hooks는 deprecated이므로 설치하지 않는다.

hook 사용 규칙

global hook을 재정의하지 않는다공식 Color Modes 페이지의 모범 사례는 "--slds-g-*로 시작하는 hook을 재정의하지 말고 읽기 전용으로 소비하라. 재정의하면 UI가 깨질 수 있다"이다.

또 hook을 쓸 때는 항상 fallback을 둔다. hook이 없는 환경(SLDS 1 테마, Storybook 설정 누락 등)에서도 깨지지 않게 하기 위해서다.

/* 좋음: 의미 hook + fallback */
.card {
  background: var(--slds-g-color-surface-container-1, #fff);
  /* 기존 --lwc token을 쓰던 코드를 옮길 때: 옛 token을 fallback으로 */
  border-color: var(--slds-g-color-border-1, var(--lwc-colorBorder));
}

/* 나쁨 */
:host { --slds-g-color-accent-1: #e4002b; }   /* global hook 재정의 */
.title { color: #0176d3; }                      /* 하드코딩 색 */
.x { color: var(--slds-g-color-accent-1); }     /* fallback 없음 */

공식 권장 패턴은 var(--slds-g-color-surface-container-1, var(--lwc-colorBackgroundAlt))처럼 SLDS 2 hook을 앞에, 옛 token을 fallback으로 두는 것이다. 반대로 --lwc token의 fallback에 SLDS hook을 넣는 것은 금지된다.

위 예시의 --lwc-colorBorder미확인 fallback으로 쓴 token 이름은 설명용이다. 실제 이전 작업 때는 원래 코드에 있던 token 이름을 그대로 쓴다.

base 컴포넌트의 빈틈

"없는 것만 추가한다"의 실제 예다. 아래 두 가지는 공식 문서로 빈틈을 확인했기 때문에 밀버스 컴포넌트로 만든다.

lightning-badge: 의미색을 고를 속성이 없다

  • 속성은 label, icon-name, icon-position, icon-alternative-text 네 개뿐이다. variant 속성이 없다
  • 색은 유틸리티 클래스로 바꾼다. 예: <lightning-badge label="완료" class="slds-theme_success"></lightning-badge>
  • badge 블루프린트에는 success / warning / error / info / inverse / light 변형이 있다
  • badge의 component hook은 SLDS 1 전용이다

그래서 "상태값을 넣으면 알맞은 의미색이 나오는 뱃지"를 milvusBadge로 만든다. 사용하는 쪽이 클래스 이름을 외울 필요가 없고, 색은 Feedback 계열 hook을 따른다.

lightning-combobox: 다중 선택이 안 된다

  • 공식 문서: "Multiple selection is not supported." 다중 선택이 필요하면 lightning-dual-listbox를 쓰라고 안내한다
  • lightning-select는 multiple(+ size)을 지원하지만 브라우저 기본 목록 상자로 그려진다
  • 즉 검색 가능한 다중 선택 콤보박스는 base 컴포넌트에 없다

그래서 milvusMultiSelect를 만든다.

설계 원칙과의 연결두 컴포넌트 모두 표현 컴포넌트로 만든다. 데이터 조회(@wire, Apex)는 이를 감싸는 컨테이너가 맡는다. 그래야 Storybook에서 org 없이 모든 상태를 나열할 수 있다 (06 도구 비교).

Themes and Branding

Setup의 Themes and Branding은 org 전체의 브랜드 색과 로고를 정하는 곳이다. 밀버스의 "색은 org에서 온다" 원칙의 출발점이다.

  • org에서 활성 테마는 하나다. 커스텀 테마는 최대 300개까지 만들 수 있다
  • 내장 테마는 편집하거나 복제할 수 없다
  • Salesforce Classic과 네이티브 모바일 앱에는 적용되지 않는다
  • SLDS 2 테마에서는 배경색, 배경 이미지, 전역 헤더 색을 설정할 수 없다 (접근성 때문)
  • 폰트 설정은 문서에 없다. 폰트는 org에서 오지 않는다
  • 앱 단위 브랜딩(App Manager)은 내장 테마(Lightning Lite / Blue)를 항상 덮어쓴다. 커스텀 테마를 덮어쓰려면 App Manager에서 덮어쓰기 옵션을 켜야 한다
색과 폰트의 출처브랜드 색 → org Themes and Branding (배포 불필요) → accent hook이 따라감. 폰트·브랜드 고유 모양 → brands/<브랜드>/root.css의 --milvus-* 변수 (배포 필요). org 테마 데이터 구조는 05 테마 동기화에 있다.

브랜드별 버튼 디자인

이 절이 가장 중요하다"브랜드마다 버튼 모양(모서리, 굵기 등)을 다르게 해 달라"는 요청은 반드시 나온다. SLDS 2에서는 lightning-button의 모양을 브랜드별로 바꾸는 공식 방법이 없다. component hook(--slds-c-button-*)은 SLDS 1 전용이고, global hook은 읽기 전용이기 때문이다.

밀버스의 대응 순서

순서요구방법판단
1브랜드 색만 다르면 된다org Themes and Branding에서 브랜드 색 지정. lightning-button이 accent 색을 따라간다권장 코드 변경 없음
2특별한 요구 없음lightning-button을 그대로 쓴다기본값
3브랜드 고유 모양이 꼭 필요하다root.css에 --milvus-button-* 정의 + SLDS 버튼 블루프린트(slds-button 마크업) 기반 milvusButton. fallback은 SLDS 기본값구현함 파일럿 컴포넌트
4고객사가 lightning-button 자체의 모양까지 바꾸길 원한다opt-in 확장 계층 brands/<브랜드>/override.css에서 모양 관련 --slds-g-*(반경, 폰트)만 재정의. milvus.config.json의 "overrides": true인 브랜드에만 로드공식 권고 밖 확인 후에만, 릴리스마다 재확인

3번 방법의 예시

/* 브랜드 차이는 여기서 --milvus-* 로만 표현한다. 색은 넣지 않는다(org에서 온다) */
:root {
  --milvus-button-radius: var(--slds-g-radius-border-pill, 15rem);
  --milvus-button-font-weight: var(--slds-g-font-weight-7, 700);
}
<template>
  <button class="slds-button slds-button_brand milvus-button" type="button" onclick={handleClick}>
    {label}
  </button>
</template>
/* .slds-* 클래스를 덮어쓰지 않고, 자기 클래스에만 스타일을 준다 */
.milvus-button {
  /* 브랜드 값 → 없으면 SLDS hook → 없으면 SLDS 기본값 */
  border-radius: var(--milvus-button-radius, var(--slds-g-radius-border-2, 0.25rem));
  font-weight: var(--milvus-button-font-weight, inherit);
}

이렇게 하면 브랜드 root가 없는 곳에서는 SLDS 기본 버튼과 똑같이 보이고, 색은 여전히 slds-button_brand가 accent hook을 따라간다.

  • --slds-g-radius-border-2(0.25rem), --slds-g-radius-border-pill(15rem), --slds-g-font-weight-7(700)은 @salesforce-ux/design-system 2.264.1 CSS에서 이름과 값을 직접 확인했다. SLDS 버튼 블루프린트의 기본 반경 fallback도 0.25rem이다
  • 반경 hook은 radius-border-1..4, pill, circle이 있다
결정 (2026-09-26)공식 권고는 아니지만 고객사별 니즈가 다양하므로 milvusButton을 파일럿으로 구현한다. 그래도 고객사가 lightning-button 자체를 바꾸길 원하면 4번(opt-in override.css)을 쓴다. 이때 색(accent 계열)은 재정의하지 않는다. 색은 org 테마가 원본이다. Salesforce가 SLDS 2 component hook을 지원하면 4번을 그쪽으로 옮긴다.
대가를 알고 쓴다milvusButton은 lightning-button이 해 주던 것(아이콘 배치, 비활성 처리, 접근성 속성 등)을 직접 맞춰야 한다. 그래서 "모양이 꼭 달라야 하는가"를 먼저 묻고, 필요한 브랜드에서만 쓴다. 미확인 SLDS 2 org 화면에서 slds-button_brand 마크업이 lightning-button과 완전히 같게 보이는지는 아직 비교하지 않았다.

스스로 점검

Q1. 우리 org(SLDS 2)에서 --slds-c-button-radius-border로 버튼 모서리를 바꾸면 되나?

안 된다. component hook(--slds-c-*)은 SLDS 1에서만 지원된다. 브랜드 고유 모양이 필요하면 root.css의 --milvus-button-*와 milvusButton을 쓴다. lightning-button 자체까지 바꿔야 하면 opt-in override.css를 쓰되 공식 권고 밖임을 알고 쓴다.

Q2. 브랜드 A만 강조색을 빨강으로 하고 싶다. --slds-g-color-accent-1을 root.css에서 바꾸면 되나?

안 된다. global hook 재정의는 공식 가이드라인 밖이고, 밀버스는 opt-in override.css에서도 색(accent 계열)은 재정의하지 않는다. 색은 org Themes and Branding의 브랜드 색으로 정하고, accent 계열이 그것을 따라가게 둔다.

Q3. var(--slds-g-color-surface-container-1)만 쓰면 무엇이 문제인가?

fallback이 없다. hook이 없는 환경에서 값이 비어 깨진다. no-slds-var-without-fallback 규칙에 걸린다. var(--slds-g-color-surface-container-1, #fff)처럼 쓴다.

Q4. 상태별 색 뱃지가 필요하다. 왜 lightning-badge에 variant="success"를 주지 않나?

lightning-badge에는 variant 속성이 없다(label, icon-name, icon-position, icon-alternative-text뿐). 유틸리티 클래스로 색을 바꿀 수는 있지만, 상태값만으로 의미색을 고르게 하려고 milvusBadge를 만든다.

Q5. 공식 문서에 npx @salesforce-ux/slds-linter lint라고 나온다. 어떻게 실행하나?

pnpm dlx @salesforce-ux/slds-linter lint force-app. 프로젝트에 설치했다면 pnpm exec slds-linter lint force-app. pnpm 대응은 pnpm의 일반 동작이며 Salesforce 문서에 적힌 것은 아니다.
