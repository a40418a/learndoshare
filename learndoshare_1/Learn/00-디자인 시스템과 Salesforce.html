디자인 시스템과 Salesforce

디자인 시스템이 무엇으로 이루어지는지, Salesforce가 그것을 SLDS와 styling hook으로 어떻게 구현했는지, 밀버스가 그 위에 무엇을 얹는지 정리한다. 각 절은 개념 → Salesforce에서는 → 밀버스에서는 → 직접 확인하기 순서다.

1. 디자인 시스템이란

개념

디자인 시스템은 여러 화면과 제품이 같은 모양과 동작을 갖게 하는 공유 자산이다. SLDS 사이트는 디자인 시스템의 기반을 "재사용할 코드, 통일된 시각 언어, 접근성 기준, 원칙"의 조합이라고 설명한다. 이 문서는 다섯 가지로 나눠 본다.

구성무엇인가근거
디자인 토큰색, 간격, 글자 크기, 반경, 그림자 같은 디자인 값에 이름을 붙인 것. 하드코딩한 값 대신 이름으로 참조한다SLDS Styling API, SLDS 1 Design Tokens. 도구 사이에서 토큰을 주고받는 표준 형식은 W3C Design Tokens Community Group이 만든다(2025.10이 첫 안정판)
컴포넌트특정 기능이나 동작을 맡는 UI의 독립된 요소. 버튼, 입력창, 카드 등SLDS Components
패턴여러 컴포넌트를 조합해 같은 문제를 같은 방식으로 푸는 방법. 이 문서에서 쓰는 정의다SLDS 2 사이트의 "Agentic Patterns" 페이지는 AI 에이전트와 함께 일하는 화면(agentic experiences)을 만들 때 쓰는 패턴을 모았다. 예: AI 카드, 어시스턴트 패널, 피드 (2026-10-09 갱신)
원칙결정이 갈릴 때 기준이 되는 가치SLDS 2의 원칙 5개: Clarity, Innovation, Scalability, Empowerment, Inspiration
운영누가 무엇을 바꾸는가. 값의 주인, 바꾸는 절차, 알리는 방법SLDS의 역할 구분(관리자, 디자이너, 개발자)과 "hook 값은 SLDS가 정한다"는 규칙

Salesforce에서는

  • 토큰은 CSS 사용자 정의 속성인 styling hook으로 구현된다. 공식 설명은 "SLDS는 디자인 토큰을 CSS custom property, 곧 styling hook에 대응시킨다"이다 (3절)
  • 컴포넌트는 두 종류다. 동작까지 들어 있는 기본 컴포넌트(lightning-*)와, HTML·CSS만 있는 블루프린트(slds-* 클래스)다 (2절)
  • 운영: global styling hook의 값은 SLDS가 정하고, Salesforce가 언제든 바꿀 수 있으며 릴리스 노트로 알린다. 브랜드 색과 로고는 관리자가 Themes and Branding에서 정한다. 개발자는 hook을 읽기만 한다
  • SLDS 2 전환 안내는 일을 관리자(전환 주도, 샌드박스, 사용자 공지), 디자이너(시각 일관성 검증), 개발자(SLDS Linter, 코드 수정, 테스트)로 나눈다

밀버스에서는

밀버스는 SLDS를 대체하지 않는다. README 1.3의 첫 원칙이 "SLDS가 제공하는 것을 최대한 쓴다"이다. 그래서 밀버스의 운영은 "누가 무엇을 바꾸는가"를 Salesforce의 구분 위에 한 칸 더 얹는 일이다.

무엇을누가어디서
hook의 기본값, 기본 컴포넌트SalesforceSLDS 2 CSS, lightning-* (우리가 고치지 않는다)
브랜드 색, 로고관리자 또는 배포org 테마의 BrandingSet (4절)
모양(반경, 간격 등)브랜드 요청이 있을 때만 개발자util.css (8절)
SLDS에 없는 컴포넌트디자인 시스템 오너force-app/main/default/lwc/milvus*

직접 확인하기

  • SLDS 사이트의 Visual Language 페이지에서 원칙 5개를 읽는다
  • Global Styling Hooks 페이지 첫머리에서 "SLDS determines the values of global styling hooks" 문장을 찾는다. 운영의 주인이 누구인지 알려 주는 문장이다

2. SLDS

개념

디자인 시스템도 버전이 바뀐다. 구조(마크업과 레이아웃)와 시각 디자인(색, 반경 등)을 분리해 두면, 테마만 바꿔 모양을 바꿀 수 있다. 또 컴포넌트를 "동작까지 든 완성품"과 "모양만 정한 틀"로 나눠 제공하면, 쓰는 쪽이 상황에 맞게 고를 수 있다.

Salesforce에서는

SLDS(Salesforce Lightning Design System)는 두 버전이 있다. SLDS 2는 Spring '25에 소개됐고, 원래 SLDS는 SLDS 1이라 부른다. SLDS 2는 구조와 시각 디자인을 styling hook으로 분리하는 새 CSS 프레임워크 위에 만들어졌다.

3. 토큰의 Salesforce 이름: styling hook

개념

토큰은 층으로 흐른다. 값 → 의미 있는 이름 → 특정 컴포넌트의 이름 → 실제 CSS 속성 순서다. 위층 값을 한 번 바꾸면 그것을 참조하는 모든 컴포넌트가 바뀌고, 아래층 이름을 바꾸면 그 컴포넌트만 바뀐다. 웹에서는 이 이름을 CSS 사용자 정의 속성(--이름)으로 만들고 var()로 읽는다.

Salesforce에서는

SLDS 사이트의 공식 흐름은 "디자인 토큰 값 → global styling hook → 컴포넌트 수준 styling hook → 컴포넌트 구현"이다. 예: #066AFE → --slds-g-color-accent-container-1 → --slds-c-button-color-background → background-color.

설치된 SLDS 2 CSS를 열어 보면 SLDS 사이트의 흐름에 없는 두 접두사가 더 있다. 그래서 실제 체인은 네 단계다.

접두사무엇인가근거
--slds-r-*원래 값(팔레트). @layer defaults의 :where(html)에 85개: brand, error, info, success, warning 계열이 17단계씩패키지 CSS. 공식 문서에는 설명이 없다. "r"이 무엇의 약자인지 미확인
--slds-g-*global hook. 이름 규칙 --slds-g-{분류}-{속성}-{변형}. 색, 그림자, 테두리·반경, 글자, 간격, 크기공식 문서. 패키지 CSS의 두 번째 @layer defaults에 524개
--slds-s-*컴포넌트별 기본값. @layer shared의 :where(html)에 107개. 대부분 g hook을 가리킨다패키지 CSS. SLDS 사이트에는 설명이 없다. Salesforce의 SLDS Linter ESLint 플러그인(@salesforce-ux/eslint-plugin-slds) README는 --_slds-와 함께 Salesforce 내부용 private hook으로 분류한다(규칙 no-slds-private-var). "s"가 무엇의 약자인지 미확인 (2026-10-09 갱신)
--slds-c-*컴포넌트 수준 hook. 사용자가 덮어쓰라고 열어 둔 자리공식 문서. SLDS 2에서는 Developer Preview / 미지원(2절)
/* r: 원래 값 (@layer defaults) */
--slds-r-color-brand-50: #066afe;
/* g: 의미 있는 이름 (@layer defaults) */
--slds-g-color-accent-container-1: var(--slds-r-color-brand-50);
--slds-g-radius-border-pill: 15rem;
/* s: 컴포넌트별 기본값 (@layer shared) */
--slds-s-button-radius-border: var(--slds-g-radius-border-pill);
/* 구현: c가 있으면 c, 없으면 s, 그것도 없으면 g */
.slds-button {
  border-radius: var(
    --slds-c-button-radius-border,
    var(--slds-s-button-radius-border, var(--slds-g-radius-border-2))
  );
}

즉 버튼 모서리는 c hook이 없으면 --slds-s-button-radius-border를 읽고, 그 값이 --slds-g-radius-border-pill(15rem)이라 알약 모양이 된다.

공식 규칙: global hook은 읽기만 한다Global Styling Hooks 페이지의 규칙은 "참조한다, 값을 다시 할당하지 않는다, SLDS 1에서도 그려지도록 fallback을 둔다" 세 가지다. Color Modes 페이지도 "--slds-g-*를 재정의하지 마라. UI가 깨질 수 있다"고 적는다. 반면 관리자의 Themes and Branding은 "특정 hook 값을 브랜드에 맞게 덮어쓰는 방식"으로 동작한다고 Styling API 페이지가 설명한다. hook 값을 바꾸는 공식 경로는 org 테마다.
  • SLDS 1의 디자인 토큰(--lwc-*)은 SLDS 2에서 동작하지 않는다. LWC 개발자 가이드는 global hook으로 바꾸라고 안내한다
  • 권장 쓰는 법: var(--slds-g-color-surface-container-1, var(--lwc-colorBackgroundAlt))처럼 SLDS 2 hook을 앞에, 옛 값을 fallback으로 둔다(SLDS 2 전환 안내의 예)

밀버스에서는

  • 컴포넌트 CSS는 hook을 읽기만 하고 fallback을 반드시 둔다 (CLAUDE.md 3장)
  • util.css는 공식 권고 밖이라는 것을 알고 택한 예외다. 지금 규칙(2026-10-09 갱신, 설계 5.2·5.3. 구현 lib/rules.ts, 검사 pnpm test:brands의 scripts/check-brands.ts): :root 블록 하나에 이름에 color가 없는 --slds-g-*(글꼴 제외), 포커스 그림자, 중립 색(light-dark()), 피드백 색, SLDS 2·기본 컴포넌트 CSS가 var()로 읽는 --slds-s-*(색은 hover·선택 바탕 6개만), 밀버스가 읽는 --milvus-*, letter-spacing만 쓴다. 클래스 규칙, @font-face, --slds-c-*, --sds-c-*, 브랜드 색(accent·brand) 재정의, 읽는 곳이 없는 이름은 금지다. 전체 표는 01 SLDS에 있다. 예전 scripts/check-brands.mjs(PR #19 규칙)는 지웠다
  • --slds-s-* 허용(#18, PR #19): 공식 권고 밖이고 native 전환 때 효과가 사라질 수 있다는 것을 알고 허용했다(README 2장, 설계 1장). 위의 private 분류는 2026-10-09에 확인했고, 설계 15장에 "허용 유지 여부 미정"으로 올렸다. 기본 우선에서는 util.css를 브랜드 요청이 있을 때만 쓰므로 당장 바꾸지 않는다. 01 문서도 같은 내용이다 (2026-10-09 갱신)
  • 규칙 통합 (2026-10-09 구현): 전 컴포넌트 분석(7절)에 따라 위 규칙으로 넓혔고, 서로 달랐던 검사 스크립트·CLAUDE.md·설계 5.2를 하나로 맞췄다(Task 7)
  • 기본 우선(2026-10-09 결정): 기본 상태에서는 util.css가 비어 있다. 브랜드 요청이 있을 때만 쓴다 (8절)

4. 브랜드는 어디서 오는가

개념

브랜드 값은 원본을 한 곳에 두고 나머지를 계산하게 해야 어긋나지 않는다. 특히 색은 "입력한 색" 하나에서 여러 단계의 팔레트를 만들고, 글자와 배경의 대비 기준을 넘는 단계를 골라 쓴다. SLDS 2 Color Modes 페이지는 WCAG 2.1에 따라 일반 글자와 아이콘은 4.5:1, 큰 글자(18pt, 굵게 14pt)는 3:1 이상을 지키라고 적는다 (2026-10-09 갱신).

Salesforce에서는

  • Themes and Branding(Setup): 테마는 화면의 모양을 정하는 시각 스타일 묶음이다. 기본 테마를 고르거나 커스텀 테마를 만든다. SLDS 2 테마를 활성화하면 org에 SLDS 2가 켜진다
  • 관리자는 브랜드 이미지를 올리고 브랜드 색을 고른다. SLDS 2는 WCAG 대비를 만족하는 보조 accent 색을 자동으로 고른다

  • org 실측(2026-10-08): BrandingSet과 LightningExperienceTheme은 배포로 만들어진다. 활성 테마 이름 한 필드만 담은 설정을 배포하면 그 필드만 바뀐다. 테마를 지우면 그 테마의 BrandingSet도 지워진다
  • 팔레트 규칙(실측으로 역산, 2026-10-05): 단계마다 CIELAB 명도 L*가 고정이고(95→96, 90→91, 50→49, 40→39, 30→29, 20→19, 10→8), 색상각은 유지한다. 그래서 원본 브랜드 색은 그대로 들어가지 않는다. 예: #0176D3 → 50단계 #2976ca (README 3장, lib/palette.ts)

  • 50단계는 L* 49라서 흰 글자 대비가 모든 색에서 4.62~4.68:1이다. 그래서 브랜드 색을 막지 않고, 입력한 색·실제 버튼 색(50)·링크 색(40)을 함께 보여 준다(설계 5.4)
  • 밀버스는 지금 BRAND_COLOR와 BRAND_IMAGE만 다룬다(설계 5.1). SLDS 2 전용 ACCENT_COLOR_* 속성을 쓸지는 설계 15장에 미정으로 올라 있다 (2026-10-09 갱신)
  • pnpm milvus init --brand <이름>은 Salesforce 기본색 #0176D3으로 BrandingSet과 테마 파일을 만든다. --from-org는 org의 활성 테마·BrandingSet·로고를 받아 그대로 쓰고, 활성 테마가 SLDS 2(SLDS_v2)가 아니면 아무것도 쓰지 않고 멈춘다(설계 4.1, Task 11 구현, 2026-10-12 갱신)

5. shadow DOM과 스타일이 닿는 범위

개념

shadow DOM은 웹 컴포넌트의 내부 DOM을 감싸 바깥의 HTML, CSS, JavaScript가 건드리지 못하게 하는 표준이다. 페이지의 CSS 규칙(예: .slds-button { … })은 shadow 트리 안으로 들어가지 않는다. 그러나 상속은 경계를 넘는다. shadow 트리의 맨 위 요소는 호스트 요소에서 상속받고, --로 만든 사용자 정의 속성은 기본적으로 상속된다. 그래서 styling hook(사용자 정의 속성)은 닿고, 클래스 규칙은 닿지 않는다.

Salesforce에서는

  • LWC는 Lightning Experience와 Experience Cloud에서 synthetic shadow(폴리필)를 쓴다. Lightning Out처럼 그 밖에서 쓰면 native shadow로 그린다
  • synthetic shadow에서는 앱이 전역 스타일시트로 DOM 전체를 꾸민다. native shadow에서는 그렇게 할 수 없고, 컴포넌트 스타일을 번들에 넣어야 한다
  • Salesforce는 mixed shadow mode(베타)를 거쳐 native shadow로 옮겨 가겠다고 적었다. 컴포넌트는 static shadowSupportMode = "native"로 native를 택한다
  • npm lightning-base-components 1.28.19-alpha는 package.json의 lwc.nativeShadowEnabledComponents에 156개를 native 지원으로 지정해 두었다(설치본 확인). org에 언제 적용될지는 미확인
문서 수준 CSS가 넣은 것synthetic (지금 org)native (전환 뒤)
:root의 --slds-g-*닿음상속으로 닿음. 그 hook을 읽는 곳이 컴포넌트 CSS에 남아 있을 때만 효과
:root의 --slds-s-*닿음 (실측)기본 컴포넌트의 native CSS가 직접 읽는 이름에만 닿을 가능성이 높다 추정
.slds-* 클래스 규칙닿음 (실측 2026-10-09. 더 구체적인 선택자가 이기는 곳은 예외)닿지 않음

밀버스에서는

  • org 실측(2026-10-07, #16): LEX는 기본 컴포넌트를 synthetic으로 그린다. 홈, 계정 목록, 새 계정 화면에서 쟀고 native는 내부 primitive 3개뿐이었다. Storybook도 org와 같게 전부 synthetic으로 그린다(README 3장)
  • org 실측(2026-10-08): LEX에서 loadStyle로 넣은 CSS는 문서 head에 들어가, 프로브 컴포넌트뿐 아니라 같은 페이지의 표준 헤더 버튼과 document.body에 붙는 LightningAlert 모달까지 바꿨다. 컴포넌트 hook --slds-s-input-radius-border도 닿았다
  • org 실측(2026-10-09, 2026-10-12 갱신): 프로브 화면의 lightning-* 호스트 90개 가운데 data-render-mode가 있는 것은 0개였다(전부 synthetic). 클래스 규칙도 쟀다. loadStyle로 넣은 .slds-button { border-radius: 0 }이 lightning-button 안의 버튼과 같은 화면의 표준 헤더 버튼 대부분을 0px로 바꿨다. 더 구체적인 선택자가 이기는 버튼(appdev-panel-button 4px, search-button 8px, 즐겨찾기 별 240px)은 예외였다. util.css의 중립 색·피드백 색 hook은 페이지 바탕, 전역 헤더, 글자·테두리, 시스템 경고 배너, body에 붙는 표준 토스트까지 바꿨다(info 토스트만 못 잼)
  • native 전환 위험: 전환되면 클래스 규칙(milvusBridge.css)은 사라지고 hook으로 바꿀 수 있는 비율도 떨어진다(7절의 "native" 열). 소스 분석상 "native에서는 --slds-s-*가 닿지 않는다"는 지나친 서술이고, 기본 컴포넌트의 native CSS가 직접 읽는 s 이름에는 닿을 가능성이 높다 추정, 실측 필요
  • 감지 (2026-10-09 구현): 기본 컴포넌트는 synthetic이 아닐 때 호스트에 data-render-mode="shadow"를 붙인다(LBC 소스). 밀버스 컴포넌트가 첫 렌더 뒤 c/milvusScript의 detectNativeShadow로 자기 템플릿 안의 lightning-* 호스트에서 이것을 찾아 개발 콘솔에 경고한다(설계 9.2, 02 LWC). org에서 울리는지는 아직 보지 않았다

직접 확인하기

  • LEX 화면에서 DevTools Elements 패널을 연다. native 컴포넌트는 #shadow-root 아래에 보이고, synthetic 컴포넌트는 그렇지 않다(LWC 개발자 가이드의 설명)
  • lightning-button 호스트 요소에 data-render-mode 속성이 있는지 본다
  • 자기 컴포넌트에서는 this.template.synthetic이 synthetic이면 true, native면 undefined다

7. 전 컴포넌트 분석

개념

hook이 있다는 것과 hook으로 바꿀 수 있다는 것은 다르다. 컴포넌트 CSS가 그 hook을 var()로 읽어야 바뀐다. 값을 직접 쓴 선언(하드코딩)은 어떤 hook으로도 바뀌지 않는다. 그래서 "브랜드가 모든 컴포넌트에 반영되는가"는 선언을 하나씩 세어 봐야 답할 수 있다.

한 번 세는 것으로 끝나지 않는다. 디자인 시스템의 CSS는 릴리스마다 바뀐다. 같은 기준으로 다시 세고 지난 결과와 비교하는 검사를 자동으로 돌려야 새 하드코딩이나 사라진 hook을 알아챌 수 있다. SLDS 사이트도 hook 값은 Salesforce가 언제든 바꾸고 릴리스 노트로 알린다고 적는다(아래 Salesforce에서는) (2026-10-13 갱신).

Salesforce에서는

  • SLDS 2 global hook의 공식 범주는 색, 그림자, 테두리·반경, 글자(글꼴·크기·굵기·줄 간격), 간격, 크기 6개다. 문서의 범주 목록에 움직임·커서·대소문자·자간이 없다. hook 값은 SLDS가 정하고 Salesforce가 언제든 바꿀 수 있다 (2026-10-13 확인)
  • 컴포넌트 수준 hook(--slds-c-*)은 SLDS 2에서 아직 지원하지 않는다. LWC 개발자 가이드는 링크와 폼 요소를 custom property로 꾸미는 것도 지원하지 않는다고 따로 적는다 (2026-10-13 확인)
  • 설치된 패키지에서 보면 --slds-g-duration-* 8개는 정의만 있고 읽는 곳이 0이다. 곡선(easing) hook은 없다. 개체 아이콘 배경색은 SLDS 2 CSS 973곳과 LBC JS 966곳에 값이 박혀 있다(2026-10-08 연구)

8. 밀버스의 층과 명령

개념

브랜드 요구를 들어줄 때는 공식 기능부터 쓰고, 그것으로 안 되는 만큼만 한 층씩 내려간다. 층이 아래로 갈수록 할 수 있는 것은 늘고, Salesforce 업데이트에 깨질 위험도 커진다.

Salesforce에서는

공식 경로는 Themes and Branding(브랜드 색·로고)과, 컴포넌트 CSS에서 hook을 읽는 것이다. 커스텀 CSS는 정적 리소스로 올려 LEX에서는 loadStyle, VF에서는 <apex:stylesheet>로 싣는다(6절). global hook 재정의와 SLDS 클래스 덮어쓰기는 공식 권고 밖이다(3절).

milvusButton은 비교 예시로 남는다 (2026-10-09 갱신)처음에는 "버튼만 다르게"가 목적이었고, 한때는 hook이 없는 모양과 native 전환 대비를 맡기려 했다. 2026-10-09 결정으로 모양만 바꾸려고 새 컴포넌트를 만들지 않고, hook·브리지로 안 되는 모양은 milvusOverride.css로 바꾼다. milvusButton은 지우지 않고 "새로 만드는 방식"의 비교 예시로 둔다(09 실험 A). util.css에 --milvus-button-custom: on이 없으면 lightning-button을 그대로 그린다(README 2장).

  • LEX: 먹힌다. loadStyle한 CSS가 문서 head에 들어가 같은 페이지의 표준 UI와 모달·토스트까지 바꿨다(5절 실측). 밀버스 컴포넌트가 있는 페이지에 들어가고, 앱 유틸리티 바에 milvusBrandLoader를 두면 그 앱의 표준 화면에도 들어간다(6절, 2026-10-12 갱신)
  • VF: <apex:slds/>가 SLDS 1로 그려지면 먹히지 않는다. 원인은 SLDS 버전이다. VF 설정을 켜고 SLDS 2 테마를 쓰면 <apex:slds/>가 SLDS 2가 되고 util.css가 먹힌다. 브랜드 색은 팔레트 CSS를 더해야 LEX와 같다(6절, Help, 2026-10-09 실측, 2026-10-12 갱신)
  • 기본 우선에서는 util.css 자체가 필요 없다. 그래도 VF를 LEX와 같은 SLDS 2로 맞추는 일은 남는다
