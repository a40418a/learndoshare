LWC와 스토리북 통합

번들러가 다른 LWC(Rollup)와 Storybook(Vite)을 어떻게 잇는지, 공개된 PoC가 어디까지 보여 줬고 우리가 무엇을 더 풀었는지 정리한다. 분기점은 #3에서 통과했고, 이 문서는 지금 저장소의 빌드 방식을 설명한다.

예상 2시간선행: 02 LWC, 03 Storybook, 07 pnpm2026-09-26 작성 · 2026-10-09 갱신 · lwc · @lwc/rollup-plugin 9.4.3

왜 알아야 하나

LWC 컴포넌트는 그대로 브라우저에서 돌지 않는다. 템플릿(HTML)과 CSS를 JS로 컴파일해야 하고, 빌드할 때 컴파일러가 모든 모듈 파일을 찾아야 한다. 우리 저장소에서 이 컴파일은 Rollup + @lwc/rollup-plugin이 한다. 반면 Storybook의 web components 프레임워크(@storybook/web-components-vite)는 Vite 위에서 돈다.

LWC 쪽Rollup + @lwc/rollup-plugin으로 컴파일
≠
Storybook 쪽@storybook/web-components-vite (Vite)

번들러가 다르므로 "Storybook에 LWC 플러그인 하나 꽂으면 끝"이 아니다. 둘을 이을 다리가 필요하다. 이 문서의 선택은 "LWC는 Rollup으로 미리 빌드하고, Storybook은 그 결과물(dist/lwc/)만 읽는다"이다.

분기점 통과 (2026-10-09 갱신)공개 PoC는 가장 단순한 경우(<h1>, <p>)만 보여 줬다. 우리는 SFDX 폴더, lightning-* 컴포넌트, SLDS 2 스타일, 브랜드 전환까지 #3에서 확인했다 (README 3장 "Storybook 통합"). 아래 빌드 구조와 코드는 계획이 아니라 지금 저장소의 실제 구성이다.

근거 자료: digitalflask PoC

Nikita Verkhoshintcev가 2025년 8월 4일 digitalflask 블로그에 공개한 글 "Optimizing Salesforce Front-End with Lightning Web Components & Design Systems"가 가장 가까운 선행 사례다. 같은 블로그에 2025년 6월 2일 "Salesforce Lightning Web Components Design System Challenges"가 먼저 올라왔다. 블로그 글이라 사실의 근거가 아니라 참고 사례로만 쓴다.

PoC가 한 일

1. 구조LWR 생성기로 만든 LWC OSS 프로젝트. 컴포넌트는 src/modules/c/header
→
2. 빌드Rollup이 LWC를 네이티브 커스텀 요소로 dist/에 빌드
→
3. 등록dist를 import해 customElements.define으로 등록
→
4. 렌더lit의 html로 태그를 그린다
  • 원문은 LWR 생성기를 npm init lwr@latest로 실행한다. 우리는 pnpm create lwr@latest로 바꿔 읽는다 (07 pnpm 대응표)
  • 등록할 때 원래 태그(c-header)가 아닌 다른 태그(lwc-header)를 쓰고, customElements.get으로 이미 등록됐는지 먼저 확인한다. 같은 이름을 두 번 define하면 브라우저가 NotSupportedError를 내기 때문이다
  • Storybook 실행 스크립트는 "LWC 빌드 && storybook dev -p 6006" 형태다. 즉 Storybook을 띄우기 전에 한 번 빌드한다

PoC가 하지 않은 일

저자 스스로 향후 과제로 더 나은 예제, lightning-* 컴포넌트 포함, Lightning Data Service 모킹, 시각 회귀 테스트 예제를 꼽았다. 2026-10-09에 블로그 목록을 다시 봤을 때 이 주제의 후속 글은 없었다.

PoC를 대하는 태도"Rollup 결과물을 Storybook에서 커스텀 요소로 렌더할 수 있다"는 참고로만 쓴다. 완성된 해법으로 가져다 쓰지 않았다. 우리의 어려운 부분(SFDX, lightning-*, SLDS)은 PoC 범위 밖이었고, 아래 절들이 그것을 푼 방법이다.

@lwc/rollup-plugin과 모듈 해석

플러그인이 LWC 컴파일과 c/milvusBadge 같은 import 해석을 함께 한다. 해석은 내부적으로 @lwc/module-resolver가 맡는다.

주요 옵션 (9.4.3 README)

옵션의미저장소
rootDirLWC 루트 모듈 디렉터리. 기본값은 Rollup input이 있는 디렉터리쓰지 않음 (alias 경로를 절대 경로로 줌)
modulesModuleRecord[]. @lwc/module-resolver에 넘기는 모듈 해석 규칙SFDX alias + 공식 예제 alias + { npm: 'lightning-base-components' }
disableSyntheticShadowSupportsynthetic shadow 지원 코드를 빼서 결과를 줄이는 옵션켜지 않음. 우리는 synthetic을 쓴다
enableDynamicComponents템플릿 컴파일러의 동적 컴포넌트(lwc:is)를 켠다켬. 공식 예제 multiColumnSortingModal이 lwc:is를 쓴다
apiVersion컴파일 기준 API 버전. 컴포넌트의 *.js-meta.xml이 있으면 그것이 우선쓰지 않음

ModuleRecord 세 가지

종류모양의미
alias{ "name": "c/milvusBadge", "path": "..." }이 이름을 이 파일로 해석
dir{ "dir": "src/modules" }<dir>/<namespace>/<name>/<name>.js 구조를 찾음
npm{ "npm": "lightning-base-components" }npm 패키지가 내보내는 LWC 모듈을 가져옴. map 키는 README에 없고 타입 정의(types.d.ts)에만 있다

설정은 플러그인 옵션 외에 lwc.config.json 파일이나 package.json의 lwc 키에도 둘 수 있다. 모듈을 찾지 못하면 해석기는 NO_LWC_MODULE_FOUND 오류를 낸다.

SFDX 폴더를 c/ 로 해석하기

가장 먼저 부딪히는 함정dir 레코드에는 namespace 옵션이 없다. dir는 <dir>/<namespace>/<name>/<name>.js를 기대하는데, SFDX는 force-app/main/default/lwc/<name>/<name>.js라서 네임스페이스 폴더 c가 없다.

2026-09-26 모듈 해석기로 직접 실험한 결과다 (README 3장 "SFDX 경로 모듈 해석").

설정결과
{ dir: 'force-app/main/default/lwc', namespace: 'c' }실패 NO_LWC_MODULE_FOUND. namespace는 무시된다
{ dir: 'force-app/main/default' }의도와 다름 lwc 폴더가 네임스페이스로 취급되어 lwc/milvusBadge로 해석된다
컴포넌트마다 alias 레코드동작 c/milvusBadge로 해석된다. 저장소가 쓰는 방식
폴더 하나에 심볼릭 링크 c → force-app/main/default/lwc 두고 그 폴더를 dir로미확인 이론상 가능. 시험하지 않았다
{ "name": "c/milvusBadge", "path": "force-app/main/default/lwc/milvusBadge/milvusBadge.js" }

컴포넌트가 늘 때마다 손으로 추가할 수는 없으므로, rollup.lwc.config.mjs가 lwc 폴더를 읽어 alias 목록을 자동 생성한다 (저장소 코드).

인터넷 예제 주의미확인 일부 설정 예제에 { dir, namespace: 'c' } 형태가 보인다. 그 예제가 어떤 해석기를 쓰는지는 확인하지 않았다. 일반 @lwc/module-resolver 9.4.3에서는 위 표처럼 동작하지 않는다.

요소 만들기: createElement와 CustomElementConstructor

빌드된 LWC 클래스를 화면에 놓는 방법은 두 가지다. 둘 다 @lwc/engine-dom README에 있다.

// ① 표준 커스텀 요소로 등록 (PoC 방식)
customElements.define('lightning-hello', LightningHello.CustomElementConstructor);

// ② 엔진에 요소를 만들게 한다 (저장소 방식)
const element = createElement('lightning-hello', { is: LightningHello });
  • CustomElementConstructor는 예전의 buildCustomElementConstructor()를 대체한다 (deprecated)
  • 저장소는 ②를 쓴다 (stories/helpers.js의 lwc()). 저장소 주석이 든 이유는 "태그 이름이 엔진 내부 등록과 충돌하지 않는다"이다. ①처럼 같은 태그를 두 번 define하는 경우도 생기지 않는다
  • synthetic shadow에서도 동작한다. 단, import '@lwc/synthetic-shadow'가 LWC 엔진보다 먼저 실행돼야 한다. LWC 메인테이너는 "synthetic shadow MUST be loaded first"라고 답했다. 엔진이 DOM API를 미리 잡아 두기 때문이다 (lwc#2029). 설치된 엔진도 로드될 때 한 번만 synthetic 여부를 확인한다 (isSyntheticShadowDefined, 로컬 확인)
알려진 한계: 루트 요소의 slotsynthetic shadow에서 루트 요소(직접 만든 최상위 LWC 요소)에 slot으로 넣은 내용은 제대로 렌더되지 않는다. 메인테이너는 이를 버그가 아닌 synthetic shadow의 한계로 보고, 내용을 템플릿 안에서 넣는 다른 컴포넌트(래퍼)를 만들라고 답했다 (lwc#2029). slot을 받는 컴포넌트는 스토리 전용 래퍼 LWC 안에 넣어서 보여 줘야 한다.

현재 빌드 구조와 shadow 모드

2026-10-09 갱신: 이 절은 원래 "확장 아키텍처 (계획)"이었다. 지금은 아래 구조로 동작한다.

1. Rollup 빌드진입 둘(index: stories/lwc-entry.js, catalog: 공식 예제)을 한 번의 빌드로
→
2. dist/lwcindex.js, catalog.js, synthetic-shadow chunk, 엔진이 든 공통 chunk
→
3. preview.jsSLDS 2 CSS 전역 로드, 브랜드 decorator
→
4. 스토리helpers.js가 dist/lwc/index.js를 읽고 createElement로 요소를 만든다

왜 한 번의 빌드인가

컴포넌트마다 따로 빌드하면 각 결과물에 LWC 엔진이 하나씩 들어간다. 엔진이 페이지에 여러 벌 있으면 컴포넌트끼리 서로를 모르는 상태가 될 수 있다. 입력을 여러 개 준 한 번의 Rollup 빌드는 공통 코드를 공유 chunk로 뽑아내므로 엔진이 한 벌만 로드된다. lightning-base-components 안의 동적 import 때문에 chunk는 여러 개 생긴다. 미확인 엔진 중복 시 실제 증상은 재현하지 않았다.

synthetic shadow를 먼저 실행하기

진입이 둘이면 엔진이 공통 chunk로 빠져 진입 파일 본문보다 먼저 실행된다. 그래서 @lwc/synthetic-shadow도 manualChunks로 별도 chunk로 빼서 import 순서로 엔진보다 앞에 둔다. preview.js에서는 synthetic shadow를 import하지 않는다 (2026-10-09 정정: 이전 예시는 preview.js 첫 줄에 두었다).

shadow 모드: 전부 synthetic

  • org: 공식 문서는 Lightning Experience와 Experience Cloud가 synthetic shadow polyfill을 쓴다고 한다. 2026-10-07 org 실측에서도 홈, 계정 목록, 새 계정 화면의 기본 컴포넌트가 synthetic이었고 native는 내부 primitive 3개뿐이었다 (README 3장 "LWC shadow 모드", #16)
  • Storybook: org와 같게 모든 LWC를 synthetic으로 그린다 (PR #17). 패키지의 native 지원 목록 156개는 org에 아직 적용되지 않았으므로 쓰지 않는다
  • 경과: #11은 빌드 버그로 모든 LWC가 native로 그려진 상태에서 쟀다 → #14는 패키지 목록대로 혼합 모드로 그렸다 → #16(PR #17)에서 org 실측에 맞춰 전부 synthetic으로 바꿨다
기능 게이트 하나만 닫는다npm 패키지는 @salesforce/gate/*를 모두 열린 것으로 연결한다. 그중 bc.260.enableComboboxElementInternals가 열려 있으면 baseCombobox가 생성자에서 attachInternals()를 부르고, LWC 엔진은 synthetic shadow에서 "attachInternals API is not supported in synthetic shadow." 오류를 낸다. org에서는 같은 컴포넌트가 synthetic으로 동작하므로 이 게이트가 닫혀 있다고 보고(추정), 저장소 빌드는 이 게이트 하나만 닫는다. 나머지 게이트는 패키지 stub대로 열려 있다.

개발 루프

pnpm dev:lwc(rollup -w, 감시 모드)와 pnpm exec storybook dev -p 6006을 터미널 두 개에서 띄운다. 컴포넌트를 저장하면 Rollup이 dist를 다시 쓰고, Storybook(Vite)이 바뀐 파일을 다시 읽는다. 상태를 유지하는 HMR이 아니라 다시 빌드 후 새로 고침이다. 미확인 저장 후 반영까지 걸리는 시간은 측정 기록이 없다.

SLDS 2 CSS (2026-10-09 갱신)전역 CSS는 @salesforce-ux/design-system-2 2.264.2의 dist/css/bundled/slds2.cosmos.css다. preview.js에서 import한다. @salesforce-ux/design-system(2.264.1)은 SLDS 1 빌드라서 브랜드 색이 버튼에 반영되지 않았다 (#3 실측).

저장소 코드

Rollup 설정

import { existsSync, readFileSync, readdirSync, rmSync } from 'node:fs';
import { resolve } from 'node:path';
import lwc from '@lwc/rollup-plugin';
import nodeResolve from '@rollup/plugin-node-resolve';
import replace from '@rollup/plugin-replace';

const LWC_DIR = 'force-app/main/default/lwc';

// dir 레코드에는 namespace 옵션이 없다 → 폴더를 읽어 c/<이름> alias를 만든다
const sfdxModules = readdirSync(LWC_DIR, { withFileTypes: true })
  .filter((e) => e.isDirectory() && existsSync(`${LWC_DIR}/${e.name}/${e.name}.js`))
  .map((e) => ({ name: `c/${e.name}`, path: resolve(LWC_DIR, e.name, `${e.name}.js`) }));

// 해시가 붙은 이전 chunk가 쌓이지 않게 먼저 지운다
rmSync('dist/lwc', { recursive: true, force: true });

// Salesforce 공식 예제 alias 목록 (scripts/generate-slds-catalog.mjs가 만든다)
const catalog = JSON.parse(readFileSync('stories/slds-catalog/examples.json', 'utf8'));

// combobox의 ElementInternals 게이트 하나만 닫는다
const CLOSED_GATES = new Set(['@salesforce/gate/bc.260.enableComboboxElementInternals']);
const closedGates = {
  name: 'milvus-closed-gates',
  resolveId: (id) => (CLOSED_GATES.has(id) ? '\0milvus-closed-gate' : null),
  load: (id) => (id === '\0milvus-closed-gate' ? 'export default { isOpen: () => false };' : null),
};

export default {
  // 진입 여러 개, 빌드 한 번 → 엔진은 공통 chunk 한 벌
  input: { index: 'stories/lwc-entry.js', catalog: 'stories/slds-catalog/entry.js' },
  output: {
    dir: 'dist/lwc',
    entryFileNames: '[name].js',
    format: 'esm',
    sourcemap: true,
    // synthetic shadow를 별도 chunk로 빼서 엔진보다 먼저 실행되게 한다
    manualChunks: (id) => (id.includes('@lwc/synthetic-shadow') ? 'synthetic-shadow' : undefined),
  },
  // 해석하지 못한 import는 빌드 단계에서 실패시킨다
  onwarn(warning, warn) {
    if (warning.code === 'UNRESOLVED_IMPORT') throw new Error(warning.message);
    warn(warning);
  },
  plugins: [
    closedGates,
    replace({
      preventAssignment: true,
      values: { 'process.env.NODE_ENV': JSON.stringify('development') },
    }),
    lwc({
      enableDynamicComponents: true,
      modules: [...sfdxModules, ...catalog, { npm: 'lightning-base-components' }],
    }),
    nodeResolve(),
  ],
};

@lwc/engine-dom 9.4.3의 dist 파일에는 process.env.NODE_ENV 참조가 182곳 있다 (로컬 확인). @rollup/plugin-replace 문서는 바로 이 값을 치환하는 예를 보여 준다. 미확인 LWC 문서가 이 방식을 권장하는지는 찾지 못했다. alias 경로는 resolve()로 절대 경로를 주므로 rootDir과 상관없다. 컨테이너(org 전용) 컴포넌트는 진입 파일에서 export하지 않으면 빌드되지 않는다.

요소 만들기 도우미

// Rollup으로 미리 컴파일한 LWC 번들 (pnpm build:lwc). Storybook(Vite)은 결과물만 읽는다
import { createElement } from '../dist/lwc/index.js';
export * from '../dist/lwc/index.js';

export function lwc(tag, Ctor, props = {}, events = {}) {
  const element = createElement(tag, { is: Ctor });
  for (const [key, value] of Object.entries(props)) {
    if (value !== undefined) element[key] = value;       // @api 속성은 JS property로
  }
  for (const [name, handler] of Object.entries(events)) {
    if (handler) element.addEventListener(name, (event) => handler(event.detail ?? event));
  }
  return element;
}

스스로 점검

Q1. Storybook에 LWC를 바로 넣지 못하고 Rollup으로 미리 빌드하는 이유는?

LWC는 빌드할 때 컴파일해야 하고, 저장소에서는 Rollup + @lwc/rollup-plugin이 그 일을 한다. @storybook/web-components-vite는 Vite 위에서 돈다. 번들러가 다르므로 Rollup 결과물(dist/lwc)을 Storybook이 읽게 한다.

Q2. { dir: 'force-app/main/default/lwc', namespace: 'c' }가 왜 실패하나? 대신 무엇을 쓰나?

dir 레코드에는 namespace 옵션이 없고 <dir>/<namespace>/<name>/<name>.js 구조를 기대한다. SFDX에는 c 폴더가 없어 NO_LWC_MODULE_FOUND가 난다. 컴포넌트마다 alias 레코드(c/milvusBadge → 파일 경로)를 자동 생성해 쓴다.

Q3. lightning-base-components를 설치했는데 우리 컴포넌트의 @salesforce/label/c.xxx import가 실패한다. 패키지에 stub이 있지 않나?

패키지의 scopedImports/ 연결은 패키지 내부 import에만 적용된다. 우리 코드용 stub 파일을 만들고 alias 레코드로 연결해야 한다.

Q4. slot을 받는 컴포넌트를 스토리에서 바로 만들었더니 내용이 안 보인다. 왜이고, 어떻게 하나?

synthetic shadow에서 루트 요소에 slot으로 넣은 내용은 제대로 렌더되지 않는 알려진 한계다 (lwc#2029). 스토리 전용 래퍼 LWC 안에서 그 컴포넌트를 쓰고, 래퍼를 만든다.

Q5. 패키지에 native 지원 목록(156개)이 있는데 왜 Storybook은 전부 synthetic으로 그리나?

org(LEX)가 기본 컴포넌트를 synthetic으로 그리기 때문이다 (공식 문서, 2026-10-07 실측). Storybook은 org와 같은 모습을 보여 줘야 하므로 그 목록을 쓰지 않는다.

Q6. 기능 게이트를 전부 닫지 않고 combobox 게이트 하나만 닫는 이유는?

그 게이트가 열려 있으면 attachInternals()를 불러 synthetic shadow에서 엔진 오류가 나기 때문이다. 다른 게이트는 오류가 없어서 패키지 stub대로 둔다. org에서 각 게이트가 열려 있는지는 확인하지 않았다.
