LEARN 04 · Phase 2 준비 (분기점)

LWC와 스토리북 통합

번들러가 다른 LWC(Rollup)와 Storybook(Vite)을 어떻게 잇는지, 공개된 PoC가 어디까지 증명했고 우리가 무엇을 더 검증해야 하는지 정리한다. Phase 2의 성공 여부가 여기서 갈린다.

예상 2시간선행: 02 LWC, 03 Storybook, 07 pnpm2026-09-26 기준 lwc · @lwc/rollup-plugin 9.4.3

왜 알아야 하나

LWC 컴포넌트는 그대로 브라우저에서 돌지 않는다. 템플릿(HTML)과 CSS를 JS로 컴파일해야 하고, 이 컴파일은 Rollup + @lwc/rollup-plugin이 담당한다. 반면 Storybook의 web components 프레임워크(@storybook/web-components-vite)는 Vite 위에서 돈다.

LWC 쪽Rollup + @lwc/rollup-plugin으로 컴파일
≠
Storybook 쪽@storybook/web-components-vite (Vite)

번들러가 다르므로 "Storybook에 LWC 플러그인 하나 꽂으면 끝"이 아니다. 두 가지를 이을 다리가 필요하다. 이 문서의 선택은 "LWC는 Rollup으로 미리 빌드하고, Storybook은 그 결과물을 표준 커스텀 요소로 쓴다"이다.

이 문서의 성격공개 PoC는 가장 단순한 경우(<h1>, <p>)만 보여 준다. 우리에게 필요한 SFDX 폴더, lightning-* 컴포넌트, SLDS 스타일, 브랜드 전환은 아직 누구도 공개적으로 증명하지 않았다. 아래 확장 아키텍처는 계획이자 가설이다.

근거 자료: digitalflask PoC

Nikita Verkhoshintcev가 2025년 8월 4일 digitalflask 블로그에 공개한 글 "Optimizing Salesforce Front-End with Lightning Web Components Design Systems"가 가장 가까운 선행 사례다. 같은 저자가 앞서 2025년 6월 2일에 "Salesforce LWC Design System Challenges"를 썼다.

PoC가 한 일

1. 구조LWR 생성기로 만든 구조. 컴포넌트는 src/modules/c/header
→
2. 빌드Rollup이 LWC를 네이티브 커스텀 요소로 dist/에 빌드
→
3. 등록스토리에서 dist를 import해 customElements.define으로 등록
→
4. 렌더lit의 html로 태그를 그린다
  • 원문은 LWR 생성기를 npm 명령으로 실행한다. 우리는 pnpm create lwr@latest로 바꿔 읽는다 (07 pnpm 대응표)
  • 등록할 때 원래 태그(c-header)가 아닌 다른 태그(lwc-header)를 쓰고, customElements.get으로 이미 등록됐는지 먼저 확인한다. 같은 이름을 두 번 등록하면 브라우저가 오류를 내기 때문이다
  • Storybook 실행 스크립트는 "LWC 빌드 && storybook dev -p 6006" 형태다. 즉 Storybook을 띄우기 전에 한 번 빌드한다

PoC가 하지 않은 일

저자 스스로 향후 과제로 더 나은 예제, lightning-* 컴포넌트 포함, Lightning Data Service 모킹, 시각 회귀 테스트 예제를 꼽았다. 2026-09 기준 후속 글은 찾지 못했다.

PoC를 대하는 태도"Rollup 결과물을 Storybook에서 커스텀 요소로 렌더할 수 있다"는 근거로만 쓴다. 완성된 해법으로 가져다 쓰면 안 된다. 우리의 어려운 부분(SFDX, lightning-*, SLDS)은 PoC 범위 밖이다.

@lwc/rollup-plugin과 모듈 해석

플러그인이 LWC 컴파일과 c/milvusBadge 같은 import 해석을 함께 한다. 해석은 내부적으로 @lwc/module-resolver가 맡는다.

주요 옵션 (9.4.3 README)

옵션의미
rootDirLWC 루트 모듈 디렉터리. 기본값은 Rollup input이 있는 디렉터리
modulesModuleRecord[]. @lwc/module-resolver에 넘기는 모듈 해석 규칙
disableSyntheticShadowSupportsynthetic shadow 지원 코드를 빼는 옵션. 우리는 synthetic을 쓰므로 켜지 않는다
enableDynamicComponents동적 컴포넌트(lwc:is) 관련
apiVersion컴파일 기준 API 버전

ModuleRecord 세 가지

종류모양의미
alias{ "name": "c/milvusBadge", "path": "..." }이 이름을 이 파일로 해석
dir{ "dir": "src/modules" }<dir>/<namespace>/<name>/<name>.js 구조를 찾음
npm{ "npm": "lightning-base-components", "map": {...} }npm 패키지가 내보내는 LWC 모듈을 가져옴 (map은 선택)

설정은 플러그인 옵션 외에 lwc.config.json 파일이나 package.json의 lwc 키에도 둘 수 있다.

SFDX 폴더를 c/ 로 해석하기

가장 먼저 부딪히는 함정dir 레코드에는 namespace 옵션이 없다. dir는 <dir>/<namespace>/<name>/<name>.js를 기대하는데, SFDX는 force-app/main/default/lwc/<name>/<name>.js라서 네임스페이스 폴더 c가 없다.

모듈 해석기로 직접 실험한 결과다.

설정결과
{ dir: 'force-app/main/default/lwc', namespace: 'c' }실패 NO_LWC_MODULE_FOUND. namespace는 무시된다
{ dir: 'force-app/main/default' }의도와 다름 lwc 폴더가 네임스페이스로 취급되어 lwc/milvusBadge로 해석된다
컴포넌트마다 alias 레코드동작 c/milvusBadge로 해석된다
폴더 하나에 심볼릭 링크 c → force-app/main/default/lwc 두고 그 폴더를 dir로미확인 이론상 가능. 아직 시험하지 않았다
{ "name": "c/milvusBadge", "path": "force-app/main/default/lwc/milvusBadge/milvusBadge.js" }

컴포넌트가 늘 때마다 손으로 추가할 수는 없으므로, 빌드 설정에서 lwc 폴더를 읽어 alias 목록을 자동 생성한다 (예시 코드).

인터넷 예제 주의{ dir, namespace: 'c' } 형태는 LWR이나 LWC Garden 설정에서만 보인다. 이들은 자체 해석기(포크)를 쓰는 것으로 보이며, 일반 @lwc/module-resolver에서는 동작하지 않는다.

lightning-base-components

org 밖에서 lightning-badge, lightning-button 같은 기본 컴포넌트를 쓰려면 npm 패키지 lightning-base-components가 필요하다.

항목내용
최신 버전1.28.19-alpha (latest 태그). alpha 태그만 있다. 그 밖의 dist-tag: next 1.26.3-rc.0-alpha, ssr, previous
배포자 · 라이선스Salesforce (lwc-admin) · MIT. 외부 기여는 받지 않는다
README의 제한 사항"SLDS styles needs to be globally defined at application level", "@lwc/synthetic-shadow is required"
빠진 컴포넌트org 데이터가 필요한 것: 레코드 폼, lightning-input-field, 파일 업로드, 지도, lightning-input-rich-text
설정{ "npm": "lightning-base-components" }
해석 확인lightning/badge, lightning/button, lightning/navigation 해석됨. 노출 모듈 118개. lightning/uiRecordApi는 없다
패키지 안의 stub은 우리 것이 아니다패키지는 내부적으로 @salesforce/label/*, @salesforce/i18n/*, @salesforce/gate/*를 자기 scopedImports/ 폴더로 연결해 둔다. 하지만 이 연결은 패키지 안에서 한 import에만 적용된다. 우리 컴포넌트가 @salesforce/label/c.xxx를 import하면 따로 alias 레코드로 stub 파일을 연결해야 한다.

설치는 정확한 버전으로 고정한다.

pnpm add -D -E lightning-base-components@1.28.19-alpha

CustomElementConstructor

빌드된 LWC 클래스를 표준 커스텀 요소로 등록하는 방법이다. @lwc/engine-dom README에 문서화돼 있다.

customElements.define('lightning-hello', LightningHello.CustomElementConstructor);
  • 예전의 buildCustomElementConstructor()를 대체한다 (deprecated)
  • 대안으로 createElement('x-foo', { is: Ctor })로 요소를 만들어 직접 붙일 수도 있다
  • synthetic shadow에서도 동작한다. 단, import '@lwc/synthetic-shadow'가 가장 먼저 실행되는 import여야 한다
알려진 한계: 루트 요소의 slotsynthetic shadow에서 루트 요소(직접 등록한 커스텀 요소)에 slot으로 넣은 내용이 제대로 렌더되지 않는다. 메인테이너는 이를 한계로 보고 래퍼 컴포넌트를 쓰라고 답했다 (lwc#2029). slot을 받는 컴포넌트는 스토리 전용 래퍼 LWC 안에 넣어서 보여 줘야 한다.

확장 아키텍처 (계획)

가설 PoC를 우리 조건(SFDX, lightning-*, SLDS, 브랜드)으로 넓힌 구상이다. 아직 동작을 확인하지 않았다.

1. Rollup 빌드SFDX alias + lightning-base-components. 입력 여러 개를 한 번의 빌드로 → LWC 엔진이 공유 청크 하나로
→
2. dist컴포넌트별 ESM 파일 + 공유 청크
→
3. preview.js@lwc/synthetic-shadow 먼저, SLDS CSS 전역 로드, 브랜드 decorator
→
4. 스토리CustomElementConstructor로 등록, lit으로 렌더

왜 한 번의 빌드인가

컴포넌트마다 따로 빌드하면 각 결과물에 LWC 엔진이 하나씩 들어간다. 엔진이 페이지에 여러 벌 있으면 컴포넌트끼리 서로를 모르는 상태가 될 수 있다. 입력을 여러 개 준 한 번의 Rollup 빌드는 공통 코드를 공유 청크로 뽑아내므로 엔진이 하나만 로드된다. 미확인 엔진 중복 시 실제 증상은 아직 재현하지 않았다.

개발 루프

rollup -w(감시 모드)와 storybook dev를 병렬로 실행한다. 컴포넌트를 저장하면 Rollup이 dist를 다시 쓰고, Vite가 dist 변경을 감지해 새로 고친다. 진짜 HMR(상태 유지 교체)이 아니라 다시 빌드 후 새로 고침이다.

SLDS 버전 (정정, #3에서 실측)최신 SLDS 2는 별도 패키지 @salesforce-ux/design-system-2의 dist/css/bundled/slds2.cosmos.css다. 아래의 @salesforce-ux/design-system은 SLDS 1 빌드라 브랜드 색이 버튼에 반영되지 않았다. 원래 문장: 전역 CSS는 @salesforce-ux/design-system 2.264.1의 assets/styles/salesforce-lightning-design-system.min.css를 쓴다. 이 경로는 패키지에 실제로 있다 (CDN으로 확인). org의 SLDS 버전과 맞는지는 01 SLDS 문서 기준으로 확인한다.

예시 코드

예시(검증 전)아래 코드는 설계를 설명하기 위한 초안이다. 아직 실행해 보지 않았다. Phase 2 첫날 실제로 돌려 보고 이 문서를 고친다.

Rollup 설정

import fs from 'node:fs';
import path from 'node:path';
import lwc from '@lwc/rollup-plugin';
import replace from '@rollup/plugin-replace';

const LWC_DIR = 'force-app/main/default/lwc';

// lwc 폴더를 읽어 c/<name> alias 목록을 만든다 (dir 레코드는 SFDX 구조를 못 읽으므로)
const components = fs
  .readdirSync(LWC_DIR, { withFileTypes: true })
  .filter((d) => d.isDirectory() && fs.existsSync(path.join(LWC_DIR, d.name, `${d.name}.js`)))
  .map((d) => d.name);

const componentAliases = components.map((name) => ({
  name: `c/${name}`,
  path: path.join(LWC_DIR, name, `${name}.js`),
}));

// 우리 코드가 쓰는 @salesforce/* 는 직접 stub을 연결한다
const stubAliases = [
  { name: '@salesforce/label/c.milvus_Close', path: 'storybook-stubs/label/milvus_Close.js' },
];

// 표현 컴포넌트만 입력으로 (컨테이너는 org 전용)
const input = Object.fromEntries(
  components
    .filter((name) => name !== 'milvusRecordBadge')
    .map((name) => [name, path.join(LWC_DIR, name, `${name}.js`)]),
);

export default {
  input,                              // 입력 여러 개, 빌드 한 번 → 엔진 공유 청크
  output: { dir: 'dist/lwc', format: 'esm', entryFileNames: '[name].js' },
  plugins: [
    replace({                         // engine-dom dist에 process.env.NODE_ENV 참조가 있다
      preventAssignment: true,
      'process.env.NODE_ENV': JSON.stringify('development'),
    }),
    lwc({
      rootDir: '.',
      modules: [...componentAliases, ...stubAliases, { npm: 'lightning-base-components' }],
    }),
  ],
};

@lwc/engine-dom 9.4.3의 dist 파일에 process.env.NODE_ENV 참조가 있는 것은 확인했다. @rollup/plugin-replace로 치환하는 방식이 이 플러그인과 함께 권장되는 방법인지, alias 경로가 rootDir 기준으로 해석되는지, 컨테이너를 빼는 방식(이름 목록 vs 폴더 규칙)은 미확인이다.

"scripts": {
  "build:lwc": "rollup -c rollup.lwc.config.js",
  "watch:lwc": "rollup -c rollup.lwc.config.js -w",
  "storybook": "pnpm build:lwc && storybook dev -p 6006"
}

감시 모드는 터미널 두 개에서 pnpm watch:lwc와 pnpm exec storybook dev -p 6006을 따로 띄운다. 한 명령으로 묶는 도구는 아직 정하지 않았다.

lit의 .label=${...}는 HTML 속성이 아니라 DOM 프로퍼티로 넣는 문법이다. @api 속성은 DOM 프로퍼티로 노출되므로 이 방식이 맞다.

성공 기준 (셋 다 만족)

  • lightning-badge와 lightning-button이 SLDS 스타일이 적용된 채 Storybook에 렌더된다
  • 같은 컴포넌트의 org 화면 스크린샷과 비교해 모습이 일치한다
  • 컴포넌트 파일을 저장하면 몇 초 안에 Storybook에 반영된다

실패 시 경로

1. 오류 분류pnpm 해석 / LWC 컴파일 / 런타임(shadow·SLDS) 중 어디인가
→
2. LWC Garden3일 동안 대안으로 시도
→
3. org 문서 앱org 안에 컴포넌트 문서 앱을 만드는 방식으로 전환
오류 분류가 먼저"안 된다"로 뭉뚱그리면 다음 선택을 할 수 없다. 모듈을 못 찾는 오류(pnpm·resolver), 템플릿·CSS 컴파일 오류(LWC 컴파일러), 렌더는 되지만 모습이 다른 경우(shadow·SLDS)는 원인도 대응도 다르다.

스스로 점검

Q1. Storybook에 LWC를 바로 넣지 못하고 Rollup으로 미리 빌드하는 이유는?

LWC 컴파일은 Rollup + @lwc/rollup-plugin이 담당하는데, @storybook/web-components-vite는 Vite 위에서 돈다. 번들러가 다르므로 Rollup 결과물(dist)을 표준 커스텀 요소로 Storybook에 넘긴다.

Q2. { dir: 'force-app/main/default/lwc', namespace: 'c' }가 왜 실패하나? 대신 무엇을 쓰나?

dir 레코드에는 namespace 옵션이 없고 <dir>/<namespace>/<name>/<name>.js 구조를 기대한다. SFDX에는 c 폴더가 없어 NO_LWC_MODULE_FOUND가 난다. 컴포넌트마다 alias 레코드(c/milvusBadge → 파일 경로)를 자동 생성해 쓴다.

Q3. lightning-base-components를 설치했는데 우리 컴포넌트의 @salesforce/label/c.xxx import가 실패한다. 패키지에 stub이 있지 않나?

패키지의 scopedImports/ 연결은 패키지 내부 import에만 적용된다. 우리 코드용 stub 파일을 만들고 alias 레코드로 연결해야 한다.

Q4. slot을 받는 컴포넌트를 스토리에 직접 등록했더니 내용이 안 보인다. 왜이고, 어떻게 하나?

synthetic shadow에서 루트 요소에 slot으로 넣은 내용은 제대로 렌더되지 않는 알려진 한계다 (lwc#2029). 스토리 전용 래퍼 LWC 안에서 그 컴포넌트를 쓰고, 래퍼를 등록한다.

Q5. 분기점에서 "실패"를 선언하기 전에 반드시 할 일은?

오류를 pnpm 해석 / LWC 컴파일 / 런타임(shadow·SLDS) 중 하나로 분류한다. 그 뒤에 LWC Garden을 3일 시도하고, 그래도 안 되면 org 문서 앱으로 간다.
