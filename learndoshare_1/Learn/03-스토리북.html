왜 알아야 하나

LWC 컴포넌트는 원래 org 안에서만 보인다. 디자이너, 기획자, 다른 프로젝트 개발자가 "버튼이 어떻게 생겼나"를 보려고 매번 org에 들어갈 수는 없다. Storybook은 컴포넌트를 상태별(스토리)로 늘어놓은 정적 사이트를 만들어 준다.

Rollup 사전 컴파일dist/lwc/에 JS 생성

→

Storybook 입장에서 우리 컴포넌트는 그냥 웹 컴포넌트다. 그래서 프레임워크는 @storybook/web-components-vite를 쓴다. 이 렌더러는 스토리가 돌려준 lit 템플릿, HTML 문자열, DOM 노드를 캔버스에 그린다 (렌더러 소스, v10.6.0. 설치된 10.6.0 dist에서도 같음). 우리 저장소는 lit 템플릿 대신 DOM 요소를 돌려준다 (stories/helpers.js의 lwc()). LWC를 Storybook 안에서 직접 컴파일하지 않는 이유와 요소를 만드는 방법은 04 통합에서 다룬다.

2026-10-09 갱신: 처음 계획은 CustomElementConstructor로 태그를 등록하고 lit html로 그리는 것이었다. 지금 저장소는 createElement로 요소를 만든다.

공식 설치 문서는 npm create storybook@latest를 먼저 보여 주고, 패키지 매니저 탭에서 pnpm을 고르면 pnpm create storybook@latest다. 우리는 pnpm 형태로 실행한다 (07 pnpm 대응표).

pnpm create storybook@latest

# 또는 설치 없이 CLI 일회성 실행
pnpm dlx storybook@latest init --type web_components --builder vite \

스토리 작성 (CSF3)

가장 작은 스토리

웹 컴포넌트 렌더러에서는 component에 태그 이름 문자열을 넣는다. render가 없으면 Storybook이 그 태그로 요소를 만들고 args를 JS property로 넣는다 (element[key] = value). 이 동작은 문서 페이지가 아니라 렌더러 소스(render.ts, v10.6.0)에 있다.

const meta = { component: 'demo-button' };
export default meta;

export const Primary = {
  args: { primary: true, label: 'Button' },
};

조금 더 갖춘 형태 (lit 사용 예)

import { html } from 'lit';

export default {
  title: 'Example/Button',
  component: 'demo-button',
  tags: ['autodocs'],              // addon-docs가 있으면 문서 페이지 자동 생성
  args: { label: 'Button', primary: false },
  argTypes: {
    label: { control: 'text' },
    primary: { control: 'boolean' },
  },
  render: (args) => html`<demo-button .label=${args.label} ?primary=${args.primary}></demo-button>`,
};

export const Primary = { args: { primary: true } };
export const Secondary = {};

lit 바인딩 네 가지

문법의 원문은 Lit 공식 문서 — Expressions다.

문법무엇을 설정하나예
x=${v}HTML attribute (항상 문자열)variant=${args.variant}
.x=${v}JS property (객체, 배열, 숫자 그대로).options=${args.options}
?x=${v}boolean attribute (true면 붙이고 false면 제거)?disabled=${args.disabled}
@x=${fn}이벤트 리스너@click=${args.onClick}
LWC의 @api 속성은 property로 넘긴다HTML attribute 값은 항상 문자열이라 배열이나 객체는 attribute로 넘기면 문자열이 되어 버린다. JS property 이름은 camelCase(iconName), HTML attribute 이름은 kebab-case(icon-name)다. 우리 저장소는 lit 바인딩을 쓰지 않고, stories/helpers.js의 lwc()가 args를 element[key] = value로 넣는다. property로 넘기는 것과 같다.

미확인 LWC 요소가 HTML attribute(icon-name="...")를 받아 @api property로 반영하는지, boolean attribute를 어떻게 해석하는지는 Storybook에서 시험하지 않았다. 저장소는 property만 쓰므로 지금은 영향이 없다.

decorator와 globals

globals는 모든 스토리가 공유하는 값(테마, 언어 등)이고, decorator는 스토리를 감싸는 함수다. 툴바에서 global을 바꾸면 decorator가 그 값을 읽어 스토리를 다시 그린다. 브랜드 전환은 이 구조로 만든다.

import { html } from 'lit';

export default {
  globalTypes: {
    theme: {
      description: 'Global theme for components',
      toolbar: {
        title: 'Theme',
        icon: 'circlehollow',
        items: ['light', 'dark'],
        dynamicTitle: true,          // 툴바에 선택된 값을 표시
      },
    },
  },
  initialGlobals: { theme: 'light' },
  decorators: [
    (story, context) => html`<div data-theme=${context.globals.theme}>${story()}</div>`,
  ],
};
옛 자료의 globals, defaultValuepreview의 globals는 8.2에서 deprecated, 9.0에서 삭제되고 initialGlobals로 바뀌었다. 초기값도 더 이상 globalTypes.defaultValue에서 오지 않는다 (MIGRATION.md). globalTypes와 initialGlobals는 .storybook/preview.*에만 쓴다.

2026-10-13 갱신: 아래는 저장소 .storybook/brand.ts와 preview.ts를 줄인 것이다(타입 생략). 브랜드 목록은 Vite 플러그인이 만드는 가상 모듈 virtual:milvus-brands에서 온다. 저장소에서 띄우면 brands/의 데모 브랜드, 프로젝트에서 pnpm milvus storybook으로 띄우면 그 프로젝트의 브랜드다(두 모드와 Vite 플러그인). 툴바 항목은 이 목록으로 자동으로 만든다.

// lib/storybook-plugin.ts가 모드에 맞게 만든 브랜드 목록. 첫 브랜드가 기본 브랜드다
import { brands, mode } from 'virtual:milvus-brands';

const STYLES = [
  ['milvus-brand-bridge', 'bridgeCss'],     // milvusBridge.css
  ['milvus-brand-util', 'utilCss'],         // util.css (프로젝트는 milvusBrand.css)
  ['milvus-brand-override', 'overrideCss'], // milvusOverride.css
];

export function applyBrand(name) {
  const brand = brands.find((b) => b.name === name) ?? brands[0];
  const root = document.documentElement;
  // ① 브랜드 색: 팔레트 → :root의 --slds-r-color-brand-* (org 테마 흉내). 비면 SLDS 2 기본 팔레트
  for (const prop of [...root.style])
    if (prop.startsWith('--slds-r-color-brand-')) root.style.removeProperty(prop);
  for (const [step, color] of Object.entries(brand.palette))
    root.style.setProperty(`--slds-r-color-brand-${step}`, color);

  // ② 브리지 → util.css → override 순서로 문서 head에 (org의 loadBrand와 같은 순서)
  for (const [id, key] of STYLES) {
    const style =
      document.getElementById(id) ??
      document.head.appendChild(Object.assign(document.createElement('style'), { id }));
    style.textContent = brand[key];
  }
  return brand;
}

사이드바 로고

Storybook 화면 왼쪽 위 로고와 제목은 manager 쪽 테마로 바꾼다. 공식 문서 Theming 페이지 기준 import 경로는 storybook/manager-api와 storybook/theming이다. 테마 객체는 합쳐지지 않고 통째로 바뀐다. base만 필수다.

import { addons } from 'storybook/manager-api';
import { create } from 'storybook/theming';

// main.ts의 managerHead가 기본 브랜드의 로고(data URL)와 버튼 색(50단계)을 넣어 준다
const brand = window.MILVUS_BRAND ?? {};

addons.setConfig({
  theme: create({
    base: 'light',                    // 필수. 나머지는 선택
    brandTitle: '밀버스 디자인 시스템',
    brandImage: brand.logoUrl,
    // 색이 없으면(오류 상태) 넘기지 않는다. undefined를 넘기면 기본 색까지 지워진다
    ...(brand.color && { colorPrimary: brand.color, colorSecondary: brand.color }),
  }),
});

manager(사이드바)는 툴바의 브랜드 선택과 따로 돈다. 그래서 로고는 기본 브랜드(목록의 첫 브랜드) 하나로 정한다. 저장소 코드는 manager가 Vite 가상 모듈을 읽지 못한다고 보고(main.ts 주석), managerHead로 window.MILVUS_BRAND = {"logoUrl":…,"color":…}를 넣는다. 로고는 data URL이라 개발 서버, 정적 빌드, 사이드바가 같은 값을 쓴다. 대신 로고가 크면 번들도 그만큼 커진다(lib/storybook-plugin.ts의 ponytail: 주석). managerHead는 서버를 띄울 때 계산되므로, 프로젝트 로고·색을 바꾸면 미리보기는 바로 바뀌지만 사이드바는 Storybook을 다시 띄워야 바뀐다.

두 모드와 Vite 플러그인 구현

2026-10-13 추가(Task 17·18). 같은 Storybook 설정(.storybook/)이 두 곳에서 돈다. 이 디자인 시스템 저장소에서 데모 브랜드를 보여 줄 때가 저장소 모드, 패키지를 설치한 고객 프로젝트에서 그 프로젝트의 브랜드를 보여 줄 때가 프로젝트 모드다. 모드를 가르는 것은 환경 변수 MILVUS_PROJECT_DIR 하나다.

개념

  • Vite 플러그인은 Vite가 모듈을 찾고(resolveId) 읽고(load) 개발 서버를 만들 때(configureServer) 끼어드는 객체다. Storybook의 Vite 빌더는 main 설정의 viteFinal에서 기본 Vite 설정을 받아 고친 설정을 돌려받는다. 공식 예는 mergeConfig로 합친다
  • 가상 모듈은 디스크에 없는 모듈이다. 플러그인이 virtual:my-module 같은 이름을 받아 코드를 만들어 준다. Vite 문서는 이것을 빌드 때의 정보를 보통의 ESM import로 소스에 넘기는 방법이라고 설명한다. 찾은 id 앞에 \0을 붙이는 것은 Rollup의 관례로, 다른 플러그인이 이 모듈을 처리하려 들지 않게 한다. 브라우저에서는 /@id/__x00__…로 보인다
  • configureServer는 개발 서버에 미들웨어를 붙이는 데 가장 많이 쓰는 hook이다. 정적 빌드(production build)에서는 부르지 않는다. 같은 hook에서 파일 감시자와 모듈 그래프에 접근할 수 있고, 모듈을 무효화한 뒤 server.ws.send({ type: 'full-reload' })로 페이지를 다시 읽게 할 수 있다(Vite 문서의 handleHotUpdate 예)
  • server.fs.allow는 개발 서버가 /@fs/로 내줄 수 있는 파일을 제한한다. 기본은 Vite가 찾은 작업 공간 루트다. 값을 직접 주면 이 자동 탐지가 꺼지므로 searchForWorkspaceRoot를 함께 넣는다
  • 듣는 주소: Vite 자체의 server.host 기본값은 localhost다. Storybook CLI 문서는 --host를 "0.0.0.0이면 모든 네트워크 인터페이스"라고만 적고 기본값은 적지 않는다. 설치된 storybook 10.6.0은 --host가 없으면 Node의 listen에 host 없이 넘기고(dist/core-server/index.js, 설치본 확인), Node는 host를 빼면 모든 주소(:: 또는 0.0.0.0)에서 받는다

Salesforce에서는

  • Storybook에는 org가 없다. org에서 브랜드 색과 로고는 Setup의 Themes and Branding에서 만든 커스텀 테마가 정하고, Activate를 누르면 모든 사용자에게 적용된다(Help). 메타데이터로는 BrandingSet(brandingSets/ 폴더)이고, BRAND_COLOR는 #54C254 같은 hex 문자열, BRAND_IMAGE는 로고 경로다(Metadata API)
  • org는 브랜드 색에서 팔레트를 만들어 쓰지만 그 결과는 API로 읽히지 않는다(05 테마 동기화). 그래서 두 모드 모두 같은 규칙(lib/palette.ts)으로 계산해 흉내 낸다
  • 프로젝트 모드는 org에 배포할 파일 자체(BrandingSet, 정적 리소스 milvusBrand.css·milvusBridge.css·milvusOverride.css)를 읽는다. 배포 전에 보는 화면과 배포할 내용이 같은 원본에서 나온다는 뜻이다. Storybook은 org와 같게 모든 LWC를 synthetic shadow로 그린다(04 통합)

  3. 패키지 의존성에 든 storybook 실행 파일을 지금 실행 중인 node로 직접 실행한다. 셸 없이 인자 배열로 넘기므로 경로에 공백·한글이 있어도 된다. 고객 프로젝트에 storybook을 따로 설치하지 않아도 된다
  4. 인자는 dev -c <패키지 .storybook의 실경로> --host localhost, 정적 빌드면 build -c … -o .milvus/storybook-static이다. 작업 폴더가 프로젝트라 캐시와 오류 로그가 패키지가 아니라 프로젝트에 생긴다
  5. 부모에게만 오는 종료 신호(SIGTERM, SIGHUP)를 Storybook에 넘기고, Storybook의 종료 코드를 그대로 돌려준다. 신호로 끝나면 128+신호 번호(Ctrl-C는 130)다
  • -c에 실경로: pnpm의 node_modules/<패키지>는 .pnpm/… 안 실제 폴더를 가리키는 심볼릭 링크다. 링크 경로를 넘기면 미리보기가 빈 화면이 되어서, .·..·심볼릭 링크를 푼 경로(realpath)를 넘긴다(설계 4.2, Task 3 스파이크). MILVUS_PROJECT_DIR도 같은 이유로 실경로다
  • --host localhost: 위 개념대로 그냥 띄우면 모든 네트워크 주소에서 듣는다. 프로젝트 모드는 server.fs.allow에 프로젝트 폴더가 들어가므로, 같은 네트워크의 다른 PC에 프로젝트 파일이 열릴 수 있다. 그래서 dev에는 항상 붙인다. 다른 PC에서 직접 읽어 보지는 않았다(설계 4.2) 미확인. 정적 빌드는 서버가 없어 붙이지 않는다

  • 가상 모듈 virtual:milvus-brands: mode와 brands(이름, 라벨, 출처, 팔레트, 브랜드 색, util·브리지·override CSS 문자열, 로고 data URL, 오류)를 내보낸다. brand.ts가 이것을 import한다. 정적 빌드에서는 빌드 당시의 값이 번들에 들어간다
  • 감시와 새로고침: 저장소 모드는 brands/와 templates의 정적 리소스, 프로젝트 모드는 milvus.config.json, brandingSets/, staticresources/, contentassets/를 감시한다. 아직 없는 파일도 잡도록 폴더를 본다. 바뀌면 가상 모듈을 무효화하고 전체 새로고침을 보낸다. 그래서 Claude가 milvusBrand.css를 고치면 Storybook이 저절로 바뀐다(08 브랜드 요청 → 반영 흐름)
  • 미들웨어 /__milvus/brand-request: 명세 페이지가 요청 파일을 읽고(GET) 쓴다(POST). 다음 절에서 다룬다
  • 오류: 프로젝트 모드에서 BrandingSet이 없거나, BRAND_COLOR가 틀리거나, milvusBrand.css가 util.css 규칙(lib/rules.ts, 설계 5.2)을 어기면 프로젝트 브랜드 대신 오류를 담은 "SLDS 기본" 하나만 준다. 화면 위에 이유와 pnpm milvus check --style 안내가 뜬다(설계 4.2, 10장)

브랜드 명세 페이지 구현

2026-10-13 추가(Task 19). Storybook 사이드바 시작하기 / 브랜드 명세는 "무엇을 바꿀 수 있고 지금 값은 무엇인가"를 보여 주고, 원하는 것을 받아 파일로 저장하는 페이지다. 저장한 파일은 Claude Code가 읽어 반영한다(08 브랜드 요청 → 반영 흐름).

개념

  • 브라우저의 페이지는 프로젝트 파일을 직접 쓸 수 없다. 그래서 페이지가 개발 서버에 요청을 보내고, 서버(Vite 미들웨어, 위 configureServer)가 파일을 쓴다. 정적 빌드에는 이 서버가 없다
  • 개발 서버는 요청이 같은 PC의 그 페이지에서 왔는지 가려야 한다. 브라우저는 다른 출처(origin) 요청과, 같은 출처라도 POST 같은 요청에 Origin 헤더(scheme·호스트·포트)를 붙인다. 같은 출처의 GET·HEAD에는 붙이지 않는다(MDN)
  • 문서 페이지 자동 생성(autodocs)을 전역으로 켰을 때 한 컴포넌트만 빼려면 그 meta의 tags에 '!autodocs'를 넣는다. 명세 페이지는 입력 폼이라 문서 탭에 같은 폼을 한 번 더 그리지 않으려고 이것을 쓴다

Salesforce에서는

  • 공식으로 브랜드를 정하는 화면은 Setup의 Themes and Branding이다. 관리자가 색 팔레트와 로고 등을 정하고 Activate로 모든 사용자에게 적용한다(Help). 명세 페이지의 "브랜드 색"·"로고"는 이 값(BrandingSet의 BRAND_COLOR·BRAND_IMAGE)을 바꾸자는 요청이다
  • Salesforce는 입력한 브랜드 색을 그대로 쓰지 않고 접근성 있는 색으로 바꿔 쓴다(01 Themes and Branding). 그래서 페이지는 입력 색과 실제 버튼 색(50단계), 링크 색(40단계)을 각각의 흰색 대비와 함께 보인다
  • SLDS 2 사이트의 Styling Hook Index는 global hook을 범주별로 이름과 라이트·다크 값으로 보여 준다. 값은 SLDS가 정하고 Salesforce가 언제든 바꿀 수 있으며, 고객 코드에서 global hook 값을 덮어쓰는 것은 지원하지 않는다고 적는다. 명세 페이지의 모양 항목 대부분은 이 hook을 바꾸자는 요청이라 공식 권고 밖이다(01 styling hook)

밀버스에서는

  • 입력은 네 가지 (2026-10-20 사용자 피드백): 브랜드 색, 로고, 피드백 색, 디자인 명세만 입력한다. 모두 선택이다. 처음에는 항목 34개마다 입력 칸이 있었는데, 처음 보는 사람이 "다 채워야 하나"로 받아들여 줄였다. 다른 디자인 시스템 문서(예: 슬랙 디자인 시스템의 색·간격 표)를 통째로 붙여 넣는 쓰임새도 사용자가 원했다
  • 디자인 명세 (옛 "전체 스타일"): 큰 여러 줄 입력칸에 표, 피그마 토큰 JSON, 사이트 주소, 자연어 등 무엇이든 붙여 넣는다. 사람이 항목을 고르지 않고 milvus-brand skill이 내용을 읽어 아래 "바꿀 수 있는 것"의 항목으로 나눈다. 붙여 넣은 줄바꿈은 그대로 저장된다
  • 바꿀 수 있는 것: 나머지 SPEC_ITEMS(lib/spec-items.ts, 설계 6.1, 9.3)는 입력 없이 묶음별 참고 카드로 그린다. 카드마다 설명, 예시, 한계, 접힌 지금 값 표가 있다. 항목 정의와 hook 목록은 그대로라 반영 검사도 그대로다(input만 "none"). 지금 값은 툴바에서 고른 브랜드를 적용한 :root의 계산값이고, 색은 #RRGGBB로 보인다. 정하지 않은 값은 "정하지 않음(SLDS 기본값 / Salesforce 원래 값)"이다
  • 바꿀 수 없는 것: 글꼴, 커서·링크 밑줄, 개체 아이콘 색, Salesforce 고정 목록(group: "표시만")은 "바꿀 수 있는 것"과 섞지 않고 맨 아래에 따로 보인다(00 반영 검사의 Salesforce 고정 합의)
  • 브랜드 색: 요청에 #RRGGBB가 있으면 같은 팔레트 규칙으로 버튼·링크 색과 대비를 미리 계산해 보인다
  • 피드백 색: 성공·경고·오류·정보마다 견본, 글자·배경 값, 배경 위·흰색 위 대비
  • 로고: 지금 로고와 "프로젝트 루트 기준 상대 경로" 입력. URL에서 받지 않는다
  • native 전환 시 잃는 부분: 브리지 변수를 쓰는 항목에 표시한다(01 브리지)
  • Salesforce 고정: 바꿀 수 없는 항목(lib/fixed-list.ts, 설계 9.4)을 "두 모드 모두 고정"과 "native 전환 뒤 생기는 고정"으로 나눠 보인다. 입력은 없다

저장과 요청 파일

  • 저장은 프로젝트 모드의 개발 서버에서만 된다. 저장소 모드와 정적 빌드에서는 입력이 꺼지고 이유가 뜬다
  • 페이지를 열면 프로젝트 루트의 milvus-brand-request.md를 읽어 입력을 채운다. 저장하면 파일 전체를 다시 쓴다. 저장 직전에 파일을 다시 읽어서, 페이지를 연 뒤 편집기로 고친 내용 가운데 페이지에서 바꾸지 않은 항목은 파일 쪽을 따른다
  • 디자인 명세 안에서 ## 로 시작하는 줄(붙여 넣은 문서의 제목)은 \## 로 적는다. 그대로 두면 다시 읽을 때 그 줄부터 새 절이 되기 때문이다. 이미 \로 시작하는 줄은 \를 하나 더 붙여, 읽을 때 하나만 떼면 원래 글이 된다(tests/request.test.ts)
  • 2026-10-20 전에 항목별 입력으로 저장한 절(## 모서리 등)은 지우지 않는다. 저장해도 원문 그대로 남고, 페이지가 그 절의 제목과 내용을 접힌 목록(details)으로 보여 준다(legacySections). skill은 그 항목에 반영하되, 같은 항목을 디자인 명세도 다루면 디자인 명세가 우선하고 반영 전에 충돌을 확인받는다. 필요 없는 옛 절은 사람이 요청 파일에서 지운다. 요청의 앞뒤 공백(첫 줄 들여쓰기 포함)은 지우고 안쪽 줄바꿈·들여쓰기는 그대로 둔다. 옛 제목 ## 전체 스타일은 디자인 명세로 읽고 다음 저장 때 ## 디자인 명세로 적는다
  • 빈 항목은 적지 않는다. 저장: 시각을 적고, 툴바가 프로젝트 브랜드이면 항목마다 그 순간의 지금: 값을 함께 적는다. 다른 브랜드를 보고 있거나 프로젝트 브랜드를 읽지 못했으면 지금 값을 모르므로 파일에 있던 지금: 줄을 그대로 둔다(saveRequest). Claude가 적은 반영: 줄은 저장할 때 지운다. 명세 항목이 아닌 줄과 절(사람이 적은 메모 등)은 지우지 않고 남긴다(lib/request.ts)

미들웨어의 안전장치

  • 쓰는 파일은 프로젝트 루트의 milvus-brand-request.md 하나로 고정이다. 요청 본문의 경로나 파일 이름은 보지 않는다

원본과 hook 보기 진행 중

2026-10-13 추가(Task 21). 카탈로그(컴포넌트 / 기본)의 컴포넌트 페이지마다 마지막 스토리 원본과 hook이 있다. 이 컴포넌트에 어떤 hook이 어디서 닿고 무엇이 hook으로 안 바뀌는지를 Salesforce 원본 파일과 함께 보여 준다(설계 9.5). 화면 구성은 리뷰 반영으로 바뀌는 중이라 여기서는 기능만 적는다. 설계 9.5의 미리보기는 아직 없다(아래 계획).

개념

  • 블루프린트: SLDS가 정한 컴포넌트의 마크업과 클래스다. Salesforce 기본 컴포넌트는 블루프린트를 구현한다. 예를 들어 lightning-button은 buttons 블루프린트를 구현하고, org 테마에 따라 SLDS 1이나 SLDS 2 모양이 된다(Component Reference)
  • styling hook: LWC 개발자 가이드는 styling hook을 SLDS 스타일시트 안의 자리표시자라고 설명한다. CSS 규칙이 var(--hook, 기본값)으로 읽는 이름이다. 그래서 "이 컴포넌트에 어떤 hook이 닿는가"는 원본 CSS의 var()를 따라가면 알 수 있다. 밀버스는 이 일을 정적 반영 검사로 한다(00 7절)
  • 필요할 때 불러오기: 원본 파일은 수백 개라 처음부터 다 싣지 않는다. Vite는 import 경로 끝에 ?raw를 붙이면 파일 내용을 문자열로 가져온다. 동적 import()는 모듈을 필요할 때 비동기로 불러오는 문법이다. Vite 문서의 비동기 청크 절은 이런 호출을 코드 분할된(code-split) 동적 import로 다룬다

Salesforce에서는

  • 공식 자료에서 hook을 보는 곳은 SLDS 2 사이트의 Styling Hook Index(global hook의 범주별 이름과 라이트·다크 값)와 Component Reference의 컴포넌트 페이지다. Component Reference의 lightning-button 페이지는 --slds-c-button-* 목록을 주지만 컴포넌트 hook은 SLDS 1에서만 지원된다고 적는다(01 styling hook)
  • SLDS 2 사이트의 Component-Level Styling Hooks 페이지는 --slds-c-*를 Beta·Developer Preview(정식 출시 아님, 운영에 쓰지 말 것)로 소개하고, 컴포넌트의 Specifications 탭에서 찾으라고 한다(확인 2026-10-13). LWC 개발자 가이드는 같은 hook을 SLDS 2에서 아직 지원하지 않는다고 적는다. 두 문서의 문구가 다르다. 밀버스 util.css는 어느 쪽이든 --slds-c-*를 쓰지 않는다(설계 5.2)
  • 컴포넌트가 읽는 g·s hook을 선택자별로 보여 주는 공식 페이지는 찾지 못했다(Specifications 탭의 hook 목록은 열어 보지 못했다) 미확인. 그래서 설치된 공식 패키지 원본에서 계산한다. lightning-base-components 1.28.19-alpha(설치본의 기본 컴포넌트 html·js·css와 native용 *.slds.css)와 @salesforce-ux/design-system-2 2.264.2(npm 설명상 컴포넌트별 원본 CSS가 dist/components/에 있다)다
  • 두 패키지의 LICENSE.txt는 같은 "Terms of Use"다(저작권 연도와 갱신일만 다르다). 소프트웨어를 복제하고 공개적으로 보여 주고 배포할 수 있게 허락하면서, 사본에는 이 약관을 함께 넣으라고 한다(설치본 확인). 그래서 원본을 보여 주는 곳에 약관 전문을 싣는다. 참고로 package.json의 license 칸은 lightning-base-components가 "MIT", @salesforce-ux/design-system-2가 "SEE LICENSE IN LICENSE.txt"다. 밀버스는 파일에 든 약관 전문을 따른다
  • 원본을 고쳐도 org는 바뀌지 않는다. LWC 개발자 가이드는 SLDS 클래스와 기본 컴포넌트 내부가 앞으로 바뀔 수 있어 CSS 덮어쓰기를 지원하지 않는다고 적는다. 이 보기는 고치는 곳이 아니라 확인 근거다

스스로 점검

Q1. 블로그 예제가 @storybook/addon-essentials를 설치하라고 한다. 어떻게 하나?

설치하지 않는다. 9부터 삭제됐고 controls, actions, viewport 등은 코어에 들어 있다. 문서 기능이 필요하면 @storybook/addon-docs만 따로 추가한다.

Q2. 웹 컴포넌트 스토리의 component에는 무엇을 넣나?

태그 이름 문자열이다. 예: component: 'demo-button'.

Q3. 배열 options를 LWC 컴포넌트에 넘길 때 options=${args.options}와 .options=${args.options} 중 무엇을 쓰나? 왜?

.options=. 앞의 것은 attribute라 문자열로 바뀌고, .을 붙여야 JS property로 배열이 그대로 전달된다. 우리 저장소의 lwc() 도우미는 처음부터 property로 넣는다.

Q4. 툴바 초기값을 globalTypes.brand.defaultValue에 넣었는데 적용되지 않는다. 왜?

9.0부터 초기값은 preview의 initialGlobals에서 온다. initialGlobals: { brand: 'Milvus_DesignSystem' }처럼 쓴다.

Q5. 툴바에서 Sample_Forest를 골랐다가 Milvus_DesignSystem으로 돌아오면 각진 모서리가 남나?

남지 않는다. applyBrand가 <style id="milvus-brand-util">의 내용을 새 브랜드의 util.css로 바꾸고(없으면 빈 문자열), 이전 팔레트도 지운 뒤 다시 넣는다.

Q6. 기획자에게 Storybook을 보여 주려면?

pnpm build-storybook으로 storybook-static을 만들어 정적 호스팅에 올리고 링크를 공유한다. 개발 서버나 org가 필요 없다. 다만 정적 사이트에서는 브랜드 명세 페이지의 입력이 꺼진다(저장할 서버가 없다).

Q7. 같은 .storybook/ 설정이 이 저장소와 고객 프로젝트에서 다른 브랜드를 보여 준다. 무엇으로 갈리나? (2026-10-13 추가)

환경 변수 MILVUS_PROJECT_DIR다. pnpm milvus storybook이 프로젝트 실경로를 넣어 주면 main.ts가 프로젝트 모드로 플러그인을 만든다. 플러그인의 가상 모듈 virtual:milvus-brands가 저장소면 brands/, 프로젝트면 BrandingSet과 staticresources/에서 브랜드를 만든다. brand.ts는 어느 쪽이든 같은 모양의 목록을 받는다.

Q8. 회의실의 다른 노트북에서 내 PC의 프로젝트 Storybook을 보여 주려고 IP 주소로 열었다. 왜 안 되고, 어떻게 보여 주나? (2026-10-13 추가)

pnpm milvus storybook은 개발 서버를 --host localhost로 띄운다. 프로젝트 모드는 프로젝트 폴더를 서빙할 수 있게 열어 두므로, 모든 네트워크 주소에서 들으면 같은 네트워크의 다른 PC에 프로젝트 파일이 열릴 수 있기 때문이다(다른 PC에서 직접 확인하지는 않았다). 보여 주려면 pnpm milvus storybook build로 정적 사이트를 만들어 공유한다. 요청 파일 저장(미들웨어)도 같은 PC에서 온 요청만 받는다.

Q9. "원본과 hook"의 원본 탭에서 button.css를 보니 고치고 싶은 값이 있다. 그 파일을 고치면 org 버튼이 바뀌나? (2026-10-13 추가)

바뀌지 않는다. 원본은 설치된 npm 패키지의 파일이고, org는 Salesforce가 내려주는 기본 컴포넌트를 쓴다. 고쳐도 내 Storybook만 바뀐다. 그 값이 hook으로 바뀌는지는 같은 페이지의 hook 표와 "hook이 닿지 않는 선언" 표에서 보고, 바꾸고 싶으면 브랜드 명세 페이지에 요청한다.
