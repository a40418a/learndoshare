LEARN 03 · Phase 1·3 준비

스토리북

밀버스 컴포넌트를 org 없이 보여 주는 카탈로그가 Storybook이다. 웹 컴포넌트용 설정, 스토리 작성법, 브랜드를 바꿔 보는 툴바까지 우리 프로젝트에 필요한 만큼만 정리한다.

예상 1.5시간선행: 02 LWC · 07 pnpm2026-09-26 작성 · 2026-10-09 갱신

왜 알아야 하나

LWC 컴포넌트는 원래 org 안에서만 보인다. 디자이너, 기획자, 다른 프로젝트 개발자가 "버튼이 어떻게 생겼나"를 보려고 매번 org에 들어갈 수는 없다. Storybook은 컴포넌트를 상태별(스토리)로 늘어놓은 정적 사이트를 만들어 준다.

LWC 소스force-app/.../lwc/
→
Rollup 사전 컴파일dist/lwc/에 JS 생성
→
요소 만들기LWC createElement로 DOM 요소를 만든다
→
Storybook스토리의 render가 그 요소를 돌려준다

Storybook 입장에서 우리 컴포넌트는 그냥 웹 컴포넌트다. 그래서 프레임워크는 @storybook/web-components-vite를 쓴다. 이 렌더러는 스토리가 돌려준 lit 템플릿, HTML 문자열, DOM 노드를 캔버스에 그린다 (렌더러 소스, 설치된 10.6.0에서도 같음). 우리 저장소는 lit 템플릿 대신 DOM 요소를 돌려준다 (stories/helpers.js의 lwc()). LWC를 Storybook 안에서 직접 컴파일하지 않는 이유와 요소를 만드는 방법은 04 통합에서 다룬다.

2026-10-09 갱신: 처음 계획은 CustomElementConstructor로 태그를 등록하고 lit html로 그리는 것이었다. 지금 저장소는 createElement로 요소를 만든다.

설치와 초기화

공식 문서는 npm create storybook@latest로 안내한다. 우리는 pnpm 형태로 바꿔 실행한다 (07 pnpm 대응표).

# 생성기 방식 (create-storybook 실행)
pnpm create storybook@latest

# 또는 설치 없이 CLI 일회성 실행
pnpm dlx storybook@latest init --type web_components --builder vite \
  --package-manager pnpm --features docs test a11y --yes --no-dev
플래그의미
--type web_components쓸 프레임워크(프로젝트 유형)를 지정한다
--builder viteVite 빌더 사용. @storybook/web-components-vite는 Vite ≥ 5가 필요하다
--package-manager pnpm의존성 설치를 pnpm으로
--features docs test a11y문서, 테스트, 접근성 기능을 질문 없이 함께 구성
--yes질문을 건너뛰고 모든 기능을 포함해 설치

export default {

  stories: ['../stories/**/*.mdx', '../stories/**/*.stories.js'],

pnpm hoisting 설정은 미리 넣지 않는다이 저장소는 hoisting 설정 없이 설치하고 실행한다 (.npmrc 없음). "Cannot find module"이 실제로 났을 때만 07 pnpm · hoisting 문제 해결 순서대로 publicHoistPattern을 좁게 추가한다. 설치 중 esbuild 빌드 승인 요청이 나오면 pnpm approve-builds(pnpm 10.1부터)로 승인한다. 저장소는 package.json의 pnpm.onlyBuiltDependencies에 esbuild를 넣어 두었다.

스토리 작성 (CSF3)

가장 작은 스토리

웹 컴포넌트 렌더러에서는 component에 태그 이름 문자열을 넣는다. render가 없으면 Storybook이 그 태그로 요소를 만들고 args를 JS property로 넣는다 (element[key] = value).

const meta = { component: 'demo-button' };
export default meta;

export const Primary = {
  args: { primary: true, label: 'Button' },
};

조금 더 갖춘 형태 (lit 사용 예)

import { html } from 'lit';

export default {
  title: 'Example/Button',
  component: 'demo-button',
  tags: ['autodocs'],              // addon-docs가 있으면 문서 페이지 자동 생성
  args: { label: 'Button', primary: false },
  argTypes: {
    label: { control: 'text' },
    primary: { control: 'boolean' },
  },
  render: (args) => html`<demo-button .label=${args.label} ?primary=${args.primary}></demo-button>`,
};

export const Primary = { args: { primary: true } };
export const Secondary = {};

lit 바인딩 네 가지

문법의 원문은 Lit 공식 문서 — Expressions다.

문법무엇을 설정하나예
x=${v}HTML attribute (항상 문자열)variant=${args.variant}
.x=${v}JS property (객체, 배열, 숫자 그대로).options=${args.options}
?x=${v}boolean attribute (true면 붙이고 false면 제거)?disabled=${args.disabled}
@x=${fn}이벤트 리스너@click=${args.onClick}
LWC의 @api 속성은 property로 넘긴다HTML attribute 값은 항상 문자열이라 배열이나 객체는 attribute로 넘기면 문자열이 되어 버린다. JS property 이름은 camelCase(iconName), HTML attribute 이름은 kebab-case(icon-name)다. 우리 저장소는 lit 바인딩을 쓰지 않고, stories/helpers.js의 lwc()가 args를 element[key] = value로 넣는다. property로 넘기는 것과 같다.

미확인 LWC 요소가 HTML attribute(icon-name="...")를 받아 @api property로 반영하는지, boolean attribute를 어떻게 해석하는지는 Storybook에서 시험하지 않았다. 저장소는 property만 쓰므로 지금은 영향이 없다.

decorator와 globals

globals는 모든 스토리가 공유하는 값(테마, 언어 등)이고, decorator는 스토리를 감싸는 함수다. 툴바에서 global을 바꾸면 decorator가 그 값을 읽어 스토리를 다시 그린다. 브랜드 전환은 이 구조로 만든다.

import { html } from 'lit';

export default {
  globalTypes: {
    theme: {
      description: 'Global theme for components',
      toolbar: {
        title: 'Theme',
        icon: 'circlehollow',
        items: ['light', 'dark'],
        dynamicTitle: true,          // 툴바에 선택된 값을 표시
      },
    },
  },
  initialGlobals: { theme: 'light' },
  decorators: [
    (story, context) => html`<div data-theme=${context.globals.theme}>${story()}</div>`,
  ],
};
옛 자료의 globals, defaultValuepreview의 globals는 8.2에서 deprecated, 9.0에서 삭제되고 initialGlobals로 바뀌었다. 초기값도 더 이상 globalTypes.defaultValue에서 오지 않는다 (MIGRATION.md). globalTypes와 initialGlobals는 .storybook/preview.*에만 쓴다.

브랜드 decorator 저장소 코드

2026-10-09 갱신: 아래는 저장소 .storybook/brand.js와 preview.js를 줄인 것이다. 브랜드 폴더를 읽어 툴바 항목을 자동으로 만든다. Vite의 import.meta.glob은 파일 패턴에 맞는 모듈을 한 번에 가져오고, CSS에 ?inline을 붙이면 페이지에 자동 주입하지 않고 CSS 문자열만 받는다.

// brands/<브랜드>/theme.json (pnpm sync:theme이 만든다)
const themes = Object.values(
  import.meta.glob('../brands/*/theme.json', { eager: true, import: 'default' })
);
export const brands = Object.fromEntries(themes.map((t) => [t.name, t]));

// brands/<브랜드>/util.css 를 문자열로 받는다 (페이지에 자동 주입하지 않음)
export const utilCss = Object.fromEntries(
  Object.entries(
    import.meta.glob('../brands/*/util.css', { query: '?inline', import: 'default', eager: true })
  ).map(([path, css]) => [path.split('/').at(-2), css])
);

export function applyBrand(name) {
  const root = document.documentElement;
  // ① 브랜드 색: theme.json의 palette → :root의 --slds-r-color-brand-* (org 테마 흉내)
  for (const prop of [...root.style])
    if (prop.startsWith('--slds-r-color-brand-')) root.style.removeProperty(prop);
  for (const [step, color] of Object.entries(brands[name]?.palette ?? {}))
    root.style.setProperty(`--slds-r-color-brand-${step}`, color);

  // ② 모양: 고른 브랜드의 util.css 하나만 문서 head에 (org의 loadStyle과 같은 위치)
  const style =
    document.getElementById('milvus-brand-util') ??
    document.head.appendChild(Object.assign(document.createElement('style'), { id: 'milvus-brand-util' }));
  style.textContent = utilCss[name] ?? '';
}
import '@salesforce-ux/design-system-2/dist/css/bundled/slds2.cosmos.css';
import { applyBrand, brands } from './brand.js';

export default {
  globalTypes: {
    brand: {
      description: '브랜드 (org Themes and Branding 시뮬레이션)',
      toolbar: {
        title: '브랜드',
        icon: 'paintbrush',
        items: Object.values(brands).map((t) => ({ value: t.name, title: t.label })),
        dynamicTitle: true,
      },
    },
  },
  initialGlobals: { brand: 'Milvus_DesignSystem' },
  decorators: [
    (story, context) => {
      applyBrand(context.globals.brand ?? 'Milvus_DesignSystem');
      return story();
    },
  ],
};
  • CSS 변수(custom property)는 부모에게서 상속되고, shadow 트리의 맨 위 요소는 호스트 요소에게서 상속받는다. 그래서 :root에 둔 값이 shadow DOM 안쪽 컴포넌트까지 닿는다
  • util.css는 :root에 선언하므로 문서 전체에 적용된다. 그래서 <style> 하나의 내용을 바꿔 끼워 한 번에 한 브랜드만 둔다. 팔레트도 바꾸기 전에 지운다
  • glob의 query: '?inline'은 Vite 문서의 두 규칙(glob의 query 옵션, CSS ?inline)을 합친 것이고, 저장소 brand.js가 실제로 이렇게 쓴다
  • paintbrush 아이콘 이름은 설치된 storybook 10.6.0 manager 코드의 아이콘 표에 있다 (PaintBrushIcon, 로컬 확인). 아이콘은 @storybook/icons 패키지에서 온다. 공식 예제는 circlehollow와 globe를 쓴다
  • 기본 우선 (2026-10-09 결정): brands/Milvus_DesignSystem/처럼 util.css가 없는 브랜드는 Salesforce 기본 모양에 브랜드 색만 바뀐다. 모양은 브랜드 요청이 있을 때만 바꾼다
이전 설계 (2026-10-09 갱신)예전 예시는 brands/<브랜드>/root.css에 --milvus-* 변수만 두고, theme.json의 hooks를 래퍼 div의 인라인 CSS 변수로 넣었다. root.css는 util.css 하나로 합쳤고(#11), 브랜드 색은 래퍼가 아니라 :root의 팔레트로 넣는다. accent hook이 :root에서 계산되기 때문이다 (brand.js 주석).
시뮬레이션이다툴바로 브랜드를 바꿔도 org는 바뀌지 않는다. org가 브랜드 색에서 자동으로 만드는 팔레트는 API로 읽히지 않는다. 그래서 pnpm sync:theme이 우리 규칙(scripts/palette.mjs)으로 계산해 theme.json의 palette에 저장한다. 2026-10-08 org 프로브에서 활성화한 브랜드 색 #2E7D32의 LEX accent #468244가 이 규칙의 50단계와 같았다 (05 테마 동기화).

인터랙션 테스트

스토리에 play 함수를 붙이면 렌더링 후 사용자 동작을 흉내 내고 결과를 검사한다. expect와 fn은 storybook/test에서 가져오고, userEvent와 canvas는 play 함수의 인자로 받는다.

import { html } from 'lit';
import { expect, fn } from 'storybook/test';

export const Clicked = {
  args: { label: 'Save', onClick: fn() },
  render: (args) => html`<demo-button .label=${args.label} @click=${args.onClick}></demo-button>`,
  play: async ({ canvasElement, args, userEvent }) => {
    await userEvent.click(canvasElement.querySelector('demo-button'));
    await expect(args.onClick).toHaveBeenCalled();
  },
};

미확인 컴포넌트 내부(shadow DOM 안쪽) 요소를 찾아 클릭하는 방법은 LWC 요소에서 아직 시험하지 않았다. 위 예시는 호스트 요소를 클릭한다.

화면 캡처 비교(시각 회귀 테스트)는 Storybook 팀이 만든 클라우드 서비스 Chromatic으로 한다(@chromatic-com/storybook). 도입 여부는 미정이다.

사이드바 로고

Storybook 화면 왼쪽 위 로고와 제목은 manager 쪽 테마로 바꾼다. 공식 문서 Theming 페이지 기준 import 경로는 storybook/manager-api와 storybook/theming이다. 테마 객체는 합쳐지지 않고 통째로 바뀐다. base만 필수다.

import { addons } from 'storybook/manager-api';
import { create } from 'storybook/theming';

// main.mjs의 managerHead가 brands/Milvus_DesignSystem/theme.json 내용을 넣어 준다
const brand = window.MILVUS_BRAND ?? {};

addons.setConfig({
  theme: create({
    base: 'light',                    // 필수. 나머지는 선택
    brandTitle: '밀버스 디자인 시스템',
    brandImage: brand.logo ? `static/brands/${brand.name}/${brand.logo}` : undefined,
    colorPrimary: brand.brandColor,
  }),
});

manager(사이드바)는 툴바의 브랜드 선택과 따로 돈다. 그래서 로고는 기본 브랜드 하나로 정한다. 저장소는 GitHub Pages 하위 경로에서도 열리도록 상대 경로(static/brands/…)를 쓴다. 공식 문서도 하위 경로에 배포할 때는 상대 경로를 쓰라고 한다. Theming 페이지는 절대 URL 예만 보여 주고 상대 경로 해석은 설명하지 않는다.

우리 프로젝트 적용

Storybook이 맡는 역할 (2026-10-09 갱신)

Storybook은 브랜드를 org에 배포하기 전에 눈으로 확인하는 곳이다. 기본 상태는 Salesforce 기본 모양에 브랜드 색과 로고만 바꾼 것이다.

  1. 관리자가 org Setup의 Themes and Branding에서 브랜드 색과 로고를 정한다
  2. pnpm sync:theme이 org 테마를 brands/<브랜드>/theme.json(브랜드 색, 계산한 팔레트)과 로고 파일로 가져온다 → 브랜드 툴바와 사이드바 로고에 반영
  3. 브랜드 요청이 있을 때만 brands/<브랜드>/util.css에 hook 값을 쓴다 → 같은 툴바로 바로 확인
  4. 컴포넌트는 "기본"(Salesforce 공식 예제를 그대로 컴파일한 카탈로그)과 "밀버스 추가"로 나뉜다
층파일Storybook에서 반영되는 곳
브랜드 색brands/<브랜드>/theme.json의 palettebrand.js가 :root의 --slds-r-color-brand-*로 넣는다
로고brands/<브랜드>/logo.*main.mjs의 managerHead → manager.js의 brandImage
모양 (요청이 있을 때만)brands/<브랜드>/util.cssbrand.js가 문서 head의 <style id="milvus-brand-util">로 넣는다. :root의 --slds-g-*, 색이 아닌 --slds-s-*, --milvus-*만 쓴다
  • 스토리는 stories/helpers.js의 lwc(tag, Ctor, props)로 LWC 요소를 만들어 돌려준다. @api 값은 property로 들어간다
  • preview.js의 tags: ['autodocs']로 모든 스토리에 문서 페이지가 생긴다
  • 다음 단계 계획 패키지를 설치한 프로젝트에서 pnpm milvus storybook이 패키지 안의 설정으로 Storybook을 띄운다. 그때 util.css는 staticresources/milvusBrand.css다 (설계 문서 4.2). 아직 구현 전이다
이전 설계 (2026-10-09 갱신)예전 계획은 L1 theme.json(색) / L2 logo.png / L3 brands/<브랜드>/root.css(--milvus-*만, --slds-g-*는 읽기만) 세 층이었다. 또 scripts/create-project.mjs --brand X --components badge,button로 브랜드·컴포넌트별 Storybook을 따로 만들려 했다. root.css는 util.css로 합쳤고, create-project.mjs는 pnpm milvus init(계획)으로 바뀌었다.

스스로 점검

Q1. 블로그 예제가 @storybook/addon-essentials를 설치하라고 한다. 어떻게 하나?

설치하지 않는다. 9부터 삭제됐고 controls, actions, viewport 등은 코어에 들어 있다. 문서 기능이 필요하면 @storybook/addon-docs만 따로 추가한다.

Q2. 웹 컴포넌트 스토리의 component에는 무엇을 넣나?

태그 이름 문자열이다. 예: component: 'demo-button'.

Q3. 배열 options를 LWC 컴포넌트에 넘길 때 options=${args.options}와 .options=${args.options} 중 무엇을 쓰나? 왜?

.options=. 앞의 것은 attribute라 문자열로 바뀌고, .을 붙여야 JS property로 배열이 그대로 전달된다. 우리 저장소의 lwc() 도우미는 처음부터 property로 넣는다.

Q4. 툴바 초기값을 globalTypes.brand.defaultValue에 넣었는데 적용되지 않는다. 왜?

9.0부터 초기값은 preview의 initialGlobals에서 온다. initialGlobals: { brand: 'Milvus_DesignSystem' }처럼 쓴다.

Q5. 툴바에서 Sample_Forest를 골랐다가 Milvus_DesignSystem으로 돌아오면 각진 모서리가 남나?

남지 않는다. applyBrand가 <style id="milvus-brand-util">의 내용을 새 브랜드의 util.css로 바꾸고(없으면 빈 문자열), 이전 팔레트도 지운 뒤 다시 넣는다.

Q6. 기획자에게 Storybook을 보여 주려면?

pnpm build-storybook으로 storybook-static을 만들어 정적 호스팅에 올리고 링크를 공유한다. 개발 서버나 org가 필요 없다.
