## 1. GitHub 토큰 만들기

패키지는 GitHub Packages에 있다. 이 레지스트리는 공개 패키지도 설치할 때 토큰을 요구한다.

1. GitHub → Settings → Developer settings → Personal access tokens → **Tokens (classic)** → Generate new token (classic)
2. 권한은 **`read:packages`** 하나만 고른다. 만료일을 둔다
3. 토큰 값은 파일·채팅·문서에 쓰지 않는다. 아래처럼 환경 변수 `NODE_AUTH_TOKEN`에만 둔다

출처: [GitHub Docs — Working with the npm registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-npm-registry) · [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

## 2. `NODE_AUTH_TOKEN` 넣기

### macOS

토큰을 키체인에 한 번 넣고, 셸이 시작할 때 꺼내 쓴다. 토큰이 `~/.zshrc`나 셸 기록에 남지 않는다.

```bash
# -w를 맨 끝에 두면 토큰을 입력하라고 묻는다
security add-generic-password -a "$USER" -s milvus-npm-token -w
echo 'export NODE_AUTH_TOKEN="$(security find-generic-password -a "$USER" -s milvus-npm-token -w)"' >> ~/.zshrc
```

새 터미널을 연다. 토큰을 새로 만들면 첫 명령에 `-U`를 붙여 갱신한다.

### Windows

1. 시작 메뉴에서 **"계정의 환경 변수 편집"** 을 연다
2. 사용자 변수 → **새로 만들기** → 이름 `NODE_AUTH_TOKEN`, 값에 토큰을 붙여 넣는다
3. 열려 있던 Git Bash·VS Code·Claude 앱을 모두 닫고 다시 연다(새 프로세스부터 보인다)

## 3. `.npmrc` 두 줄

<table>
  <thead>
    <tr><th>줄</th><th>둘 곳</th><th>이유</th></tr>
  </thead>
  <tbody>
    <tr><td>`//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}`</td><td>사용자 파일 `~/.npmrc`</td><td>pnpm 10.34.2·11.5.3부터 프로젝트 `.npmrc`의 `${…}` 토큰은 풀지 않고 무시한다(커밋되는 파일이 토큰을 다른 곳으로 보내지 못하게)</td></tr>
    <tr><td>`@a40418a:registry=https://npm.pkg.github.com`</td><td>프로젝트 `.npmrc`</td><td>팀원도 같은 레지스트리에서 받는다. 3장에서 설치 전에 넣는다</td></tr>
  </tbody>
</table>

토큰 줄은 한 번만 넣는다. 작은따옴표 안이라 `${NODE_AUTH_TOKEN}`이 글자 그대로 들어가고, pnpm이 읽을 때 환경 변수로 바꾼다.

```bash
grep -q npm.pkg.github.com ~/.npmrc 2>/dev/null || printf '//npm.pkg.github.com/:_authToken=${NODE_AUTH_TOKEN}\n' >> ~/.npmrc
```

출처: [pnpm — Auth & Registry Settings](https://pnpm.io/npmrc) · [pnpm 10.x — .npmrc](https://pnpm.io/10.x/npmrc)

## 4. pnpm 11이면 `pnpm-workspace.yaml`

`pnpm -v`가 11 이상이면 3장의 설치 **전에** 프로젝트 폴더에 이 파일을 둔다. pnpm 10이면 건너뛴다.

```yaml
minimumReleaseAgeExclude:
  - '@a40418a/*'
allowBuilds:
  esbuild: true
```

<table>
  <thead>
    <tr><th>설정</th><th>없으면 생기는 일</th></tr>
  </thead>
  <tbody>
    <tr><td>`minimumReleaseAgeExclude`</td><td>기본 `minimumReleaseAge`(1440분) 때문에 발행한 지 하루가 안 된 밀버스 버전 대신 이전 버전이 설치된다</td></tr>
    <tr><td>`allowBuilds`</td><td>기본 `strictDepBuilds` 때문에 Storybook이 쓰는 esbuild 설치 스크립트가 막혀 `ERR_PNPM_IGNORED_BUILDS`로 끝난다</td></tr>
  </tbody>
</table>

pnpm이 `allowBuilds` 자리를 이미 만들어 두었으면 덧붙이지 말고 파일을 위 내용으로 바꾼다. 같은 키가 두 번 있으면 YAML 오류다.

출처: [pnpm — Dependency Resolution Settings](https://pnpm.io/settings/dependency-resolution) · [pnpm — Build Settings](https://pnpm.io/settings/build)

## 5. org 로그인

```bash
sf org login web --alias my-org
sf org list
```

- 별칭(`my-org`)은 3장의 `--target-org`에 그대로 쓴다
- 실습은 각자 개인 Developer Edition이나 스크래치 org로 한다. 배포는 org 전체 화면을 바꾼다([8. 함께 해 보기](?path=/docs/런북-8-함께-해-보기--docs))
- `sf org display`, `sf org list --json`, `sf auth list --json`, `sf org open --url-only`처럼 **액세스 토큰을 출력하는 명령은 쓰지 않는다**. 별칭 확인은 `--json` 없는 `sf org list`로 한다
